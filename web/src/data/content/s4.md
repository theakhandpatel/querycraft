# Dates are not a type

A monthly report asks how many customers signed up in each month of 2026. `customers.signup_date` is declared `DATE` and holds `2025-11-02`, which is text, so a row written as `31/01/2026` leaves every month total without an error.

SQLite has no date type. It has text shaped like a date, functions that read that text as a calendar, and a sort order that follows the calendar. This chapter covers all three, because calendar work in SQLite depends on the text format holding still.

## The declared type does not survive the write

Chapter 2 explained affinity: a declared type picks the rule SQLite uses to convert a value, and the word you write is mostly a label. `DATE` and `TIMESTAMP` are not in the affinity table, so they get NUMERIC affinity, which converts a value only when it looks like a number. `2025-11-02` does not look like a number, so it stays text. The declared `DATE` therefore predicts nothing about a row, and the only check available is to ask `typeof` about a stored value.

You can check that on the stored rows:

```sql
SELECT id, signup_date, typeof(signup_date) AS stored
FROM customers
ORDER BY id
LIMIT 3;
```

| id | signup_date | stored |
| --- | --- | --- |
| 1 | 2025-11-02 | text |
| 2 | 2025-11-15 | text |
| 3 | 2025-12-01 | text |

`orders.ordered_at` is declared `TIMESTAMP` and behaves the same way. It holds `2026-01-04 10:12`, and `typeof` calls it text.

The declared word still matters. It tells the reader of the schema what the column means, and a tool can use it to pick a format when it renders a value. SQLite itself will not reject `banana` in either column. The declared type is a note about intent, and the storage class is what actually happened.

## The format is chosen for its sort order

Text comparison walks two strings from the left and stops at the first character that differs. If every character matches up to the end of one string, the shorter string sorts first. Put the biggest unit of time first and that rule sorts days correctly: the year decides before the month, and the month decides before the day.

Zero padding does the rest. Every field keeps the same width, so a comparison never confuses the month field with the day field. Run this:

```sql
SELECT '2026-01-10' < '2026-01-09' AS padded,
       '2026-1-10' < '2026-1-9' AS unpadded;
```

| padded | unpadded |
| --- | --- |
| 0 | 1 |

The padded answer is false, which is correct: 10 January is not before 9 January. The unpadded answer is true, which is wrong, because the character `1` sorts before `9`. Dropping one leading zero breaks a whole reporting year.

That is why the storage format matters more here than the declared type. Write `YYYY-MM-DD`, then a space, then `HH:MM`. Keep the leading zeros. The default collation compares bytes, and the digits and dashes of ISO-8601 sit in the same order as the calendar in any character set SQLite ships.

## The functions are the calendar

Because the value is text, SQLite needs a function to know that a string is a date. The functions take text that matches a recognised format and return text or a number. The ones worth knowing:

| Function | Returns |
| --- | --- |
| `date(x)` | `YYYY-MM-DD` |
| `time(x)` | `HH:MM:SS` |
| `datetime(x)` | `YYYY-MM-DD HH:MM:SS` |
| `strftime(format, x)` | the formatted string |
| `julianday(x)` | a Julian day number |
| `unixepoch(x)` | seconds since 1970 |

`date`, `time` and `datetime` normalise a value to a fixed shape. `strftime` builds the shape you ask for. `julianday` and `unixepoch` turn text into a number, which is how you do arithmetic on days.

The failure mode is quiet. A string the parser cannot read returns NULL, and it does not raise an error:

```sql
SELECT strftime('%Y-%m', '2026-01-31') AS good,
       strftime('%Y-%m', '31/01/2026') AS bad;
```

| good | bad |
| --- | --- |
| 2026-01 | NULL |

A null disappears from a `GROUP BY` without a word. A row with a mis-typed date is not reported as broken; it is simply not in the group. Compare the two counts and you see the problem:

```sql
SELECT COUNT(*) AS rows, COUNT(strftime('%Y-%m', signup_date)) AS dated
FROM customers;
```

| rows | dated |
| --- | --- |
| 30 | 30 |

Both numbers agree here, so every signup date in this file parses. When they disagree, the difference is your count of unreadable dates. That comparison is worth running once on any date column you inherit.

## Group by month with a format string

Grouping by month is the pattern to learn, because most date questions reduce to it. PostgreSQL uses `DATE_TRUNC('month', ordered_at)::date`. SQLite writes the first of the month with a format string:

```sql
SELECT strftime('%Y-%m-01', ordered_at) AS month, COUNT(*) AS orders
FROM orders
GROUP BY month
ORDER BY month;
```

| month | orders |
| --- | --- |
| 2026-01-01 | 16 |
| 2026-02-01 | 19 |
| 2026-03-01 | 18 |
| 2026-04-01 | 18 |
| 2026-05-01 | 9 |

Read it one stage at a time. The table holds 80 rows, each with its own `ordered_at` text. The format string `%Y-%m-01` takes the year from each value, then the month, then drops the day and time and writes `-01` in their place.

Sixteen rows from January all become the identical string `2026-01-01`. `GROUP BY` collapses those sixteen into one group, and `COUNT(*)` counts what landed in it. `ORDER BY month` sorts text, which is the same as sorting by date because of the format.

Try this: run the two counts from the previous section on `orders.ordered_at` instead of `signup_date`. Both come out 80, because the five groups above already account for every row in the table.

`%Y` is the four-digit year and `%m` is the zero-padded month. `-01` is a literal: `strftime` copies any character it does not recognise.

## A range filter is a text comparison

`WHERE` on a date column compares text, and `BETWEEN` is a common way to get that wrong. Here is a filter for March, written the way most people write it first:

```sql
SELECT COUNT(*) AS march_orders
FROM orders
WHERE ordered_at BETWEEN '2026-03-01' AND '2026-03-31';
```

| march_orders |
| --- |
| 17 |

Seventeen. The month table in the previous section says 18, and both queries read the same file. The missing row is here:

```sql
SELECT id, ordered_at
FROM orders
WHERE ordered_at >= '2026-03-30' AND ordered_at < '2026-04-01'
ORDER BY ordered_at;
```

| id | ordered_at |
| --- | --- |
| 1053 | 2026-03-31 04:00 |

`2026-03-31 04:00` is longer than `2026-03-31` and shares its first ten characters, so it sorts after the bound. The `BETWEEN` upper bound means midnight at the start of 31 March, not the end of that day, and one order falls outside it.

The fix is to stop naming the last day and name the first day of the next period instead.

```sql
SELECT COUNT(*) AS march_orders
FROM orders
WHERE ordered_at >= '2026-03-01' AND ordered_at < '2026-04-01';
```

| march_orders |
| --- |
| 18 |

A lower bound that is inclusive and an upper bound that is exclusive has no gap and no overlap, whatever precision the values carry. The exercise that follows asks for one year of signups, so use the same shape there. Include the first day of the year and exclude the first day of the next.

## Arithmetic is a modifier string

SQLite has no `INTERVAL` type. Date arithmetic is a modifier string passed as an extra argument to `date()`, `time()`, or `datetime()`. The modifiers are `'+1 month'`, `'-7 days'`, `'+2 hours'`, `'start of month'`, and their relatives. Several modifiers apply left to right.

```sql
SELECT date('2026-01-31', '+1 month') AS plus_month,
       julianday('2026-02-01') - julianday('2026-01-01') AS days;
```

| plus_month | days |
| --- | --- |
| 2026-03-03 | 31 |

A month added to 31 January should land in February, and February has no 31st. SQLite does not clamp to 28 February. It adds a month to the day number and normalises the overflow, which walks into March. The modifier shifts a calendar field by a count, and it knows nothing about how long a month is.

Put `'start of month'` first and the answer is what you expected:

```sql
SELECT date('2026-01-31', 'start of month', '+1 month') AS first_of_next;
```

| first_of_next |
| --- |
| 2026-02-01 |

The first modifier moves the day to the 1st, and adding a month to the 1st cannot overflow. Modifier order matters, and this is the case where it shows.

To measure a span, subtract two Julian day numbers. `julianday` returns a real number, so 1 January to 1 February is exactly 31 days.

Modifiers also work on stored rows. Here a seven-day promise on the pending orders:

```sql
SELECT id, ordered_at, date(ordered_at, '+7 days') AS ships_by
FROM orders
WHERE status = 'pending'
ORDER BY ordered_at
LIMIT 3;
```

| id | ordered_at | ships_by |
| --- | --- | --- |
| 1011 | 2026-01-18 10:00 | 2026-01-25 |
| 1018 | 2026-01-30 09:00 | 2026-02-06 |
| 1025 | 2026-02-11 08:00 | 2026-02-18 |

`date()` returns only the date part, so `ships_by` drops the time. Ask `datetime()` when the time matters.

A seed date plus `'+1 month'` inside a `WITH RECURSIVE` CTE is the SQLite replacement for PostgreSQL's `generate_series`, and it is how you build a month spine that includes the months with no rows. The porting course builds that series.

## Keep the text as the record

The format is the contract, so fix it where values enter and read it everywhere else. A date written as `02/11/2025` is ambiguous to a person and useless to `strftime`, and a table holding both formats cannot be sorted at all.

Time zones test the text form. SQLite has no time zone type, and `'now'` is UTC, so `date('now')` gives today in UTC rather than today on your wall clock. The `'localtime'` modifier converts to the host's zone, which makes the result depend on the machine that runs the query.

The machine interface tests it too. When another program needs the value, `unixepoch` gives an integer that sorts and compares without any format rules:

```sql
SELECT id, ordered_at, unixepoch(ordered_at) AS epoch
FROM orders
ORDER BY id
LIMIT 2;
```

| id | ordered_at | epoch |
| --- | --- | --- |
| 1001 | 2026-01-04 10:12 | 1767521520 |
| 1002 | 2026-01-19 16:40 | 1768840800 |

`unixepoch` reads the text as UTC. Keep ISO-8601 text as the stored record and convert at the edge, where you know which zone the other system expects. A dedicated time-series store, or a column of epoch integers agreed by everyone, is the choice when timestamps arrive at high volume and queries slice by the second.

## What to remember

What I would do: store ISO-8601 text with the padding kept. Filter with `>=` the first day of a period and `<` the first day of the next. Count `strftime` results against `COUNT(*)` on any date column you inherit. Put `'start of month'` before `'+1 month'` when the day can be the 29th, 30th or 31st.

- SQLite has no date type. `DATE` and `TIMESTAMP` are declared names that end up holding text.
- ISO-8601 text with a fixed width and zero padding sorts in calendar order, which is why range filters and `ORDER BY` work.
- An unreadable date returns NULL instead of raising, so bad rows leave a group without a message. Count the parsed values to find them.
- `strftime('%Y-%m-01', ...)` turns a timestamp into the first of its month, and grouping on it is the month rollup.
- Filter with an inclusive lower bound and an exclusive upper bound on the next period, never `BETWEEN` two whole dates.
- Date arithmetic is a modifier string, applied left to right, and `'start of month'` is what makes month addition safe.

## Check yourself

**1. Why does a date stored as text still sort and compare like a date?**

<details>
<summary>Answer</summary>

Because ISO-8601 puts the largest unit first and pads every field to a fixed width. Text comparison reads left to right, so the year decides before the month and the month before the day, and no field can be mistaken for its neighbour.

</details>

**2. A monthly report counts 30 rows but `COUNT(strftime('%Y-%m', signup_date))` returns 28. What happened to the other two?**

<details>
<summary>Answer</summary>

Two values do not parse as dates, so `strftime` returned NULL for them. `COUNT(expression)` skips nulls, so the difference is the count of unreadable values. Read those two rows with `WHERE strftime('%Y-%m', signup_date) IS NULL` and fix the data at the write path.

</details>

**3. Why does `ordered_at BETWEEN '2026-03-01' AND '2026-03-31'` lose an order that the month rollup counts?**

<details>
<summary>Answer</summary>

`2026-03-31 04:00` is longer than `2026-03-31` and shares its prefix, so it sorts after the upper bound. An exclusive bound on the first day of the next month has no such gap.

</details>

**4. You need the first day of the month after 31 January. Why does `date('2026-01-31', '+1 month')` fail, and what does the correction do?**

<details>
<summary>Answer</summary>

Adding a month to the 31st lands on a day February does not have. SQLite normalises the overflow into March and returns 2026-03-03. `'start of month'` moves the day to the 1st first, and adding a month to the 1st gives 2026-02-01.

</details>
