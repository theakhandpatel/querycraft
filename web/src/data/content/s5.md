# LIKE, GLOB and collations

A search for `jacket` returns an empty table. The value is there: the products table stores `Trail Runner Jacket`, and one pattern finds it. Four of the six patterns in this chapter return nothing, and none of them raises an error. A pattern bug reads as missing data.

The first query a learner writes tries the exact name:

```sql
SELECT name
FROM products
WHERE name = 'Jacket';
```

No rows. `=` compares two whole values, so nothing matches. A pattern solves this. SQLite gives you two pattern operators, and they disagree about case and about syntax. Pick the wrong one and the page comes back empty with no error, so the data takes the blame for a pattern bug.

## LIKE folds ASCII case

`LIKE` treats `%` as any run of characters, including none, and `_` as exactly one character. A pattern also has to cover the whole value, so most searches need `%` at both ends. It folds case before it compares:

```sql
SELECT 'Ada' LIKE 'a%'  AS like_lowercase,
       'Ada' GLOB 'a*'  AS glob_lowercase,
       'Ada' LIKE 'A%'  AS like_uppercase,
       'Ada' GLOB 'A*'  AS glob_uppercase;
```

| like_lowercase | glob_lowercase | like_uppercase | glob_uppercase |
| --- | --- | --- | --- |
| 1 | 0 | 1 | 1 |

Read the mechanism and the four numbers stop being arbitrary. For `LIKE`, SQLite converts every ASCII letter from `A` to `Z` in both operands to lowercase, then compares. `Ada` becomes `ada`, so it matches `a%` and it also matches `A%`. `GLOB` compares the bytes as stored: the byte for `A` is 65 and the byte for `a` is 97, so `Ada` does not match `a*`.

The fold happens during the comparison. It does not change what the table holds, and it does not follow the value into the result. `SELECT name FROM products` still returns `Trail Runner Jacket` with its capitals.

Each expression returns `1` or `0`, because SQLite has no boolean storage class. Chapter 2 covers that.

With that rule, a pattern query on the fixture behaves the way you predict:

```sql
SELECT name
FROM products
WHERE name LIKE '%ack%'
ORDER BY name;
```

| name |
| --- |
| Pulse Fitness Tracker |
| Trail Runner Jacket |

Two products contain those three letters. Walk the second match through the pattern: the leading `%` takes `Trail Runner J`, `ack` matches inside `Jacket`, and the trailing `%` takes `et`.

The engine tries each start position until one works, so a leading `%` is the expensive shape: no byte-ordered index has a range to seek, and the search reads every name. `%ACK%` and `%Ack%` return the same two rows, because once the fold runs the pattern carries no case information.

## The fold stops at ASCII

Only the 26 letters `A` to `Z` fold. Every other character compares as its own bytes, so an accented pair does not match. Measure three cases in one query:

```sql
SELECT 'É' LIKE 'é' AS accented_like,
       'Ada' LIKE 'A_a' AS one_underscore,
       'Abba' LIKE 'A_a' AS four_letters;
```

| accented_like | one_underscore | four_letters |
| --- | --- | --- |
| 0 | 1 | 0 |

The first column is the limit. SQLite stores text as UTF-8 bytes, and the fold table covers the 26 uppercase letters of ASCII. `É` is two bytes that fold to nothing, while `é` is two different bytes, so the comparison fails. The `lower()` function has the same limit: `lower('É')` returns `É` unchanged. An app in a language with accents needs a different plan, and SQLite's built-in operators will not supply it. Store a folded copy of the text in its own column, or normalise the value in your program before you store it.

The last two columns cover `_`, which matches exactly one character.

## GLOB is the Unix pattern

`GLOB` takes its wildcards from the shell. `*` matches any run of characters, `?` matches one character, and `[a-c]` matches one character from a set. A leading `^` inside the brackets negates the set, so `[^a-z]` means any character that is not a lowercase letter. None of these wildcards know about files or directories, so `*` matches anything, separators included.

The curriculum demo uses one product name:

```sql
SELECT name
FROM products
WHERE name GLOB '*Jacket*'
ORDER BY name;
```

| name |
| --- |
| Trail Runner Jacket |

One row, because `GLOB` compares bytes and the stored name spells `Jacket` with a capital `J`. `'*ACK*'` returns nothing, since no product spells those letters in capitals.

Try this: change `'*Jacket*'` to `'*ACK*'` and run the query again. The table comes back empty, because no stored name spells those letters in capitals. Then run the same letters through `LIKE '%ACK%'` and two rows return, because `LIKE` folds the pattern and the value to lowercase.

Keep this pair as a reference:

| | LIKE | GLOB |
| --- | --- | --- |
| Case | folds ASCII `A` to `Z` | compares bytes, so case must match |
| Any run of characters | `%` | `*` |
| One character | `_` | `?` |
| Character set | none | `[a-c]`, `[^a-c]` |
| Literal wildcard | `ESCAPE '\'` | bracket, as in `[*]` |

The escape column is the one people skip. `LIKE` takes an `ESCAPE` clause that makes the next character literal. `GLOB` has no such clause, so you put the character in brackets instead:

```sql
SELECT '100%' LIKE '100\%' ESCAPE '\' AS percent_is_literal,
       '100'  LIKE '100\%' ESCAPE '\' AS no_percent,
       'a*b'  GLOB 'a[*]b'            AS star_is_literal;
```

| percent_is_literal | no_percent | star_is_literal |
| --- | --- | --- |
| 1 | 0 | 1 |

Which operator you reach for follows from the question. Use `LIKE` for a search a person typed, where `jacket` should find `Trail Runner Jacket`. Use `GLOB` when case carries meaning, as it does in a code or a filename where `sku-a` and `SKU-A` are different rows.

## The two wildcard languages do not mix

Zero rows from a pattern query has four common causes. Each row below is measured on the twenty products, and only two of the six return anything.

| pattern | rows |
| --- | --- |
| `name = 'Jacket'` | 0 |
| `name LIKE 'jacket%'` | 0 |
| `name LIKE '%jacket%'` | 1 |
| `name GLOB '%jacket%'` | 0 |
| `name GLOB '*jacket*'` | 0 |
| `name GLOB '*Jacket*'` | 1 |

The third row is the query most searches want, and the sixth is the one the curriculum demo runs. The four failures each have one cause.

The first row has no pattern at all, so `=` compares whole values. The second fails because `LIKE 'jacket%'` is anchored at the start of the value, and no name starts with `jacket`. The fourth fails because `%` is an ordinary character to `GLOB`, so the pattern asks for a literal percent sign that no product name contains. The fifth fails because `GLOB` will not fold the capital `J`.

This is the mistake to expect. A learner writes `WHERE name GLOB '%jacket%'` after a LIKE that worked, changes only the operator name, and gets an empty table.

Nothing warns them, because the pattern is valid SQL and the query is well-formed. The correction changes the wildcard and the case together:

```sql
SELECT name
FROM products
WHERE name GLOB '*Jacket*'
```

When a pattern returns nothing, check the wildcard character first, then the case, then the anchor. Those three checks cover every failing row of the table. Change one thing at a time, so the row count tells you which change did the work.

The difference from PostgreSQL is worth one line. PostgreSQL's `LIKE` is case-sensitive and `ILIKE` is the folded version, so a pattern query does not carry over unchanged.

The exercise asks you to count one set of letters twice, once with each operator. Keep each operator in its own subquery, and work out both numbers from the rules above before you run them. An empty table is the cheapest mistake to catch early.

## Which operator an index can serve

An index on a text column stores the values in byte order, and a range lookup walks that order. That order is what a folded `LIKE` cannot use. `LIKE 'A%'` can match a value starting with `A` or with `a`, and the two sit in different parts of a byte-ordered index, so the planner has no narrow range to seek. `GLOB` compares bytes, so its pattern still starts at one place in the index.

The measured plans below come from an index added to `customers(name)`; the dataset ships none.

| setup | plan for `WHERE name LIKE 'A%'` |
| --- | --- |
| plain index on `name` | SCAN, walking the whole index |
| index on `name COLLATE NOCASE` | SEARCH, over a range of names |
| plain index, `WHERE name GLOB 'A*'` | SEARCH, over a range of names |

The rule is one sentence long: a folded `LIKE` needs an index built in a folded collation, and a `GLOB` prefix works with a plain one. A pattern with no fixed prefix, such as `'%a'`, offers nothing to seek in any collation. The next chapter reads these plan lines properly.

One switch changes the first row of that table. `PRAGMA case_sensitive_like = 1` turns the fold off for the connection, and then `LIKE 'A%'` compares bytes and can use the plain index. The switch changes the meaning of every `LIKE` on that connection, so existing queries and existing indexes have to move together. Leave it off when a search box should forgive case.

## A collation decides order and equality

A collation is the rule SQLite uses to compare two text values. It decides equality, less-than, `BETWEEN`, `ORDER BY`, `GROUP BY`, `DISTINCT` and the order of entries inside an index. Every text column has one. Without a declaration, the collation is `BINARY`, which compares UTF-8 bytes. PostgreSQL takes its collation from the operating system or ICU, set per database or per expression, and ships far more than three. SQLite ships the three below and lets a column or an expression choose one.

`BINARY` is why `=` ignores case only when you ask it to:

```sql
SELECT (SELECT COUNT(*) FROM customers WHERE name = 'ada whitfield') AS binary_match,
       (SELECT COUNT(*) FROM customers WHERE name = 'ada whitfield' COLLATE NOCASE) AS nocase_match;
```

| binary_match | nocase_match |
| --- | --- |
| 0 | 1 |

Customer 1 is `Ada Whitfield`. `BINARY` compares the bytes and the capital `A` does not equal `a`, so the plain comparison finds nothing. `COLLATE NOCASE` folds ASCII before comparing, so the pair matches. The phrase applies to this one comparison. It changes neither the stored value nor the column.

The same rule runs the sort:

```sql
SELECT name FROM customers ORDER BY name COLLATE NOCASE;
```

You get 30 rows back, and on this fixture they arrive in the order you expect. Every customer name starts with a capital, so folding changes nothing. A fixture with mixed case would not be so kind, and literals show the rule that the data hides:

```sql
SELECT 'apple' < 'Banana' AS binary_cmp,
       'apple' < 'Banana' COLLATE NOCASE AS nocase_cmp,
       'Zebra' < 'apple' AS caps_first;
```

| binary_cmp | nocase_cmp | caps_first |
| --- | --- | --- |
| 0 | 1 | 1 |

Start with `caps_first`. Under `BINARY`, `Z` is byte 90 and `a` is byte 97, so `Zebra` sorts before `apple`. That is a correct byte comparison and a wrong alphabetical order for a person. The second column shows the fix: fold both sides, `B` becomes `b`, and `apple` comes before `Banana`.

Grouping follows the same comparison. `GROUP BY city` under `NOCASE` would put `Leeds` and `leeds` in one group, and under `BINARY` in two. The fixture stores one spelling per city.

## BINARY, NOCASE and RTRIM

SQLite ships three built-in collations. Each one changes the comparison, and only the first is the default.

| collation | rule | measured difference |
| --- | --- | --- |
| `BINARY` | compare bytes | `Zebra` sorts before `apple` |
| `NOCASE` | fold ASCII `A` to `Z`, then compare bytes | `apple` sorts before `Banana` |
| `RTRIM` | ignore trailing spaces, then compare bytes | `'a' = 'a '` is 1 |

A column can also declare its collation, and then every comparison on that column inherits the rule with no `COLLATE` phrase. A `TEXT COLLATE NOCASE` email column matches `ADA@EXAMPLE.COM` against `ada@example.com`. In this fixture `email` has no such declaration, so that comparison returns 0.

`RTRIM` exists because some engines pad fixed-width text columns with spaces. SQLite stores exactly what you insert, so a trailing space arrives only when the data carries one. Here is the comparison it changes:

```sql
SELECT 'a' = 'a ' AS binary_eq,
       'a' = 'a ' COLLATE RTRIM AS rtrim_eq;
```

| binary_eq | rtrim_eq |
| --- | --- |
| 0 | 1 |

Counting with `RTRIM` treats `'a'` and `'a '` as one value. Under the default they are two.

`NOCASE` carries the same ASCII limit as `LIKE`. `'a' = 'A' COLLATE NOCASE` returns 1, and `'Á' = 'á' COLLATE NOCASE` returns 0, because neither accented character folds. When you need case-insensitive matching outside ASCII, fold the value yourself and store the result.

One more consequence ties the chapter together. A collation is part of an index, not a decoration on a query. An index serves only the collation it was built with:

```sql
CREATE INDEX customers_name_nocase ON customers (name COLLATE NOCASE);
```

With that index in place, `WHERE name = 'ada whitfield' COLLATE NOCASE` becomes an index `SEARCH`. The plain `WHERE name = 'ada whitfield'` cannot use it, because that comparison runs in `BINARY`, so it needs its own plain index on `name`. On this fixture both comparisons search once both indexes exist, and each one uses the index that matches its collation.

A lesson query does not create indexes, so treat this as a decision you make when you own the schema, and make it before the table fills. Changing the collation of a column later means rebuilding its indexes.

## What to remember

What I would do: pick the operator from the data, not from habit. Use `LIKE '%term%'` for a search a person types, and `GLOB '*Term*'` only when case carries meaning. When a pattern returns nothing, check the wildcard, then the case, then the anchor, one change at a time. If you own the schema and the search must fold case, build the index as `COLLATE NOCASE` before the table fills.

- `LIKE` folds ASCII `A` to `Z` before comparing, so it matches `Jacket` from `%jacket%` and from `%JACKET%`.
- `LIKE` takes `%` for any run and `_` for one character. `GLOB` takes `*`, `?` and `[...]`, and compares bytes, so its case must match.
- Both folds and both collations stop at ASCII. Values with accents need a folded column of your own.
- A collation decides equality, order and index order. `BINARY` puts capitals before lowercase, `NOCASE` folds first, and `RTRIM` ignores trailing spaces.
- A folded `LIKE` cannot use a plain index. Build the index on a `COLLATE NOCASE` column when you own the schema.

## Check yourself

**1. `WHERE name LIKE '%ack%'` returns two rows and `WHERE name GLOB '*ack*'` also returns two. Why do both work here, when the two operators disagree about case?**

<details>
<summary>Answer</summary>

Both products spell those letters in lowercase, in `Pulse Fitness Tracker` and `Trail Runner Jacket`. `LIKE` folds and would match anyway. `GLOB` compares bytes, and the stored bytes are already lowercase, so the exact-case pattern matches too. Change the pattern to `%ACK%` and only `LIKE` returns two rows.

</details>

**2. You write `WHERE name GLOB '%jacket%'` and get an empty table. Give both reasons the pattern fails, and the pattern that fixes them.**

<details>
<summary>Answer</summary>

`%` is an ordinary character to `GLOB`, so the pattern asks for a literal percent sign. `jacket` is lowercase while the stored name spells `Jacket`, and `GLOB` does not fold case. `'*Jacket*'` fixes both: `*` is the run wildcard and `Jacket` matches the stored bytes.

</details>

**3. Why do both sort orders match on this fixture, and what would break the match?**

<details>
<summary>Answer</summary>

Every customer name starts with a capital. Folding the ASCII letters therefore changes no comparison. The orders differ as soon as one value starts with a lowercase letter, because `BINARY` places every capital before every lowercase letter.

</details>

**4. You build `CREATE INDEX customers_name_nocase ON customers (name COLLATE NOCASE)` and nothing else. Which comparison can use it, `name = 'ada whitfield'` or `name = 'ada whitfield' COLLATE NOCASE`?**

<details>
<summary>Answer</summary>

The second one. The index stores its entries in `NOCASE` order, and an index serves only the collation it was built with. The plain comparison runs in `BINARY`, so with only this index it scans. Give that comparison its own plain index on `name` and it searches.

</details>
