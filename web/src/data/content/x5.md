# Booleans, numerics and the value contract

You port the revenue query from the PostgreSQL course, with the same joins and the same filters, and the total comes back as `1803.6200000000001`. The same port breaks `row.active === true`, because the flag arrives as `1`.

Neither problem is in your SQL. Both live in the value: what the column promises, what the engine stores, and what crosses into your program.

## The declared type is a promise the engine does not keep

The SQLite schema keeps the PostgreSQL type names, because they read as documentation: `products.price` is `NUMERIC NOT NULL` and `products.active` is `BOOLEAN NOT NULL DEFAULT 1`.

Neither is a type in the sense the PostgreSQL course taught you. SQLite stores each value in one of five storage classes: NULL, INTEGER, REAL, TEXT and BLOB. A storage class describes the value in the file, not the column, so one column holds an integer in one row and a real in the next.

A check written against the declared type is a check against nothing, and it runs without complaint.

The declared type selects an affinity: the rule for which storage class a written value gets. A name containing `TEXT` keeps text, `REAL` gets a real, `INT` gets an integer, and everything else gets NUMERIC affinity. Under it, a whole number is stored as an integer, a number with a fraction as a real, and anything else as text.

Because `BOOLEAN` and `NUMERIC` land in the same bucket, one rule answers most of this chapter. A value contract has three layers: the spelling in your query, the storage class the engine picks, and the value your program receives. Get the third one wrong and a plausible number fails a comparison.

## TRUE is one, FALSE is zero

```sql
SELECT TRUE AS t, FALSE AS f, typeof(TRUE) AS t_stored;
```

| t | f | t_stored |
| --- | --- | --- |
| 1 | 0 | integer |

`TRUE` and `FALSE` are keywords rather than a type, and here they are the integers 1 and 0. PostgreSQL returns `t` and `f` and calls the column `boolean`; SQLite returns 1 and 0 and calls it `integer`. Turning it back into a boolean is your program's decision.

The dataset shows the same shape in a real column.

```sql
SELECT id, name, active, typeof(active) AS stored
FROM products
WHERE id IN (1, 20);
```

| id | name | active | stored |
| --- | --- | --- | --- |
| 1 | Aurora Wireless Earbuds | 1 | integer |
| 20 | Discontinued Camp Stove | 0 | integer |

Nineteen products carry 1 and one carries 0. Because the flag is a number, `SUM(active)` counts the true rows, `SUM(NOT active)` the false ones, and `AVG(active)` gives the true share. The exercise leans on that.

A `STRICT` table accepts only `INT`, `INTEGER`, `REAL`, `TEXT`, `BLOB` and `ANY`, so it rejects a `BOOLEAN` column outright. Port a `boolean` column as `INTEGER` holding 1 or 0, and keep `BOOLEAN` as a label for a reader, never as the storage.

## A wrong turn: the filter that matches nothing

Suppose you saw `'true'` in a JSON payload and wrote the filter that way.

```sql
SELECT COUNT(*) AS active_products
FROM products
WHERE active = 'true';
```

| active_products |
| --- |
| 0 |

There is no error, and zero is a believable count for a quiet store. The same predicate against the PostgreSQL dataset returns 19, because there the literal is cast to `boolean`.

The comparison has to cross storage classes. NUMERIC affinity tries to convert `'true'` to a number, and `'true'` does not look like one, so it stays text. SQLite ranks the classes in a fixed order, with every integer below every text value. Both 1 and 0 are less than `'true'`, so the equality is false on every row.

The obvious repair makes it worse. `WHERE active = CAST('true' AS INTEGER)` returns 1 row, because `CAST('true' AS INTEGER)` is 0: a cast converts and does not validate.

The filter now matches the inactive product and returns a wrong set with no complaint. Three spellings, three answers: 0, 1 and 19. Only the last one matches the question.

The fix is to stop comparing the flag to text. `active` on its own is a truth value, because 0 is false and every other number is true: `WHERE active` returns 19 rows, and `WHERE NOT active` returns 1.

## Money has no fixed scale

In PostgreSQL, `price numeric(10,2)` always prints two places. The type holds an exact decimal, and the scale is part of it: `139.00` and `42.50`, never `139` and `42.5`.

A SQLite `NUMERIC` column is an affinity, and no affinity carries a scale. The seed writes `59.00` and the column stores the integer 59. It writes `42.50` and the column stores the real 42.5, because there is a fraction to keep. Ten of the twenty prices land as integers and ten as reals.

The scale you declared is gone. Read three rows and the same column gives three pictures.

```sql
SELECT id, price, typeof(price) AS stored, printf('%.2f', price) AS shown
FROM products
WHERE id IN (4, 5, 20);
```

| id | price | stored | shown |
| --- | --- | --- | --- |
| 4 | 42.5 | real | 42.50 |
| 5 | 139 | integer | 139.00 |
| 20 | 0 | integer | 0.00 |

`printf('%.2f', price)` is where the two-decimal form comes back, and it belongs at the edge, in the projection that names the column. Leave it out and a JSON client receives `139` where PostgreSQL sent `139.00`, so a price renders with no decimals.

Try this: drop `printf('%.2f', price)` from that projection and read the row with id 5. The column returns `139`, the integer in the file, while the row with id 4 still returns `42.5`. The `printf` was the only thing carrying the declared scale.

## REAL arithmetic puts noise in a total

Addition is where the missing scale becomes visible.

```sql
SELECT SUM(1.0 * oi.quantity * oi.unit_price)          AS raw_revenue,
       ROUND(SUM(1.0 * oi.quantity * oi.unit_price), 2) AS rounded_revenue
FROM orders o
JOIN order_items oi ON oi.order_id = o.id
WHERE o.status = 'completed'
  AND strftime('%Y-%m', o.ordered_at) = '2026-04';
```

| raw_revenue | rounded_revenue |
| --- | --- |
| 1803.6200000000001 | 1803.62 |

PostgreSQL returns `1803.62` for the same query, because its sum runs in `numeric`, which adds exact decimals. SQLite's sum runs in REAL, which is binary floating point, so each addition rounds to the nearest representable double. Two decimal places do not fit that grid, and the leftover shows in the last digit.

`ROUND(x, 2)` at the edge is the fix, and it is a contract fix rather than a cosmetic one. An accepted answer compares cells, so a result carrying an artifact of how the engine summed fails on something other than your logic.

The `1.0` is deliberate, and it is the part people drop. `quantity` is INTEGER and `unit_price` is NUMERIC, so the class of the product depends on the row: 79 of the 160 lines multiply to an integer and 81 multiply to a real. Multiplying by `1.0` first makes every line real before any addition happens, so the noise is the same on every run.

Drop it and the sum still ends real, because one real operand turns the running total real partway through, at a row that depends on order. On this data both spellings land on the same number in every month. The explicit `1.0` is still the habit, because it makes the result independent of the order the rows arrive in.

## Identity becomes the rowid

PostgreSQL's `serial` and `GENERATED ... AS IDENTITY` create a sequence object beside the table. `nextval` advances it, and the id column is fed from it.

Every SQLite table already has an identity: a hidden `rowid`, the physical address of the row. Declaring `INTEGER PRIMARY KEY` makes your column an alias for that value. The engine assigns the next rowid on insert, with no second object to own and no call to make.

The difference appears after a delete, and a scratch table shows it.

```sql
CREATE TABLE scratch (id INTEGER PRIMARY KEY, note TEXT);
INSERT INTO scratch (note) VALUES ('first'), ('second');
DELETE FROM scratch WHERE id = 2;
INSERT INTO scratch (note) VALUES ('third');
SELECT id, note FROM scratch;
```

| id | note |
| --- | --- |
| 1 | first |
| 2 | third |

A plain `INTEGER PRIMARY KEY` hands out one more than the largest id present, so the third row takes 2. Add `AUTOINCREMENT` and the same script gives the third row 3. That keyword promises an id is never issued twice, and it pays with a `sqlite_sequence` table, which appears in `sqlite_master` and is written on every insert.

Port `serial` to `INTEGER PRIMARY KEY`, and reach for `AUTOINCREMENT` only when the application needs the never-reuse promise, such as an id already printed on an invoice. `RETURNING` ports directly: `INSERT ... RETURNING id` works. `last_insert_rowid()` is the older alternative, and a trigger that inserts a row of its own leaves it pointing at the wrong id.

## Building text with `||` and printf

`||` means concatenation in both dialects, and the NULL rule is the same: `'a' || NULL` is NULL, because one unknown part makes the whole result unknown.

```sql
SELECT CAST(59 AS TEXT) || ' units' AS with_units,
       printf('%.2f', 42.5)        AS fixed_scale,
       (1 || 2)                    AS concat_nums;
```

| with_units | fixed_scale | concat_nums |
| --- | --- | --- |
| 59 units | 42.50 | 12 |

`1 || 2` is `'12'`, because the operator converts both sides to text first. `CAST(x AS TEXT)` and `x || ''` are the same conversion.

What differs is the vocabulary around the operator. PostgreSQL's `concat()` skips NULL arguments and `concat_ws()` joins with a separator. Both reached SQLite in 3.44, so `concat('a', NULL)` returns `a` and `concat_ws('-', 'a', NULL, 'b')` returns `a-b`. The portable expression is still `||` with an explicit `COALESCE`.

## What to remember

What I would do: declare a flag as `INTEGER`, read it as a number, and never compare it to a string. Round a money sum in the projection and print prices through `printf('%.2f', price)`, so the two decimals travel with the result. Port `serial` to `INTEGER PRIMARY KEY`, and keep the declared type as a note to the reader rather than a rule for the engine.

- The declared type picks an affinity, not a constraint. `BOOLEAN` and `NUMERIC` both get NUMERIC affinity, so the storage class follows the value.
- `TRUE` and `FALSE` are the integers 1 and 0, and a `STRICT` table refuses to declare a `BOOLEAN` column.
- Comparing a flag to a string is false on every row, and casting that string to an integer silently selects the wrong set.
- A money column keeps no scale, so `printf('%.2f', ...)` restores the two decimals and `ROUND(x, 2)` cleans a REAL sum.
- `INTEGER PRIMARY KEY` is the port of `serial`, because the column aliases the rowid. `AUTOINCREMENT` adds a never-reuse promise and a `sqlite_sequence` table.

## Check yourself

**1. Why does `SELECT COUNT(*) FROM products WHERE active = 'true'` return 0 rather than 19?**

<details>
<summary>Answer</summary>

`'true'` stays text because it cannot become a number. SQLite ranks every integer below every text value, so both `1 = 'true'` and `0 = 'true'` are false. PostgreSQL casts the literal to `boolean` and returns 19.

</details>

**2. `CAST('true' AS INTEGER)` returns 0. What does that say about casts here?**

<details>
<summary>Answer</summary>

A cast converts and does not validate. `'true'` has no numeric prefix, so the conversion yields 0, and a filter built on it selects the inactive product. PostgreSQL raises an error instead.

</details>

**3. April revenue is exact in PostgreSQL and ends in `0000000000001` here. Where did that enter?**

<details>
<summary>Answer</summary>

In the sum. PostgreSQL adds `numeric` values, which hold exact decimals. SQLite adds REAL values, which hold the nearest double, and 1803.62 has no exact double.

</details>

**4. What does `AUTOINCREMENT` add to `INTEGER PRIMARY KEY`?**

<details>
<summary>Answer</summary>

A never-reuse promise on ids, at the cost of a `sqlite_sequence` table that appears in the catalog and is written on every insert. A plain key reuses the largest id after a delete.

</details>
