# Making a predicate sargable

Customer 7 has 184 orders in the perf fixture, and the support console reads all 10 000 to show the five oldest. The query compares text with text, `WHERE customer_id::text = '7'`, because the id reaches the page as a string. Five rows come back, with 9 816 nobody asked for.

The predicate is not wrong; it is unsargable. That word comes from *Search ARGument able*: a predicate shaped so that an index can bound it. Write `customer_id = 7` and the plan reads 184 rows instead of 10 000.

## The shape the index needs

A B-tree index is a sorted copy of one column, each entry pointing at a row. Sorted order is what makes a lookup cheap. The engine compares keys and stops once they pass the value it wants, instead of reading rows one at a time.

That trick needs one side of the comparison to be the bare column, with a constant or a parameter on the other.

```sql
WHERE customer_id = 7                          -- sargable
WHERE customer_id IN (7, 8, 9)                 -- sargable
WHERE ordered_at >= '2026-03-01'
  AND ordered_at <  '2026-04-01'               -- sargable
WHERE UPPER(status) = 'REFUNDED'               -- not: which key would the index seek?
WHERE customer_id::text = '7'                  -- not: the comparison is on a cast, not the column
```

The first three predicates give the index something to work with: a value to seek, or a pair of bounds to walk between. The last two put a computed text value on the left, which the index does not store, so it cannot help. On this fixture the difference is 184 rows read against 10 000, on every load of that page.

The rule generalises: any expression between the index and the column hides the column from the planner. Nothing warns you, because the index still exists and the rows still come back. The plan simply becomes a `Seq Scan` with a `Filter`.

A `Seq Scan` reads every row in storage order, and the `Filter` runs on each row after that read. `Rows Removed by Filter` counts the rows read and thrown away.

## Functions on the column

The index on `orders.status` holds 10 000 values, one of five texts. `UPPER(status)` is a sixth value, computed once per row, and the index has never seen it. PostgreSQL reads all 10 000 rows:

```text
Seq Scan on orders  (cost=0.00..2650.00 rows=50 width=4)
  Filter: (upper(status) = 'SHIPPED'::text)
```

The estimate says 50 rows, and 9 000 orders are shipped. That 50 is module 4's default of 0.5% of the relation, applied because no statistic exists for `upper(status)`. The assumption is 180 times too small.

Written on the bare column, the same predicate estimates 9 000 rows, because the MCV list records that shipped covers 90% of the table. Both plans read the whole relation, and here that is correct: one pass beats 9 000 index lookups. `WHERE status = 'refunded'` goes further and seeks `orders_status_idx`, with a measured estimate rather than a guess.

The estimate does damage downstream. The planner sizes a hash table, picks a join order and decides whether to sort from that number. A filter believed to return 50 rows when it returns 9 000 makes a bad join look cheap.

When a rewrite is available, take it: normalise the constant, so `WHERE status = 'refunded'` replaces `UPPER(status) = 'REFUNDED'`. Replace a date function with a half-open range:

```sql
-- this day
WHERE ordered_at >= '2026-03-01' AND ordered_at < '2026-03-02'
-- this year
WHERE ordered_at >= '2026-01-01' AND ordered_at < '2027-01-01'
```

The exclusive upper bound is also the only correct way to say "this day" about a timestamp. The second block replaces `EXTRACT(YEAR FROM ordered_at) = 2026`. When the expression is the right domain model and no rewrite fits, the escape hatch is an expression index: `CREATE INDEX ON orders (UPPER(status))`. That is a real fix, and it costs storage and work on every insert.

## Casts

The exercise's query, which shows customer 7's five oldest orders, is the same mistake in a different wrapper. First the cast:

```text
Limit  (cost=2675.83..2675.84 rows=5 width=20)
  ->  Sort  (cost=2675.83..2675.96 rows=50 width=20)
        Sort Key: ordered_at
        ->  Seq Scan on orders  (cost=0.00..2675.00 rows=50 width=20)
              Filter: ((customer_id)::text = '7'::text)
```

Then the bare column:

```text
Limit  (cost=580.58..580.59 rows=5 width=20)
  ->  Sort  (cost=580.58..581.04 rows=184 width=20)
        Sort Key: ordered_at
        ->  Bitmap Heap Scan on orders  (cost=5.71..577.52 rows=184 width=20)
              Recheck Cond: (customer_id = 7)
              ->  Bitmap Index Scan on orders_customer_id_idx  (cost=0.00..5.67 rows=184 width=0)
                    Index Cond: (customer_id = 7)
```

Read the first plan from the inside out. `Seq Scan on orders` reads all 10 000 rows, and `Filter` builds a text value from each `customer_id` to keep the 184 that equal `'7'`. The estimate says 50, because a comparison on an expression has no statistic.

`Sort` orders the survivors and `Limit` stops after five.

The second plan finds the same five rows through `orders_customer_id_idx`. `Index Cond: (customer_id = 7)` is a seek on integer keys. The bitmap holds 184 row positions, `Bitmap Heap Scan` fetches them, and the estimate is 184, the truth. The sort runs in both plans over the same 184 rows; only the way those rows are found changes.

The literal is the other way to get this wrong. `customer_id = '7'` is fine: the bare column sits on the left, and the untyped literal is parsed into the column's type before the predicate exists. `customer_id = '7'::text` is an error, because no operator compares an integer with a text.

PostgreSQL also inserts casts of its own, so comparing `integer` with `text` converts one side, which is a cast around the column in all but name. Comparing `text` with `varchar` costs nothing, because the types are binary-compatible. A cast to the column's own type is folded away, so `customer_id::int = 7` still seeks the index.

## `OR` and `IN`

`IN (7, 8, 9)` is normalised to `customer_id = 7 OR customer_id = 8 OR customer_id = 9`. When every branch is indexable, the planner runs one index scan per value and unions the row positions into a bitmap, which is a `BitmapOr`. One pass over the table then fetches all three sets of rows.

Neither `IN` nor `OR` is a problem by itself. A branch with no index is the problem.

```sql
-- both columns are indexed: BitmapOr
SELECT id FROM orders WHERE customer_id = 7 OR status = 'refunded';

-- tracking_code has no index: one sequential scan for the whole predicate
SELECT id FROM orders WHERE customer_id = 7 OR tracking_code = 'QC00055433';
```

The first query plans as a `Bitmap Heap Scan` over a `BitmapOr` of `orders_customer_id_idx` and `orders_status_idx`. It estimates 233 rows and returns 232, because two of customer 7's orders are also refunded and the `Recheck Cond` settles those rows once.

The second query plans as a `Seq Scan` on the whole `OR`. Its answer includes rows that only the unindexed branch can find, so PostgreSQL reads every order and the indexed branch buys nothing.

If the branches really are two questions, an `UNION ALL` of two indexed queries is a fair rewrite: each branch gets its own access path.

## `LIKE` prefixes

A pattern anchored at the start is a range in disguise. `LIKE 'Aurora%'` matches every string that sorts at or after `Aurora` and before `Aurorb`, so a B-tree can seek that range. It can do so only when the index's collation makes sort order match pattern order. In practice that means an index with the `text_pattern_ops` operator class, or a database using the `C` collation:

```sql
CREATE INDEX products_name_pattern_idx ON products (name text_pattern_ops);
```

Without that index the pattern is tested on every row. The perf fixture holds 500 products, and exactly one is `Aurora Wireless Earbuds`. A `Seq Scan` with a `Filter` on `name ~~ 'Aurora%'` reads all 500 to find it, and it estimates 3 rows rather than 1.

The answer is one row and the work is 500.

`LIKE '%Aurora%'` is worse: the match can start anywhere, so there is no lower bound to seek and no B-tree helps. That case needs a trigram index (`pg_trgm`) or full-text search, which are different tools. `ILIKE` lands in the same category, because an index ordered by case-sensitive bytes cannot answer a case-insensitive match.

## `IN` versus `EXISTS`

The two forms often answer the same question and often produce the same plan.

```sql
SELECT c.name
FROM customers c
WHERE c.id IN (SELECT o.customer_id FROM orders o WHERE o.status = 'refunded');

SELECT c.name
FROM customers c
WHERE EXISTS (SELECT 1 FROM orders o WHERE o.customer_id = c.id AND o.status = 'refunded');
```

The planner may turn either one into a semi join: a join that returns each left row once, with no columns from the right. `IN (subquery)` usually becomes a hashed semi join over the distinct subquery values. `EXISTS` usually becomes a nested-loop semi join that stops at the first matching row per customer. Which costs less depends on the sizes, and the plan says which one you got.

The reason to reach for `EXISTS` is correctness, and the trap needs a nullable column. Ask which customers' email is absent from the Leeds list: `NOT IN` returns nothing at all, while `NOT EXISTS` returns 1 714 rows. The subquery holds a `NULL` because 47 of the 333 Leeds customers have no email, and `x <> NULL` is never true.

**Try this:** swap `NOT EXISTS` for `NOT IN` in the Leeds question. The answer goes from 1 714 rows to no rows at all, with the same subquery and the same tables.

When the id set comes from a nullable column, use `NOT EXISTS`, or filter the nulls out explicitly. `orders.customer_id` is `NOT NULL` in this fixture, so the queries above are safe either way.

## What to remember

**What I would do:** keep the column bare on the left and move the work to the constant. Write `customer_id = 7` rather than `customer_id::text = '7'`, and normalise the constant rather than wrap the column in a function. Then read the estimate as a check on the shape: a wrapped predicate on this table always says 50, whatever it matches. When the id set comes from a nullable column, use `NOT EXISTS`.

| Instead of | Write | Why it helps |
| --- | --- | --- |
| `UPPER(status) = 'REFUNDED'` | `status = 'refunded'` | the index bounds the bare column, and the guessed estimate goes away |
| `DATE(ordered_at) = ...` | a half-open range on `ordered_at` | both bounds land on the bare column |
| `customer_id::text = '7'` | `customer_id = 7` | a cast on the column hides it; a typed literal does not |
| `name LIKE '%Aurora%'` | a trigram or full-text index | a leading wildcard has no seekable bound |

Some rewrites feel as though they should help and do not. `LIMIT` on an aggregate changes nothing, because the aggregate reads every row. `SELECT *` dropped from a scan saves columns, not rows. Join order belongs to the planner, so reordering `FROM` changes nothing (module 5).

- An index needs a bare column on one side of the comparison. Any function or cast around the column hides it.
- A wrapped column also loses its statistics. The estimate falls back to 0.5% of the relation, so the number becomes a guess.
- A date function becomes a half-open range, and an anchored `LIKE` needs the right operator class before it is a range.
- `OR` and `IN` are fine while every branch is indexable. One unindexable branch costs the whole predicate.
- `NOT IN` with a `NULL` in the subquery returns nothing. `NOT EXISTS` is the safe form.

## Check yourself

**1. A colleague writes `WHERE UPPER(status) = 'REFUNDED'` and the plan estimates 50 rows. The fixture really holds 50 refunded orders, so the estimate looks right. Why is the query still a liability?**

<details>
<summary>Answer</summary>

The 50 is the default, not a measurement. Any wrapped predicate on this table estimates 50 rows. `UPPER(status) = 'SHIPPED'` would estimate 50 while matching 9 000, so the number is right by coincidence and wrong by 180 times for the next constant.

</details>

**2. `customer_id = '7'` seeks the index. `customer_id::text = '7'` reads the table. The quotes look the same, so what differs?**

<details>
<summary>Answer</summary>

The untyped literal is not text yet. PostgreSQL parses `'7'` into the column's type before it builds the predicate, so the comparison is integer against integer. The double colon forces the column itself to text, one value per row, and the integer index has no key to match.

</details>

**3. You need one day of orders from a timestamp column. Why stop before the next midnight rather than compare dates?**

<details>
<summary>Answer</summary>

Both bounds land on the bare column. `ordered_at` carries a time, so stopping before the next midnight includes every time in that day. A bound at midnight keeps only the first instant, and a date function hides the column.

</details>

**4. `WHERE customer_id = 7 OR tracking_code = 'QC00055433'` reads all 10 000 orders, even though `customer_id` has an index. Why does that branch buy nothing?**

<details>
<summary>Answer</summary>

The answer must include rows that only the unindexed branch can find, and `tracking_code` has no index. A sequential scan is the only way to test that side. Once every row is being read, an index path for the other side adds work. Splitting the query with `UNION ALL` gives each branch its own path.

</details>
