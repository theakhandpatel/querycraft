# Reading a query plan without EXPLAIN ANALYZE

The demo query returns five orders, and it takes the same time whether SQLite seeks the index on `customer_id` or reads all 80 rows. The stopwatch cannot separate the two. A plan that scans 80 rows returns the same five rows as a plan that seeks them, so nothing on screen tells you which one ran.

The engine knows, and it will say so before it runs anything. This chapter reads that answer. The app grades result rows, so a plan that visits every order still returns the right answer, and the first sign of trouble is a table that grew. That is exactly when the plan is cheapest to read. A plan is the list of steps SQLite chose, and reading it turns "the query is slow" into "the query scans, and I expected a search".

One thing you cannot do here: measure. SQLite has no `EXPLAIN ANALYZE`, so no plan in this course carries a real row count next to an estimate. The section on the three commands explains what that costs and why the plan is still worth reading.

## Three commands, three jobs

Three commands start with the word `EXPLAIN` or run beside it, and people mix them up. The mix-up costs a debugging session. `EXPLAIN` returns bytecode you have to decode, and `ANALYZE` writes to the database when you only wanted to read a plan.

| command | what it returns | the question it answers |
| --- | --- | --- |
| `EXPLAIN` | one row per virtual machine instruction | how the engine executes the plan |
| `EXPLAIN QUERY PLAN` | one row per loop | which table or index the engine visits, and how |
| `ANALYZE` | no rows, and a write to `sqlite_stat1` | how many rows the planner should expect |

`EXPLAIN` compiles the statement and returns the bytecode instead of running it. For `SELECT id FROM orders WHERE status = 'refunded'` you get eleven rows, with columns `addr`, `opcode`, `p1` through `p5`, and a comment. The opcodes carry names like `SeekGE`, `Next` and `ResultRow`. `SeekGE` jumps to the first key at or above the search value, `Next` steps to the following entry, and `ResultRow` hands a row back.

That is a real answer to a real question, and it is the wrong level for almost every question you have. Reading it costs you time and tells you nothing about which index won.

`EXPLAIN QUERY PLAN` returns the loops. Its rows have `id`, `parent`, `notused` and `detail`. The first three are bookkeeping: `id` numbers the step, `parent` points at a parent step, and `notused` is a legacy column you can ignore. `detail` holds the sentence you came for.

`ANALYZE` answers a different question. It walks the tables and writes what it finds into a table called `sqlite_stat1`. It returns no rows, because it is not answering a query. What it changes is the next plan, by giving the planner better counts.

The gap is `EXPLAIN ANALYZE`. PostgreSQL runs the query and reports the measured rows next to the estimate. SQLite has no such command. The statement `EXPLAIN ANALYZE SELECT id FROM orders WHERE status = 'refunded'` fails with a syntax error near `SELECT`, because SQLite reads `ANALYZE` as the statement you want explained and then meets `SELECT` where the statement should end.

That limit sets the standard of proof for this chapter. The plan is an intention, not a measurement. You can say which access path the engine chose. You cannot say how long it ran or how wrong the estimate was.

## A plan is a list of loops

Every plan is a small tree of loops, and each loop visits one table or one index. The `detail` column describes one loop. Two words carry the meaning.

`SCAN` visits every row of a table or index, in order. `SEARCH` jumps to the rows that satisfy a constraint, and it can only do that with an index. When a `detail` line says `SCAN orders`, the engine reads all 80 orders. When it says `SEARCH orders USING INDEX orders_customer_id_idx`, the engine seeks to the key and reads only the rows that match.

Between those two, the detail line often says which index and how much of the table it needed. `USING COVERING INDEX` means the index alone answered the query, and the table was never opened. Plain `USING INDEX` means the index found the rows and each one cost a lookup in the table. A line with no index at all means the table itself was walked.

A covering index is possible because of an index entry's shape. SQLite stores the indexed value and the rowid of the row it came from, so the index on `orders(status)` holds a `status` value plus the `rowid` of that order. `PRAGMA index_xinfo('orders_status_idx')` shows exactly that: one entry for `status`, then one for the rowid. Since `id` is the rowid alias (chapter 3 covers that), a query that asks for `id` alone is answered from the index with no table access.

## Reading the plan for the demo query

The curriculum demo is the query every other plan in this chapter is compared against:

```sql
EXPLAIN QUERY PLAN
SELECT id, status, customer_id
FROM orders
WHERE customer_id = 1
ORDER BY id;
```

Its plan is one line.

| id | parent | notused | detail |
| --- | --- | --- | --- |
| 4 | 0 | 61 | SEARCH orders USING INDEX orders_customer_id_idx (customer_id=?) |

Read the detail left to right, word by word.

`SEARCH` says the predicate gave the planner a key to seek. `orders` names the table. `USING INDEX orders_customer_id_idx` names the index from `sqlite_master`, the one on `customer_id` that chapter 1 listed. The parenthesised part is the constraint the seek uses: one value of `customer_id`, taken from the statement. One line, one loop, one index seek.

The line does not say `COVERING`, and that word is missing for a reason. The query selects `status`, and `status` is not in an index on `customer_id`, so SQLite must open the table for each of the five matches. The index finds the rows; the table supplies the column.

The `ORDER BY id` costs nothing extra, which is the part people find surprising. With equal `customer_id` values, the index entries are stored in rowid order, so the five matches already arrive sorted by `id`. The plan confirms it with an absence: there is no second line, and no `USE TEMP B-TREE FOR ORDER BY`. Sort by a column outside the index and that line appears:

```sql
EXPLAIN QUERY PLAN
SELECT id FROM orders WHERE customer_id = 1 ORDER BY ordered_at;
```

| id | parent | notused | detail |
| --- | --- | --- | --- |
| 4 | 0 | 61 | SEARCH orders USING INDEX orders_customer_id_idx (customer_id=?) |
| 14 | 0 | 0 | USE TEMP B-TREE FOR ORDER BY |

A temporary B tree is a sort the engine builds in memory. It is a second loop's worth of work, and the plan told you before you ran it.

The demo query returns five orders:

| id | status | customer_id |
| --- | --- | --- |
| 1001 | completed | 1 |
| 1002 | completed | 1 |
| 1005 | completed | 1 |
| 1006 | shipped | 1 |
| 1007 | refunded | 1 |

Five rows, found by one seek and five table lookups. The exercise uses a single equality on an indexed column, so its plan has the same shape for customer 3 as for customer 1. You can predict it before you write the query. The value changes. The loop does not.

## What a covering index saves

Ask for less and the plan changes:

```sql
EXPLAIN QUERY PLAN
SELECT id FROM orders WHERE status = 'refunded';
```

| id | parent | notused | detail |
| --- | --- | --- | --- |
| 2 | 0 | 55 | SEARCH orders USING COVERING INDEX orders_status_idx (status=?) |

Same seek, and one word more. The query asks for `id`, which is the rowid, and every entry in `orders_status_idx` already holds its rowid. The index can answer alone, so the 11 refunded orders come back without the table being opened at all.

Take the `COVERING` away by asking for a column the index does not carry. `SELECT status FROM orders WHERE customer_id = 1` returns `SEARCH orders USING INDEX orders_customer_id_idx`, because `status` lives in the table. `SELECT *` is worse in the same way for every index: it needs every column, so a covering plan is impossible.

That is the second reason to name your columns. The first is that the result then follows your question instead of the table's current definition. A short projection can turn a plan that reads the table into a plan that reads only an index. On a wide table with a large text column, the difference is the width of every row you avoid.

## A predicate that hides the index

Here is the mistake to expect. A learner wants a status match that ignores case, so they wrap the column in a function:

```sql
EXPLAIN QUERY PLAN
SELECT id FROM orders WHERE upper(status) = 'REFUNDED';
```

| id | parent | notused | detail |
| --- | --- | --- | --- |
| 2 | 0 | 214 | SCAN orders USING COVERING INDEX orders_status_idx |

The word changed. `SEARCH` became `SCAN`, because the constraint is no longer `status = something`. It is `upper(status) = something`, and `upper(status)` is a value the engine computes one row at a time and has never stored. An index on `status` is ordered by `status`, and that order says nothing about the order of `upper(status)`, so there is no key to seek. SQLite still uses the covering index, because walking 80 narrow entries beats walking 80 wide rows, and that detail is easy to mistake for success.

The result is the same 11 rows. The query is correct, it raises no error, and nothing on screen says the work changed. Only the count of entries visited differs: 80 for the wrapped version, 11 for the seek.

At 80 rows you cannot feel it. Multiply the table by a thousand and the same query reads a thousand times more entries to return the same rows.

Several predicates have this shape. `WHERE customer_id + 0 = 1` produces `SCAN orders USING COVERING INDEX orders_customer_id_idx`, and so does `WHERE CAST(customer_id AS TEXT) = '1'`. Each one computes a new value, and the index cannot help with a value that does not exist until the row is read. Chapter 4's date arithmetic has the same shape: `WHERE date(ordered_at) = '2026-01-04'` returns the right row, and no index on `ordered_at` could serve it.

The correction compares the bare column:

```sql
EXPLAIN QUERY PLAN
SELECT id FROM orders WHERE status = 'refunded';
```

Now it is a `SEARCH`, with the index and the value in the detail. If you truly need case-insensitive matching, fix the stored value rather than the predicate. Chapter 5 covers folded columns and `COLLATE NOCASE`, and either one keeps the comparison on the bare column where an index can reach it.

Try this: run `EXPLAIN QUERY PLAN` on the wrapped predicate, then on the bare one. The first detail line reads `SCAN orders USING COVERING INDEX orders_status_idx` and walks 80 entries. The second reads `SEARCH orders USING COVERING INDEX orders_status_idx (status=?)` and reaches 11. Both return the same 11 rows, which is why the result table cannot warn you.

## One line per loop in a join

A join produces one `detail` line per loop. This query joins orders to their lines and filters on `customer_id`:

```sql
EXPLAIN QUERY PLAN
SELECT o.id
FROM orders o
JOIN order_items oi ON oi.order_id = o.id
WHERE o.customer_id = 1;
```

| id | parent | notused | detail |
| --- | --- | --- | --- |
| 3 | 0 | 53 | SEARCH o USING COVERING INDEX orders_customer_id_idx (customer_id=?) |
| 7 | 0 | 54 | SEARCH oi USING COVERING INDEX order_items_order_id_idx (order_id=?) |

Read the lines top to bottom as the loop order. The outer loop finds the 5 orders of customer 1 through the index on `customer_id`. The inner loop takes each of those order ids and finds its lines through the index on `order_id`. That is a nested loop: the inner line runs once per outer row.

Both lines say `COVERING`, so neither loop opens a table. The outer loop needs `o.id`, which is a rowid, and the inner loop needs `oi.order_id`, which is the indexed column. The indexes hold everything the query projects, and the query returns in one pass per order.

Loop order is the planner's decision, not yours. Swap the two tables in the `FROM` clause and the plan comes back identical, line for line, because the planner chooses the order from the constraints it has. Read the line order, not the clause order.

## ANALYZE writes statistics

`ANALYZE` is the one command in this chapter that changes the database. It measures the tables and writes what it finds into `sqlite_stat1`, then returns nothing. Run `ANALYZE` on its own before the next query: until it has run, `sqlite_stat1` does not exist, and reading it fails with `no such table: sqlite_stat1`. Once it has run, query the table to see what it recorded:

```sql
SELECT idx, stat FROM sqlite_stat1 WHERE tbl = 'orders' ORDER BY idx;
```

| idx | stat |
| --- | --- |
| orders_customer_id_idx | 80 4 |
| orders_status_idx | 80 16 |

Read a `stat` string left to right. The first number is the rows in the table. The numbers after it are the average rows per distinct value of the index key. So `orders` holds 80 rows, and a `customer_id` value covers about 4 of them; a `status` value covers about 16.

Both of those are averages, and the data is not average. Customer 1 has 5 orders and customer 7 has 4, which is close enough. Status is not: `completed` appears on 37 orders, `shipped`, `cancelled` and `refunded` on 11 each, and `pending` on 10. The planner sees 16 and never learns that 37 is nearly half the table. There is no histogram in `sqlite_stat1`, only the average.

That limit explains when `ANALYZE` helps and when it changes nothing. With one index on a column, the planner has no choice to make, so statistics rarely move the plan.

The decision appears when two indexes could serve one query: `WHERE status = 'refunded' AND customer_id = 7` can use either index, and this fixture's plan picks `orders_customer_id_idx`. The planner compares the candidates using those averages, and an average of 16 for a status value is a rough guide when the query asks for the rarest one. Running `ANALYZE` and reading the plan again shows the same index and the same line.

Run `ANALYZE` after a bulk load, when the counts have just changed, and leave it alone otherwise. It writes to the database, so it needs a writable connection, and it is a measurement of the data rather than a fix for a query.

## What to remember

What I would do: run `EXPLAIN QUERY PLAN` before any tuning, and read the `detail` column line by line. If a line says `SCAN` where you expected a `SEARCH`, fix the predicate before you add an index. Compare the bare column, name the columns you select, and keep the sort on the rowid so no temporary B tree appears. Run `ANALYZE` once after a bulk load, then read the plan again.

- `EXPLAIN` returns bytecode, `EXPLAIN QUERY PLAN` returns loops, and `ANALYZE` writes statistics. Read the loops.
- SQLite has no `EXPLAIN ANALYZE`. A plan states what the engine will do, not what it measured.
- `SCAN` visits every row of a table or index. `SEARCH` seeks to a key, and it needs an index to do so.
- `USING COVERING INDEX` means the index answered alone. Plain `USING INDEX` means each match also cost a table lookup.
- A function or arithmetic on a column produces a new value per row, so the plan scans. Compare the bare column instead.
- `sqlite_stat1` records an average rows-per-value, not a histogram. `ANALYZE` matters when two indexes could serve the query.

## Check yourself

**1. The demo query's plan says `USING INDEX` and the refunded-orders plan says `USING COVERING INDEX`. What decides which one you get?**

<details>
<summary>Answer</summary>

The columns the query needs. An index holds the indexed column plus the rowid. `SELECT id FROM orders WHERE status = 'refunded'` needs only the rowid, so the index answers alone. The demo selects `status` while the index is on `customer_id`, so each matching row costs a table lookup to fetch `status`.

</details>

**2. `WHERE upper(status) = 'REFUNDED'` returns the same 11 rows as `WHERE status = 'refunded'`, so why is the first query worse?**

<details>
<summary>Answer</summary>

Its plan says `SCAN` where the other says `SEARCH`. `upper(status)` is computed per row and never stored, so the index on `status` offers no key to seek, and the engine visits all 80 entries to return 11 rows. The result is correct and the work is larger, which is why the mistake survives until the table grows.

</details>

**3. Why does `ORDER BY id` need no sort step, while `ORDER BY ordered_at` adds one?**

<details>
<summary>Answer</summary>

Because `id` is the rowid. Entries with the same `customer_id` sit in rowid order inside the index, so the matching rows arrive already sorted by `id`. `ordered_at` is not in the index, so the rows arrive in the wrong order and the engine builds a temporary B tree to sort them.

</details>

**4. `sqlite_stat1` says a status value covers about 16 orders, yet `completed` covers 37. Does that make `ANALYZE` useless?**

<details>
<summary>Answer</summary>

No, it makes it rough. The table stores an average per index key and no histogram, so the planner cannot see the skew. With one index the average changes nothing, because there is no choice to make. With two candidate indexes the planner compares averages, and it can back the wrong one when the query asks for the rarest status. Reading the plan is the check for that.

</details>
