# Joins without row multiplication

A report on the shop says Ada Whitfield placed 10 orders. She placed 5, and the report gives no reason to doubt it. The query behind it is short, the tables are intact, and nothing was inserted twice. The join returned one row for every product line in every order, and the count counted those rows.

This chapter names that change and gives you two ways to handle it. You will watch one order turn into four rows, learn what `COUNT(*)` and `COUNT(DISTINCT key)` each measure, and see how aggregating before you join keeps a fan-out from happening at all.

## Two tables, one order

Start with a single order and look at what a join produces.

```sql
SELECT o.id AS order_id, o.status,
       oi.id AS line_id, oi.product_id, oi.quantity, oi.unit_price
FROM orders o
JOIN order_items oi ON oi.order_id = o.id
WHERE o.id = 1006
ORDER BY oi.id;
```

| order_id | status | line_id | product_id | quantity | unit_price |
| --- | --- | --- | --- | --- | --- |
| 1006 | shipped | 6 | 5 | 1 | 139.00 |
| 1006 | shipped | 7 | 12 | 2 | 210.00 |
| 1006 | shipped | 8 | 19 | 3 | 15.50 |
| 1006 | shipped | 9 | 7 | 1 | 89.50 |

`orders` holds one row for order 1006. The result holds four. The `ON` clause states the test each pair of rows must pass: the line's `order_id` must equal the order's `id`.

For the one order row, the engine finds every line that passes, and emits one combined row for each. The order's own columns, `id` and `status`, repeat on all four.

Four lines is the answer to "what is in order 1006", and four rows is the only shape that carries four products, four quantities and four prices. Nothing was duplicated by accident. One row per line is what this join is for. The cost shows up later, when a count over rows like these reports 10 for a customer who placed 5.

## Grain is what one row of the result means

Before the join, one row of `orders` means one checkout and one row of `order_items` means one line. After the join, one row means one line, and the order has become a repeated attribute of that line.

| table | rows | one row means |
| --- | --- | --- |
| `customers` | 30 | one person |
| `orders` | 80 | one checkout |
| `order_items` | 160 | one product line inside a checkout |
| joined `orders` + `order_items` | 160 | one product line inside a checkout |

That is the grain: what one row of a result stands for. When a parent row turns into one row per child, the change is a fan-out. The join did not add rows out of nowhere. It paired each order with its lines, and that pairing is the fan-out.

The sizes make the multiplication visible. The 80 orders hold 160 lines, so joining them returns 160 rows. A report that reads an order-level column off those rows repeats it about twice on average.

Write the grain into the query before you write the aggregate. `-- one row per order` and `-- one row per line` are different promises, and only one of them describes the statement you are about to run. A total that looks wrong is usually a grain that was never stated.

## COUNT(*) counts the rows the join made

`COUNT(*)` counts result rows. After a fan-out, result rows are lines.

```sql
SELECT count(*) AS lines,
       count(DISTINCT o.id) AS orders
FROM orders o
JOIN order_items oi ON oi.order_id = o.id;
```

| lines | orders |
| --- | --- |
| 160 | 79 |

The first column is the fan-out: 160 lines, one row each. The second column recovers the order count and lands on 79 rather than 80. Order 1003 is cancelled and has no lines, and an inner join drops a parent with no match.

Chapter 1 called the child side optional; this is where that shows up. A left join would keep order 1003 with `NULL` line columns, and the distinct count would then report 80.

`COUNT(DISTINCT o.id)` builds the set of different values of `o.id` and counts it. Repeated values count once, and `NULL` counts not at all.

Try this: change `count(DISTINCT o.id)` to `count(o.id)` and run the query again. The `orders` column returns 160, because every joined row carries a non-null order id. `DISTINCT` is the whole difference between a line count and an order count.

## COUNT(DISTINCT key) counts each parent once

Here is the report from the opening, with both counts side by side.

```sql
SELECT c.name,
       count(*) AS counted,
       count(DISTINCT o.id) AS orders
FROM customers c
JOIN orders o ON o.customer_id = c.id
JOIN order_items oi ON oi.order_id = o.id
GROUP BY c.id, c.name
ORDER BY counted DESC, c.name
LIMIT 5;
```

`GROUP BY` collects rows that share a value and gives you one row per group. The group here is a customer.

| name | counted | orders |
| --- | --- | --- |
| Ada Whitfield | 10 | 5 |
| Chidi Okafor | 9 | 4 |
| Emi Tanaka | 9 | 4 |
| Hiro Ivanov | 9 | 4 |
| Kira Whitfield | 9 | 4 |

Ada has 5 orders and 10 lines. Both numbers are true. `counted` answers "how many lines did she buy", and `orders` answers "how many checkouts did she make". The report labelled the first one "orders", and that label is the whole bug.

Write `count(*) AS orders` and the query hands back 10 for Ada and 9 for each of the next four customers. Every row is inflated, and nothing in the output marks it.

Across all 23 customers who have ordered, `counted` adds up to 160 and `orders` adds up to 79. The second total is still short of 80, for the same reason: order 1003 has no lines, so no row carries its id into the join.

Two cautions keep `COUNT(DISTINCT)` honest. It repairs a count after the rows have already fanned out, which is later than you wanted. And it costs work, because the database tracks a set of values instead of incrementing a counter. When the question is only "how many orders", ask `orders` and skip the join.

The same mistake with `SUM` is harder to catch. Summing a parent-side column over child rows repeats the value once per child. The Granite Cookware Set costs 210.00, and `sum(p.price)` over its nine lines reports 1,890.00. That result is formatted like money, so nothing in the output warns you.

## The other direction does not fan out

Not every join multiplies. Put the customer beside each order and the row count stays where it was.

```sql
SELECT o.id AS order_id, c.name AS customer
FROM orders o
JOIN customers c ON c.id = o.customer_id
WHERE o.status = 'completed'
ORDER BY o.id
LIMIT 5;
```

| order_id | customer |
| --- | --- |
| 1001 | Ada Whitfield |
| 1002 | Ada Whitfield |
| 1004 | Chidi Okafor |
| 1005 | Ada Whitfield |
| 1008 | Bruno Sala |

Many orders point at one customer, so each order row matches at most one customer row. The `name` column is added and no row is added. That direction is many-to-one, and it is the safe direction for a decoration join: you are travelling from the child up to its parent.

The rule follows from the keys. A foreign key on the child names one parent, so travelling up finds at most one row. A parent can have many children, so travelling down finds many. Parent to child multiplies, child to parent does not.

## Aggregate before you join

The other repair is to shrink the child table to parent grain first, then join the small result.

```sql
SELECT c.name, o.orders
FROM customers c
JOIN (
  SELECT customer_id, count(*) AS orders
  FROM orders
  GROUP BY customer_id
) o ON o.customer_id = c.id
ORDER BY o.orders DESC, c.name
LIMIT 5;
```

| name | orders |
| --- | --- |
| Ada Whitfield | 5 |
| Chidi Okafor | 4 |
| Emi Tanaka | 4 |
| Farid Lindqvist | 4 |
| Gina Rahman | 4 |

The subquery returns 23 rows, one per customer who has ordered, and the join adds a name to each. The outer query never sees a line, so no row multiplies. Every column in the final result appears exactly once per customer, which makes `SUM` and `AVG` safe on any of them.

The fan-out is still the right tool when you need line detail. If the question is per order, group the joined rows back to order grain.

```sql
-- one row per order, with a count of its lines
SELECT o.id,
       COUNT(oi.id) AS line_items
FROM orders o
JOIN order_items oi ON oi.order_id = o.id
GROUP BY o.id;
```

That returns 79 rows, one per order that has lines. `COUNT(oi.id)` and `COUNT(*)` agree here, because the join is inner and `oi.id` is never null. Naming the column is still the safer habit, since an outer join would make the difference real.

Choose by what the outer query needs. If it needs one row per parent and nothing from the child but its total, aggregate first and join afterwards. If it needs child columns, join and then group back to parent grain. Do not join two child tables to one parent and then aggregate: the children multiply each other, and the totals fail in a way that looks like a data problem.

## What the exercise asks

The exercise asks for one row per order with three values: the order id, the customer name, and the number of line items, most line items first. The customer name lives one join up, and the line count lives one join down, so the query walks both directions and then groups back to order grain.

Two checks will tell you whether the shape is right. The result holds 79 rows, not 80, because order 1003 has no lines and the inner join drops it. The largest orders hold 4 lines, and many hold 3, so read the count column for the answer and do not read a tie as a ranking.

## What to remember

**What I would do:** write the grain as a comment above the query, then compare the joined count with the parent table counted on its own. When the report needs only a parent total, aggregate the child table first and join the small result. When it needs child columns, join and group back to parent grain. Use `COUNT(DISTINCT key)` to repair a report you cannot restructure.

- A one-to-many join returns one row per child, and the parent's columns repeat on each of those rows.
- Grain is what one row of a result means. Name it before you write the aggregate.
- After a fan-out, `COUNT(*)` counts lines. `COUNT(DISTINCT key)` counts each parent once.
- A parent-to-child join multiplies rows; a child-to-parent join does not.
- Aggregating the child table first, then joining, keeps every outer row at parent grain and makes `SUM` safe.
- An inner join also drops parents with no children, so a count after a join can be lower than the table's own count.

## Check yourself

**1. Why does joining `orders` to `order_items` return 160 rows when `orders` holds 80?**

<details>
<summary>Answer</summary>

The relationship is one-to-many, so each order pairs with every line that names it. The result keeps one row per line, and the 160 line rows replace the 80 order rows. The order's columns repeat on the line rows.

</details>

**2. The top-level count after that join is 79 orders, not 80. Where did the missing order go?**

<details>
<summary>Answer</summary>

Order 1003 is cancelled and has no lines. An inner join drops a parent with no match, so no row carries its id and no distinct count can include it. A left join from `orders` would keep it and report 80.

</details>

**3. A customer has 5 orders, 10 lines, and the query reports 10 as the order count. Which expression produced the 10, and what should replace it?**

<details>
<summary>Answer</summary>

`COUNT(*)` over the joined rows counted lines, because the join produced one row per line. `COUNT(DISTINCT o.id)` counts the customer's orders once each and returns 5.

</details>

**4. Why can you not write `avg(count(*))` to get the average number of lines per order?**

<details>
<summary>Answer</summary>

One aggregate cannot contain another, because both run at the same stage of the query. Group the lines by order in a subquery first, then average that column in the outer query. The inner result sits at order grain, which is what the average needs.

</details>
