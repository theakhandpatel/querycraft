# Conditional aggregation without `FILTER` assumptions

Eighty orders sit in the table, and the weekly report needs five counts from them. PostgreSQL returns all five in one statement. On an embedded copy of SQLite older than 3.30, the same statement returns a syntax error instead of the report.

```sql
SELECT COUNT(*) FILTER (WHERE status = 'completed') AS completed,
       COUNT(*) FILTER (WHERE status = 'cancelled') AS cancelled,
       COUNT(*) FILTER (WHERE status = 'refunded')  AS refunded,
       COUNT(*) FILTER (WHERE status = 'shipped')   AS shipped,
       COUNT(*) FILTER (WHERE status = 'pending')   AS pending
FROM orders;
```

| completed | cancelled | refunded | shipped | pending |
| --- | --- | --- | --- | --- |
| 37 | 11 | 11 | 11 | 10 |

That statement runs here as written. The engine in this course is SQLite 3.53.4, and `FILTER` has been in SQLite since 3.30, in 2019.

So the port question is not what replaces `FILTER`. It is what happens on a copy of SQLite you did not install. Engines ship inside applications, and an old one stops at the parser before it reads a row.

This chapter gives you the spelling that every build runs, explains which clause in it matters most, and shows the report written both ways.

## One pass, five numbers

The query reads `orders` once and returns one row. `COUNT(*)` counts rows, and `FILTER (WHERE ...)` decides which rows that count sees. Five aggregates with their own filters give five answers from one scan. Five separate statements would read the table five times, and a row can land between two reads, so the numbers can disagree.

## The floor under `FILTER`

`FILTER` is standard SQL, PostgreSQL has had it for years, and SQLite added it in 3.30, released in 2019. A build below that floor fails on the clause's opening parenthesis with a syntax error.

Both engines in this repository clear the floor: the browser runs `@sqlite.org/sqlite-wasm` 3.53.4 and the Go gateway runs 3.50.3. If you know the engine you ship against, keep `FILTER`.

The floor is not always yours to know. An embedded copy of SQLite travels inside desktop applications, phones and CI images that you did not build. The spelling below has no floor above the oldest SQLite ever shipped, so it runs wherever a `CASE` runs. The rest of this course uses it.

## `CASE` turns each row into a 1 or a 0

The replacement is a comparison inside `CASE`, wrapped in `SUM`. Start with the per-row value:

```sql
SELECT id, status,
       CASE WHEN status = 'completed' THEN 1 ELSE 0 END AS completed_flag
FROM orders
ORDER BY id
LIMIT 6;
```

| id | status | completed_flag |
| --- | --- | --- |
| 1001 | completed | 1 |
| 1002 | completed | 1 |
| 1003 | cancelled | 0 |
| 1004 | completed | 1 |
| 1005 | completed | 1 |
| 1006 | shipped | 0 |

The `CASE` runs once per row. A true comparison returns 1, otherwise the `ELSE` value, 0. Those six rows give four 1s. Replace the row with `SUM` and you have the count:

```sql
SELECT SUM(CASE WHEN status = 'completed' THEN 1 ELSE 0 END) AS completed,
       SUM(CASE WHEN status = 'cancelled' THEN 1 ELSE 0 END) AS cancelled,
       SUM(CASE WHEN status = 'refunded'  THEN 1 ELSE 0 END) AS refunded,
       SUM(CASE WHEN status = 'shipped'   THEN 1 ELSE 0 END) AS shipped,
       SUM(CASE WHEN status = 'pending'   THEN 1 ELSE 0 END) AS pending
FROM orders;
```

| completed | cancelled | refunded | shipped | pending |
| --- | --- | --- | --- | --- |
| 37 | 11 | 11 | 11 | 10 |

The five numbers match the `FILTER` report, and `EXPLAIN QUERY PLAN` gives both queries the same step, `SCAN orders USING COVERING INDEX orders_status_idx`. The choice between them is about which engines run them and how they read, not about speed.

## Why `ELSE 0` matters

Leave the `ELSE` out and the column silently changes meaning:

```sql
SELECT SUM(CASE WHEN status = 'refunded' THEN 1 END) AS refunded,
       SUM(CASE WHEN status = 'returned' THEN 1 END) AS returned
FROM orders;
```

| refunded | returned |
| --- | --- |
| 11 | NULL |

The `refunded` column is right, because `refunded` exists in the table. No order has the status `returned`, so every row falls through to a missing `ELSE`, returns NULL, and `SUM` over eighty NULLs is NULL. An empty sum is not zero unless you say it is.

The answer depends on the aggregate:

```sql
SELECT SUM(CASE WHEN status = 'refunded' THEN 1 ELSE 0 END)   AS sum_with_else,
       COUNT(CASE WHEN status = 'refunded' THEN 1 ELSE 0 END) AS count_with_else,
       COUNT(CASE WHEN status = 'refunded' THEN 1 END)        AS count_no_else
FROM orders;
```

| sum_with_else | count_with_else | count_no_else |
| --- | --- | --- |
| 11 | 80 | 11 |

`SUM` needs `ELSE 0`, because adding nothing must add zero. `COUNT` needs no `ELSE`, because it counts every value that is not NULL, and a `0` is a value. Add `ELSE 0` and every row counts, so 11 refunds become 80. `AVG` follows `COUNT`, since a zero pulls the average down.

Try this: rewrite the first aggregate in that query as `COUNT(CASE WHEN status = 'refunded' THEN 1 ELSE 0 END)` and run it. The column reads 80 instead of 11. The `ELSE 0` that a `SUM` needs turns a `COUNT` into the row count of `orders`.

## Reading the same report in both dialects

| PostgreSQL | SQLite |
| --- | --- |
| `COUNT(*) FILTER (WHERE p)` | `SUM(CASE WHEN p THEN 1 ELSE 0 END)` |
| `COUNT(x) FILTER (WHERE p)` | `COUNT(CASE WHEN p THEN x END)` |
| `SUM(x) FILTER (WHERE p)` | `SUM(CASE WHEN p THEN x ELSE 0 END)` |
| `AVG(x) FILTER (WHERE p)` | `AVG(CASE WHEN p THEN x END)` |

Read the third row first. The condition moves inside the aggregate, and the `ELSE` value follows it: a sum adds a zero, a count and an average skip a NULL.

## `DISTINCT ON` does not exist

PostgreSQL's `DISTINCT ON (customer_id)` has no SQLite spelling. The parser stops at `ON`, so this is not a version floor but a missing feature. The question it answers is one row per customer, with the rest of the row kept.

Build it in two steps. First, number the orders of one customer, newest first:

```sql
SELECT id, date(ordered_at) AS ordered_on,
       ROW_NUMBER() OVER (ORDER BY ordered_at DESC, id DESC) AS rn
FROM orders
WHERE customer_id = 1;
```

| id | ordered_on | rn |
| --- | --- | --- |
| 1005 | 2026-02-11 | 1 |
| 1002 | 2026-01-19 | 2 |
| 1007 | 2026-01-11 | 3 |
| 1006 | 2026-01-09 | 4 |
| 1001 | 2026-01-04 | 5 |

`ROW_NUMBER()` writes 1, 2, 3 down the result, and `OVER (ORDER BY ...)` says what the numbering follows.

Adding `PARTITION BY customer_id` restarts the numbering at 1 for every customer. Customer 2's newest order also gets `rn = 1`. Keeping those rows needs a filter, and the filter must sit in an outer query or a CTE, because `WHERE` runs before the window exists.

The function choice is part of the answer. `RANK()` gives two tied rows the same number, so a tie could survive as two rows. `ROW_NUMBER()` numbers 1, 2, 3, so one row survives per customer, and the second sort key decides which.

A window computes alongside the rows, which is why `id` and `ordered_on` survive. A `GROUP BY customer_id` would have to aggregate them away.

The exercise asks for that report for customers 1 to 5, with `customer_id`, the order id, and the date. Customer 4 has never ordered, so think about the row count before you run it.

## What to remember

**What I would do:** put the `CASE` sum in the queries you share, and `ELSE 0` in every `SUM`. Reach for `FILTER` only when you know the build that runs it, and treat an unknown engine as an old one. Then test the report against a status no row holds, because that row decides whether a column reads 0 or NULL.

- `COUNT(*) FILTER (WHERE ...)` is standard SQL, and it works on SQLite 3.30 and later. Older builds stop at the parser.
- `SUM(CASE WHEN condition THEN 1 ELSE 0 END)` is the same count with no version floor.
- `ELSE 0` belongs in a `SUM`, because a sum over NULLs is NULL. It breaks a `COUNT` and an `AVG`, which skip NULLs.
- Both spellings read the table once, and this engine gives them the same plan.
- `DISTINCT ON` never parses here. Use a partitioned `ROW_NUMBER()` when you need the whole row.

## Check yourself

**1. If `FILTER` runs on the engine in front of you, why write the `CASE` sum?**

<details>
<summary>Answer</summary>

Because the engine in front of you is not the only one the query meets. Whoever ships the application chooses the embedded copy of SQLite, and a build below 3.30 stops at the parser. The `CASE` spelling has no such floor.

</details>

**2. A report column reads NULL where you expected 0. What is the likely cause?**

<details>
<summary>Answer</summary>

A `SUM(CASE WHEN ... THEN 1 END)` with no `ELSE`. The case returns NULL for every row that fails, and a sum over NULL values is NULL, not 0. Add `ELSE 0`.

</details>

**3. Why does `COUNT(CASE WHEN status = 'refunded' THEN 1 ELSE 0 END)` return 80 instead of 11?**

<details>
<summary>Answer</summary>

`COUNT` skips NULL values and counts everything else, and `0` is not NULL. The `ELSE 0` gives every non-refunded row a value to count, so the count becomes the row count of `orders`. Drop the `ELSE`, or use `SUM`.

</details>

**4. What does `PARTITION BY customer_id` do in the `DISTINCT ON` replacement?**

<details>
<summary>Answer</summary>

It splits the rows into one group per customer, and `ROW_NUMBER()` restarts at 1 in each group. The `ORDER BY` inside `OVER` decides which order gets the 1, so `rn = 1` keeps the newest order per customer.

</details>
