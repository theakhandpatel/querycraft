# When SQLite is the right choice, and what it cannot do

Six chapters of this course ran with no database server. Every query you wrote read the same four commerce tables from a database the page built in memory, with nothing to install and no password.

That is not a teaching trick. Applications ship SQLite this way all the time, and the choice holds while one process writes. Hand the same file to a team that writes at once and every write queues for the file's single lock, until a writer waits past `busy_timeout` and gets `SQLITE_BUSY`. The bill arrives after launch, not during a tutorial.

This chapter draws the line. It names the workloads a file serves well, the five things the engine genuinely lacks, and ends with a query that reports the whole store.

## The engine is a library, and the file is the database

SQLite is a C library, not a server. A query is a function call into that library, and the library reads and writes bytes in a local file. Nothing listens on a port. There is no process to start, no connection pool to size, and no network hop between your code and your rows. The copy this course uses reports version 3.53.4, and it reads the same file format every other copy writes.

Every one of those absences is the point. It is also the bill. With no server between the code and the bytes, nothing grants one program access to one table. Nothing arbitrates a second process that wants to write.

The catalog is ordinary storage too. Chapter 1 read table and index names out of `sqlite_master`, a table you can select from like any other. A database that describes itself in itself is easy to move: copy the file, and the schema, the rows, and the indexes arrive together.

Almost everything good and bad about SQLite follows from that placement. The engine runs inside your process, beside your data, with no boundary between them.

## Workloads where a file is the right store

Reach for SQLite when the database and the program that uses it share one owner and one lifetime. Six shapes come up often.

- A desktop or mobile app. The database travels inside the install, so the user has no server to configure and no version mismatch to debug.
- A browser tab. This course is that case: the engine is compiled to WebAssembly, the schema and seed are applied in memory, and the database disappears when the tab closes.
- A test fixture. Each test opens a fresh file, seeds it, and deletes it, so one test cannot pollute the next and the suite needs no shared server.
- An analysis file. You save the result of a slow export, send the file to a colleague, and they run the same queries without an account.
- An offline cache. A phone keeps the last 500 products in a file, answers reads locally, and syncs when the network returns.
- A build cache. A compiler writes its dependency state to one file, and the next build reads it back.

Those shapes share three properties. One process writes at a time, reads vastly outnumber writes, and the data lives as long as the app does. When all three hold, a file is the cheapest correct answer, because deployment is a copy.

The two engines differ on the things a shared server exists to provide.

| Question | SQLite | PostgreSQL |
| --- | --- | --- |
| Who writes? | one process, or one at a time | many clients |
| Where does it run? | in the process | in a server |
| What is access control? | the file | roles and grants |
| What is the schema? | one namespace per file | schemas and `search_path` |
| What is strong typing? | opt-in with `STRICT` | the default |

The next three sections take those differences in turn.

## No roles and no schemas

A role is a named account inside a server. A grant is a privilege attached to that account: read this table, skip that column. PostgreSQL checks both on every statement. SQLite has neither, and one statement proves it.

```sql
-- Fails: SQLite has no GRANT statement.
GRANT SELECT ON customers TO analyst;
```

SQLite answers `near "GRANT": syntax error`. Access control is the file's, so the operating system decides which user may open it. If a process can open the file for writing, it can write.

One guard exists inside a program. `PRAGMA query_only = 1` makes a connection refuse writes, and the attempt stops with `attempt to write a readonly database`, code `SQLITE_READONLY`. That protects a reporting path from its own bugs.

The guard is a setting on one connection, so any process that opens the file can simply leave it off.

Schemas are the second gap. A schema is a namespace inside one server, so `dataset.customers` and `public.customers` can hold different tables under one name. A SQLite file has one namespace. `ATTACH` adds a second file to the connection, which is a second database rather than a namespace inside this one; afterwards `customers` names the main file's table and `other.customers` names the attached file's.

This course's dataset shows the difference. The PostgreSQL build puts the four tables in a `dataset` schema. The SQLite mirror has nowhere to put one, so its lessons address every table unqualified.

## One writer at a time

A write takes a lock on the file. Under the default rollback journal, a writer blocks readers while it commits. Turn on WAL (the write-ahead log), as most applications do, and readers keep working from the last committed state while one writer commits. In both modes the write lock is single, so a second writer waits.

The wait is capped by `busy_timeout`, a per-connection setting in milliseconds. When it expires the second writer gets `SQLITE_BUSY`, and the usual cause is two processes writing the same file in the same moment.

PostgreSQL runs many writers against one table because it locks rows and pages, not the whole file. That is part of what the extra process buys. A file suits an app with one writing process. A file that four services write to will spend its time waiting and failing.

## A declared type is a hint, not a rule

Chapter 2 measured this on `products`. One declared type, `NUMERIC`, produced ten integer values and ten real values in the same column. A declared type in SQLite picks an affinity, which decides how a value is converted on the way in. It does not decide what the column may hold.

You can break that more plainly.

```sql
CREATE TABLE demo (price INT);
INSERT INTO demo VALUES ('not a number'), (50);
SELECT typeof(price) AS stored, price FROM demo;
```

| stored | price |
| --- | --- |
| text | not a number |
| integer | 50 |

Nothing failed. The first value went in as text even though the column says `INT`, and only `typeof` shows it. The damage appears at the next filter, because SQLite orders values by storage class: every number sorts below every piece of text.

```sql
SELECT count(*) AS over_100 FROM demo WHERE price > 100;
```

That returns 1. The only row above 100 is the text row, and it qualifies because text outranks any number, not because it is large. A sum, a comparison, or a join key can go wrong the same way, and nothing warns you at the write.

Try this: delete the text row with `DELETE FROM demo WHERE typeof(price) = 'text'` and run the `price > 100` count again. Nothing qualifies now, because the text row was the only row that outranked the numbers.

A `STRICT` table closes the gap. Since version 3.37 you can declare it per table, and the allowed types are a short list: `INT`, `INTEGER`, `REAL`, `TEXT`, `BLOB`, `ANY`.

```sql
CREATE TABLE demo_strict (price INTEGER) STRICT;
INSERT INTO demo_strict VALUES ('not a number');
```

The second statement fails with the error code `SQLITE_CONSTRAINT_DATATYPE`, and the message names the column: cannot store TEXT value in INTEGER column demo_strict.price. A value that fits is still converted, so an integer inserted into a `REAL` column arrives as a real.

The commerce mirror is not `STRICT`. `SELECT name, strict FROM pragma_table_list WHERE schema = 'main'` reports 0 for every table it lists, including `sqlite_schema`. It carries the PostgreSQL declared types so both dialects read the same seed, and that leaves affinity in charge of what each column holds. The production course takes `STRICT` tables apart in its own chapter.

Altering a table has a matching limit. SQLite supports `RENAME TO`, `RENAME COLUMN`, `ADD COLUMN`, and, since 3.35, `DROP COLUMN`. Changing a column's type or adding a constraint needs a rebuild: create the new table, copy the rows, drop the old one, rename the new one. `ALTER TABLE products ALTER COLUMN price TYPE TEXT` is not a statement SQLite understands, and it fails at the word `TYPE`. The production course walks through the rebuild and `PRAGMA user_version`.

One tool is missing as well. SQLite has no `EXPLAIN ANALYZE`, so it can show you a plan but not measure the run. Chapter 6 read plans without one.

## Stacking one result under another

`UNION ALL` puts the rows of one result below the rows of another. Both branches must return the same number of columns, in the same order, because the output has one column list and the first branch names it.

Take the query the exercise asks for, one branch at a time. The first branch returns a single row: `'customers'` as `relation`, and `COUNT(*)` as `table_rows`, which is 30. The literal names the table, the count sizes it, and the row explains itself.

The second branch, `SELECT 'products', COUNT(*) FROM products`, returns `('products', 20)`. Two columns again, so the append works. That branch needs no aliases, because names come from the first branch. The exercise adds the other two tables the same way.

```sql
SELECT 'customers' AS relation, COUNT(*) AS table_rows FROM customers
UNION ALL SELECT 'products', COUNT(*) FROM products
ORDER BY table_rows DESC;
```

| relation | table_rows |
| --- | --- |
| products | 20 |
| customers | 30 |

The `ORDER BY` sorts the whole union, not one branch, and it can use the alias because the alias belongs to the first branch's column list. The mechanism is a copy and nothing else. Each branch produces rows, `UNION ALL` stacks them, and the sort runs last.

`UNION` in place of `UNION ALL` would also remove duplicate rows. Every row here is already distinct, so the answer would look the same and cost a sort. On two inputs whose rows share both a label and a count, `UNION` would quietly drop one.

The mistake that catches people is one branch written in the wrong order. Keep the first branch, then label first and count second.

```sql
-- Wrong: the second branch projects count, label.
SELECT 'customers' AS relation, COUNT(*) AS table_rows FROM customers
UNION ALL SELECT COUNT(*), 'products' FROM products
ORDER BY table_rows DESC;
```

| relation | table_rows |
| --- | --- |
| 20 | products |
| customers | 30 |

SQLite accepts this and returns four rows. A union does not force one column to hold one kind of value, so the second branch puts a number in `relation` and text in `table_rows`. The sort then lifts that row to the top, because text outranks every integer.

The report that promised largest first opens with a row that names no table, and the table it describes sits at the bottom.

The fix is one shape across every branch: literal first, count second, in all four. That is what the exercise checks, with the columns named `relation` and `table_rows` and the largest table first.

## The whole store in one row

Four counts in one row is the shortest summary of a database that is a file.

```sql
SELECT (SELECT COUNT(*) FROM customers)   AS customers,
       (SELECT COUNT(*) FROM products)    AS products,
       (SELECT COUNT(*) FROM orders)      AS orders,
       (SELECT COUNT(*) FROM order_items) AS order_items;
```

| customers | products | orders | order_items |
| --- | --- | --- | --- |
| 30 | 20 | 80 | 160 |

Each bracket is a scalar subquery: a subquery in the column list, which must return exactly one value. The outer query has no `FROM` clause, so SQLite evaluates it once and produces one row. Each subquery runs against its own table and answers with a number.

Move the file and you have moved the database. `VACUUM INTO` writes a consistent copy to a new file while the database is open, and the backup API does the same from inside a running program. Ship a read-only copy when you want a sandbox nobody can break.

## What to remember

What I would do: keep the file for the shapes with one writer, such as the desktop app, the test fixture, and the export you hand to a colleague. The moment a second process writes, or a report needs a grant instead of a copy of the file, move to a server. If the file stays, declare new tables `STRICT` and set `busy_timeout`, so a bad value and a busy writer both fail loudly.

- SQLite is a library that reads a file inside your process. There is no server, no port, and no role.
- A file fits workloads with one owner, one writer at a time, and far more reads than writes.
- The five gaps are roles and grants, schemas, many concurrent writers, enforced column types, and general `ALTER TABLE`.
- A declared type sets affinity, so a value can arrive with a different storage class. A `STRICT` table adds real checking per table.
- `UNION ALL` stacks results. The first branch names the columns, and every branch must project the same shape.
- Copying the file copies the database, and `VACUUM INTO` takes a consistent copy while it is open.

## Check yourself

**1. A friend plans a shared invoicing system for six employees who all write during the same hour. Why is one SQLite file the wrong store for that job?**

<details>
<summary>Answer</summary>

Every write takes the file's single write lock. Six people writing in the same minutes will queue, and a writer that waits past `busy_timeout` fails with `SQLITE_BUSY`. The file also has no roles, so the database cannot grant one employee read-only access to the invoices of another. A server that locks rows, not the whole file, fits that job.

</details>

**2. Why can no lesson in this course write `dataset.customers`?**

<details>
<summary>Answer</summary>

A schema is a namespace inside one server, and a SQLite file holds one namespace. `ATTACH` adds a second file to the connection, which is a second database, not a namespace inside this one. The SQLite mirror of the commerce dataset therefore keeps its four tables unqualified.

</details>

**3. `products.price` is declared `NUMERIC`, and chapter 2 found ten integer values and ten real ones. What would a `STRICT` version of that table change?**

<details>
<summary>Answer</summary>

`NUMERIC` is not one of the types a strict table accepts, so the declaration would have to become `REAL`. A `REAL` column under `STRICT` stores every fitting value as a real, so the ten integers would arrive as reals too. A text value would be rejected with `SQLITE_CONSTRAINT_DATATYPE` instead of stored.

</details>

**4. A `UNION ALL` branch projects `COUNT(*)` before its label. What does the reader see?**

<details>
<summary>Answer</summary>

The columns stop meaning one thing each. `relation` holds a number and `table_rows` holds a name for that row. The sort places it first, because text outranks every integer in SQLite's ordering, so a largest-first report opens with the wrong line. You spot it by reading the first column: a table list that contains a number is the sign.

</details>
