# Dates and intervals without types

The report needs one row for every month in a range. Port it to SQLite and you get five rows and no error, so nothing looks wrong until you count them. Two things changed at once: the month column is text, and the month with no orders is gone.

PostgreSQL carries a date type and an interval type, with typed literals and `DATE_TRUNC` to match. SQLite stores a date as ISO-8601 text and does the arithmetic in functions that take modifier strings. This chapter walks where that difference shows up in a port.

## There is no date type

PostgreSQL declares `ordered_at` as `timestamp`, and `DATE '2026-01-01'` is a typed literal the parser knows. SQLite has no date type. The dataset stores the value as text, in the same characters PostgreSQL prints:

```sql
SELECT typeof(ordered_at) AS stored, ordered_at
FROM orders
LIMIT 1;
```

| stored | ordered_at |
| --- | --- |
| text | 2026-01-04 10:12 |

SQLite has five storage classes, and date is not one of them: NULL, INTEGER, REAL, TEXT, BLOB. The table declares the column `TIMESTAMP` all the same. That declared type sets an affinity, not a storage class, and the value that arrives is text.

The engine checks nothing on the way in. An impossible date is still a stored string, and a function that cannot read it returns NULL rather than an error, so the cost lands in the report.

PostgreSQL's date vocabulary does not parse here. `SELECT DATE '2026-01-01'` reports `no such column: DATE`, and `ordered_at + INTERVAL '1 month'` reports `no such column: INTERVAL`. The engine reads both as column names.

ISO-8601 text still sorts and compares as text, so `ORDER BY ordered_at` and a `BETWEEN` on dates work unchanged. Calendar arithmetic is the part that needs a function.

The date functions accept the common ISO-8601 spellings: `YYYY-MM-DD`, an optional space or `T`, then `HH:MM`, `HH:MM:SS`, and a fractional part. `date('2026-01-04')` returns `2026-01-04`, `datetime('2026-01-04 10:12')` returns `2026-01-04 10:12:00`, and `date('2026-13-01')` returns NULL.

## Modifiers, not operators

`date(d, '+1 month')` is the arithmetic, and the second argument is a modifier string. The modifiers cover days, months, years, hours, minutes, seconds, weekdays, `start of month`, and `start of year`. They apply left to right, so a chain builds a result one step at a time. The first argument can be `'now'` in place of a date.

```sql
SELECT date('2026-01-04', '+1 day')                                        AS tomorrow,
       date('2026-01-04', 'start of month')                                AS month_start,
       date('2026-01-04', 'start of month', '+1 month', '-1 day')          AS month_end,
       unixepoch('2026-01-04 10:12')                                       AS epoch;
```

| tomorrow | month_start | month_end | epoch |
| --- | --- | --- | --- |
| 2026-01-05 | 2026-01-01 | 2026-01-31 | 1767521520 |

The third column reads as a sentence: go to the start of the month, forward one month, back one day. That is how you get the last day of a month, because no modifier names it. `julianday()` returns the same instant as a floating-point day number, and `unixepoch()` returns whole seconds.

## Adding a month is not adding 30 days

A month is not a fixed number of days, so month arithmetic has to pick a behaviour at a month end. PostgreSQL clamps to the last day of the target month. SQLite increments the month field and then normalises the overflow:

```sql
SELECT date('2026-01-31', '+1 month')                                   AS naive,
       date('2026-01-31', '+1 month', 'start of month')                 AS normalised,
       CAST(julianday('2026-02-01') - julianday('2026-01-01') AS INTEGER) AS jan_days;
```

| naive | normalised | jan_days |
| --- | --- | --- |
| 2026-03-03 | 2026-03-01 | 31 |

PostgreSQL answers `2026-02-28` for `DATE '2026-01-31' + INTERVAL '1 month'`. February 31st does not exist, so SQLite carries the three extra days into March. `2026-03-03` is not a typo. It is what adding a month means when the arithmetic moves a field and renormalises the date.

The second column shows the repair: apply `'start of month'` after the step, and the result lands on the 1st.

## A wrong turn: a report with no February

A monthly spine that starts on the last day of a month inherits the roll on every step.

```sql
WITH RECURSIVE months(m) AS (
  SELECT '2026-01-31'
  UNION ALL
  SELECT date(m, '+1 month') FROM months WHERE m < '2026-05-01'
)
SELECT months.m AS month, COUNT(orders.id) AS orders
FROM months
LEFT JOIN orders
  ON strftime('%Y-%m', orders.ordered_at) = strftime('%Y-%m', months.m)
GROUP BY months.m
ORDER BY months.m;
```

| month | orders |
| --- | --- |
| 2026-01-31 | 16 |
| 2026-03-03 | 18 |
| 2026-04-03 | 18 |
| 2026-05-03 | 9 |

February has 19 orders and no row. The steps land on the 3rd of each month, and only January is right, because it is the seed. Start the spine on the first of a month and the same query returns a row per month.

Try this: change the seed from `'2026-01-31'` to `'2026-01-01'` and run the query again. Nothing else changes. The month column lands on the 1st, and February comes back with the orders it had all along. The seed date is the whole defect.

## Durations come from `julianday()`

Subtracting one date from another is the habit that ports worst, because it runs and returns a number. `SELECT '2026-02-01' - '2026-01-01'` returns 0 here, since SQLite converts both strings to numbers. PostgreSQL returns 31 for the same arithmetic on two dates.

The working version subtracts two Julian day numbers:

```sql
SELECT c.name,
       CAST(julianday(MIN(o.ordered_at)) - julianday(c.signup_date) AS INTEGER) AS days_to_first_order
FROM customers c
JOIN orders o ON o.customer_id = c.id
GROUP BY c.id
ORDER BY days_to_first_order DESC, c.name
LIMIT 3;
```

| name | days_to_first_order |
| --- | --- |
| Farid Lindqvist | 76 |
| Gina Rahman | 67 |
| Ada Whitfield | 63 |

`julianday()` returns a floating-point day number, so the difference is a day count and `CAST(... AS INTEGER)` truncates it. For seconds, use `unixepoch(a) - unixepoch(b)` or `strftime('%s', a)`. PostgreSQL hands you an `interval` from two timestamps and an integer from two dates. Here you pick the unit, and `julianday()` gives days.

## `generate_series` is not in the engine

PostgreSQL's `generate_series` builds a spine of dates or numbers, and it is not compiled into SQLite. `SELECT COUNT(*) FROM generate_series('2026-01-01', '2026-06-01', '1 month')` reports `no such table: generate_series`. The command-line shell loads it as an extension, so a query can work in your terminal and fail inside the application.

A recursive CTE is the portable replacement:

```sql
WITH RECURSIVE months(m) AS (
  SELECT '2026-01-01'
  UNION ALL
  SELECT date(m, '+1 month') FROM months WHERE m < '2026-06-01'
)
SELECT months.m AS month, COUNT(orders.id) AS orders
FROM months
LEFT JOIN orders
  ON strftime('%Y-%m', orders.ordered_at) = strftime('%Y-%m', months.m)
GROUP BY months.m
ORDER BY months.m;
```

| month | orders |
| --- | --- |
| 2026-01-01 | 16 |
| 2026-02-01 | 19 |
| 2026-03-01 | 18 |
| 2026-04-01 | 18 |
| 2026-05-01 | 9 |
| 2026-06-01 | 0 |

The seed row runs once. Then each pass adds a month while `m < '2026-06-01'` holds, and that guard is the termination condition. Without it the CTE never stops.

June is the row the spine exists for: `LEFT JOIN` keeps the month and `COUNT(orders.id)` counts zero, because a missing row from `orders` is not a row to count.

## What to remember

What I would do: store dates as ISO-8601 text, seed the `WITH RECURSIVE` spine on the first of a month, and keep `generate_series` out of any query that ships. Use `julianday()` for a duration, and say which unit comes back. Count the rows against the months you asked for, because a lost month returns no error.

- A date is ISO-8601 text. `DATE '2026-01-01'` and `INTERVAL '1 month'` do not parse.
- Arithmetic is a function with modifier strings, applied left to right.
- `'+1 month'` increments the month field and normalises, so 31 January rolls to 3 March. PostgreSQL clamps to 28 February.
- `julianday()` differences give days; `unixepoch()` gives seconds. Subtracting two date strings gives 0.
- `generate_series` is absent. A `WITH RECURSIVE` CTE builds the spine, and its guard stops it.

## Check yourself

**1. Why does `SELECT DATE '2026-01-01'` fail?**

<details>
<summary>Answer</summary>

There is no date type for the parser to cast to. SQLite reads `DATE` as a column name and reports `no such column: DATE`. Use `date('2026-01-01')`, or compare the text directly.

</details>

**2. Why is 31 January plus one month the 3rd of March?**

<details>
<summary>Answer</summary>

The modifier increments the month field, which gives 31 February, and the engine normalises the overflow. February has 28 days in 2026, so three days carry into March. PostgreSQL clamps to 2026-02-28 instead.

</details>

**3. How does a month with no orders still get a row in the spine query?**

<details>
<summary>Answer</summary>

The spine of months is the left side of the `LEFT JOIN`, so every month survives. `COUNT(orders.id)` counts matched rows, and an unmatched month has none, so it counts 0. `COUNT(*)` would return 1.

</details>

**4. How do you get a day count between two text dates?**

<details>
<summary>Answer</summary>

Subtract two `julianday()` values and cast the result. A plain subtraction of two text dates returns 0, because SQLite converts each string to a number, so the query runs and answers the wrong thing.

</details>
