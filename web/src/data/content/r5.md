# JSON, generated columns and expression indexes

## `json1` is in the build

PostgreSQL ships `json` and `jsonb`. SQLite ships `json1`, and on any modern build it is compiled in — no extension to load, no `CREATE EXTENSION`. The functions are `json()`, `json_extract()`, `json_object()` and `json_group_array()`; since 3.38 there are also the two shorthand operators, `->` for "give me JSON" and `->>` for "give me the scalar as SQL text".

```sql
SELECT json_extract('{"sku": "QC-1", "qty": 3}', '$.qty') AS qty,
       '{"sku": "QC-1"}' ->> '$.sku' AS sku;
```

| qty | sku |
| --- | --- |
| 3 | QC-1 |

The difference between the operators is the return type, and it bites when you filter. `->` returns a JSON value — so `'{"n": 1}' -> '$.n'` is the JSON number `1`, not the SQL integer — while `->>` returns the SQL value, which is almost always what a `WHERE` clause wants. A query that compares a `->` result to a number is comparing a JSON document to a number, and the answer may surprise you.

## Storage is still TEXT

A JSON document in SQLite is TEXT. There is no `jsonb`-style binary representation and no write-time validation unless you ask for it with a `CHECK (json_valid(col))` constraint. The functions parse on every call, which is fine for the sizes a row holds and means the "is it jsonb or json?" question from PostgreSQL does not arise: there is one representation, it is the text you wrote, and the cost of parsing is the price of reading it.

Because it is just text, building JSON from a result set is a `GROUP BY` with `json_group_array`:

```sql
SELECT category,
       json_group_array(name) AS products
FROM (SELECT category, name FROM products ORDER BY category, name)
GROUP BY category
ORDER BY category;
```

| category | products |
| --- | --- |
| Electronics | ["Aurora Wireless Earbuds","Nimbus Headphones","Noise-Cancel Earmuffs","Pulse Fitness Tracker","Vertex Mechanical Keyboard"] |
| Home | ["Bamboo Shelf","Cedar Desk Lamp","Ceramic Vase","Linen Duvet Cover","Wool Throw Blanket"] |
| Kitchen | ["Copper Kettle","Espresso Tamper","Granite Cookware Set","Maple Cutting Board"] |
| Outdoor | ["Discontinued Camp Stove","Harbor Rain Shell","Rope Dog Leash","Solar Camp Lantern","Summit Hiking Poles","Trail Runner Jacket"] |

The inner `ORDER BY` is load-bearing: `json_group_array` collects rows in the order the scan produced them, so without it the array order is an implementation detail. An ordered subquery feeding the aggregate is the SQLite idiom for "build this array deterministically".

## Generated columns (3.31+)

A generated column is computed from other columns in the same row. `VIRTUAL` computes on read and stores nothing; `STORED` computes on write and occupies space, which is what lets you index it.

```sql
CREATE TABLE products_v2 (
    id        INTEGER PRIMARY KEY,
    name      TEXT NOT NULL,
    price     NUMERIC NOT NULL,
    price_txt TEXT GENERATED ALWAYS AS (printf('%.2f', price)) STORED
);
```

That definition is also the answer to the money problem from the affinity chapter: `price_txt` fixes the two-decimal scale at write time, so the value the application reads is the value the report needs and no `printf` is needed on the way out. PostgreSQL has the same feature with the same `STORED`/`VIRTUAL` split, so this part of the port is a naming exercise rather than a redesign.

## Index the expression, or a slice of the table

Two index shapes carry more weight in SQLite than the equivalent in PostgreSQL, because there is no other place to put the work.

An **expression index** indexes a value the query computes rather than a bare column — `CREATE INDEX products_name_nocase ON products (name COLLATE NOCASE)` makes the case-insensitive sort from the essentials course indexable. A **partial index** indexes a predicate's slice — `CREATE INDEX orders_open ON orders (customer_id) WHERE status = 'pending'` — and the planner uses it only for queries whose `WHERE` implies the same slice. Both exist in PostgreSQL; both are more important here, because a function wrapped around a column hides an index and there is no plan-cost feedback loop to tell you it did.

## Check yourself

**1. What is the difference between `->` and `->>`?**

<details>
<summary>Answer</summary>

`->` returns a JSON value, `->>` returns the scalar as SQL text/number. Filter and compare with the second; use the first when you want to keep building JSON.

</details>

**2. Why does the `json_group_array` query order the subquery?**

<details>
<summary>Answer</summary>

The aggregate collects rows in scan order, which is not defined without an `ORDER BY`. Ordering the subquery makes the array contents deterministic.

</details>

**3. What is the difference between a `STORED` and a `VIRTUAL` generated column?**

<details>
<summary>Answer</summary>

`VIRTUAL` is computed on read and stores nothing; `STORED` is computed on write and occupies space, so it can be indexed. Both are generated from other columns of the same row.

</details>
