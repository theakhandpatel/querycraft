# IN, EXISTS and the NULL trap

The customer list came back empty. The query asked which customers sit outside a list of four cities, and it returned 0 rows where `NOT EXISTS` returned 22. No error, no warning, no hint about which part of the query gave up.

The retention team's version is the safe one, and that is the trap. It wants the customers who have never placed an order, so it can send them a first-purchase offer. You have met both spellings of that question already, `IN` in the first chapter of this course and `EXISTS` in the second. Both return the same seven names, because `orders.customer_id` is declared `NOT NULL` in `backend/internal/dataset/schema.sql`. Point the same shape at a column that allows `NULL`, and `NOT IN` can return nothing at all.

This chapter shows the logic behind that silence, the form that avoids it, and the comparison operator that treats an unknown as a value.

## Same question, two spellings

`IN` takes a one-column list and tests each row for membership in it. `EXISTS` takes a subquery and reports whether at least one row matches. Both reduce to the same test here, which is whether the customer has an order.

```sql
SELECT count(*) AS with_orders
FROM customers
WHERE id IN (SELECT customer_id FROM orders);
```

| with_orders |
| --- |
| 23 |

```sql
SELECT count(*) AS with_orders
FROM customers c
WHERE EXISTS (SELECT 1 FROM orders o WHERE o.customer_id = c.id);
```

| with_orders |
| --- |
| 23 |

PostgreSQL reads both as a semi-join, which is a join that keeps each customer row at most once however many order rows match it. The count comes back the same because the database recognises the shared meaning, not because you wrote the same words twice.

The agreement has one condition. `IN` is shorthand for a chain of equality tests against the values the subquery returns, and `EXISTS` is a search for a matching row.

Those two ideas coincide while every value in play is either a real value or a real non-match. They part company the moment `NULL` appears, because `NULL` is not a value. It means unknown.

That agreement costs a whole answer, not one row. The same shape with `NOT IN` on a nullable column returns none of the rows it is supposed to.

## A comparison answers true, false or unknown

A `WHERE` clause keeps a row only when its predicate is true. SQL gives a predicate three possible answers, and only one of them keeps the row: true keeps it, false drops it, unknown drops it too. Unknown is what you get whenever a comparison cannot be settled, and comparing anything to `NULL` cannot be settled. This is called three-valued logic, and it is the rule behind every silent `NULL` surprise in this chapter.

The city column shows all three answers at once. Thirty customers, three of them in Leeds, four with no city recorded, and the rest somewhere else.

| group | customers | `city = 'Leeds'` |
| --- | --- | --- |
| lives in Leeds | 3 | true |
| lives elsewhere | 23 | false |
| city not recorded | 4 | unknown |

A filter keeps one of those three answers and drops the rest. `WHERE city = 'Leeds'` keeps the 3 customers marked true. `WHERE city <> 'Leeds'` keeps the 23 marked false, and still drops the 4 marked unknown, because flipping a comparison does not turn unknown into true. That is why "not Leeds" returns 23 rows instead of 27.

## One NULL in the list empties the result

`IN` is sugar for a chain of `=` tests joined by `OR`. `NOT IN` is the same chain with `<>` and `AND`:

```text
x NOT IN (a, b, NULL)
  ->  x <> a AND x <> b AND x <> NULL
```

The third term is the trouble. `x <> NULL` is unknown for every `x`, on every row, always. An `AND` is true only when all of its terms are true, so one unknown term is enough to stop the conjunction from being true. The row is dropped.

Here is the expansion run against real ids, with the list `(1, 2, NULL)`. Each column is one term of the conjunction, and the last column is the answer that `WHERE` sees.

| `id` | `id <> 1` | `id <> 2` | `id <> NULL` | whole conjunction |
| --- | --- | --- | --- | --- |
| 1 | false | true | unknown | false |
| 2 | true | false | unknown | false |
| 3 | true | true | unknown | unknown |
| 4 | true | true | unknown | unknown |

Customer 1 fails on the first term and customer 2 fails on the second. Customers 3 and 4 pass both equality tests and then meet the unknown term, which leaves the whole expression unknown. Nothing in the table is true, so the query returns no rows.

The failure is total rather than partial, and that is worth pausing on.

A real value in the list removes only the rows that equal it. A `NULL` removes every row, however many real values sit beside it.

Remove the `NULL` and the same query comes back with a real answer:

```sql
SELECT count(*) FILTER (WHERE id NOT IN (1, 2))      AS without_null,
       count(*) FILTER (WHERE id NOT IN (1, 2, NULL)) AS with_null
FROM customers;
```

| without_null | with_null |
| --- | --- |
| 28 | 0 |

Twenty-eight customers are neither id 1 nor id 2. Add `NULL` to the list and the count falls from 28 to 0 without a single customer changing. The list did the damage, not the table.

The left side of the comparison carries the same hazard. `NULL NOT IN (1, 2)` is unknown too, so a nullable column on the left loses its own rows even when the list is clean. Both sides have to hold real values for `NOT IN` to mean what you think.

## The trap is live in this dataset

`orders.customer_id` is `NOT NULL`, so the obvious query is safe here, and that is exactly why the bug ships. The same shape pointed at a nullable column fails today. `customers.city` allows `NULL`, and four customers leave it empty.

```sql
SELECT count(*) AS not_in_list
FROM customers
WHERE city NOT IN (SELECT city FROM customers WHERE id <= 4);

SELECT count(*) AS not_exists
FROM customers c
WHERE NOT EXISTS (
    SELECT 1 FROM customers c2 WHERE c2.id <= 4 AND c2.city = c.city
);
```

The subquery returns four cities: Leeds, Milan, Lagos and one `NULL`, because customer 4 has no city. Those four values become four `<>` terms, one of which is `city <> NULL`. The first query returns 0 rows. The second returns 22.

The 22 are the 18 customers in other cities plus the 4 whose city is unknown. `EXISTS` never evaluates `city <> NULL`; it asks whether a matching row was found, and an unknown comparison finds nothing. So the unknown-city customers survive, which is the honest answer to "no customer with id 4 or below shares this city".

Nothing about the first query is broken syntax. It parses, it plans, it runs, and it returns zero rows, which is also a plausible answer to a real question. A report that goes blank after a data import looks like missing data. The cause is one `NULL` in a list you never wrote by hand.

## The NULL-safe forms, and the seven customers

`NOT EXISTS` is the form to reach for. It keeps the outer row when the inner query finds nothing, and it never compares a value against a list that might hold `NULL`.

```sql
SELECT c.name
FROM customers c
WHERE NOT EXISTS (
    SELECT 1 FROM orders o WHERE o.customer_id = c.id
)
ORDER BY c.name;
```

| name |
| --- |
| Aya Rahman |
| Bo Ivanov |
| Cleo Haidar |
| Dara Novak |
| Dev Larsen |
| Yara Park |
| Zane Lindqvist |

Seven names, one per customer with no order. Read the inner query as a test on the current row: it asks whether any order belongs to this customer. When no order does, the customer is kept.

A `LEFT JOIN` reaches the same set. Join `customers` to `orders`, then keep the rows where the order side came back empty:

```sql
SELECT c.name
FROM customers c
LEFT JOIN orders o ON o.customer_id = c.id
WHERE o.id IS NULL
ORDER BY c.name;
```

That returns the same seven names. The test `o.id IS NULL` is unambiguous only because `orders.id` is a primary key and cannot be null. Join on a nullable column and the test matches rows it should not.

A third option changes the list instead of the operator. Add `WHERE customer_id IS NOT NULL` inside the subquery, and no `NULL` can reach the comparison. That is correct when ignoring null keys is what you mean. It is not a general fix, because it decides a question about the data on the reader's behalf.

The rule worth carrying: use `NOT EXISTS` or the `LEFT JOIN` form whenever the subquery column can be `NULL`. Use `NOT IN` only when you can point at the `NOT NULL` in the schema that makes it safe.

## IS DISTINCT FROM treats a missing value as a value

Sometimes you want the unknown row in the result. `IS DISTINCT FROM` compares two values and treats `NULL` as a value you can match, so `NULL IS DISTINCT FROM 'Leeds'` is true rather than unknown.

```sql
SELECT count(*) FILTER (WHERE city <> 'Leeds')           AS plain,
       count(*) FILTER (WHERE city IS DISTINCT FROM 'Leeds') AS null_safe
FROM customers;
```

| plain | null_safe |
| --- | --- |
| 23 | 27 |

The difference is the four customers with no city. The plain `<>` cannot judge them, so it drops them. `IS DISTINCT FROM` treats "no city" as distinct from "Leeds", which matches how a person reads the question, so the four come back and the count rises to 27.

There is a mirror operator for the other direction. `IS NOT DISTINCT FROM` is an equality test that counts `NULL` as equal to `NULL`, which makes it the only safe way to compare two nullable columns for sameness.

Try this: run `count(*) FILTER (WHERE city = 'Leeds')` beside `count(*) FILTER (WHERE city IS NOT DISTINCT FROM 'Leeds')`. Both return 3, because neither form treats a missing city as Leeds. The null-safe equality earns its keep only when the right side is also a column that can be null.

These operators matter in this chapter because they are the row-level version of the same decision `NOT IN` refuses to make. `NOT IN` gives up on unknown and drops the row. `IS DISTINCT FROM` picks an answer and keeps it. Choose the one that matches your question, and write the query so the next reader can see the choice.

## What the exercise asks you to practise

The exercise asks for the name of every customer who has never placed a completed order, alphabetically, using the NULL-safe form. The chapter's example asks who has never ordered at all. The shape is the same, but the exercise adds one condition inside the inner query: `o.status = 'completed'`. On this dataset plain `NOT IN` would pass the check, because `customer_id` cannot be null. The point is the habit: the query you write here runs unchanged on a schema where the column is nullable.

Two things to check before you submit. The result is one column named `name`, so the sort has something to order by. And the count is eleven, which you can confirm against the nineteen customers who have placed a completed order.

The next chapter asks the same question again with `EXCEPT`, a set operation that subtracts one list from another. Three tools for one question, and each one fails in a different place.

## What to remember

**What I would do:** write `NOT EXISTS` first, and switch to `NOT IN` only when you can point at the `NOT NULL` in the schema that makes it safe. Then run the query against a row whose key is missing, because that is the row the two forms disagree on. When the unknown rows belong in the answer, use `IS DISTINCT FROM` and let the query say so.

- `IN` tests membership in a list and `EXISTS` tests for a matching row. On a key that cannot be null, both return the same rows.
- A comparison answers true, false or unknown, and `WHERE` keeps only true. Comparing anything to `NULL` gives unknown.
- `x NOT IN (a, b, NULL)` expands to an `AND` chain with one unknown term, which no row can satisfy, so the result is empty.
- A nullable left side fails the same way: `NULL NOT IN (1, 2)` is unknown and the row is dropped.
- `NOT EXISTS` and `LEFT JOIN ... WHERE key IS NULL` avoid the trap, provided the join key cannot be null.
- `IS DISTINCT FROM` keeps the unknown rows, and `IS NOT DISTINCT FROM` is the null-safe equality form.

## Check yourself

**1. Why does one `NULL` in the list empty a `NOT IN` result?**

<details>
<summary>Answer</summary>

The `<>` tests are joined by `AND`, and the `NULL` term is unknown on every row. An `AND` is true only when all terms are true, so no row can pass. An extra real value adds one more term, and a non-matching row satisfies it, so the answer changes without collapsing.

</details>

**2. Customer ids 3 and 4 both drop out of `WHERE id NOT IN (1, 2, NULL)`. How does their reason differ from customer 1's?**

<details>
<summary>Answer</summary>

Customer 1 fails a real test: `id <> 1` is false. Customers 3 and 4 pass both equality tests and then meet `id <> NULL`, which is unknown. Anything other than true drops the row, so both rows go, for a different reason.

</details>

**3. `orders.customer_id` is `NOT NULL`, so `NOT IN` passes the exercise. Why is that not evidence that the query is safe?**

<details>
<summary>Answer</summary>

Because the safety comes from the schema, not from the query. A column that allows `NULL`, an outer join that produces nulls, or a fresh import can change that in a release that never touches your SQL. Point the same shape at `customers.city` and the count goes to zero.

</details>

**4. What does `WHERE city IS DISTINCT FROM 'Leeds'` return that `WHERE city <> 'Leeds'` does not, and why?**

<details>
<summary>Answer</summary>

The four customers with no city. `<>` cannot judge them, so the comparison is unknown and the row is dropped, giving 23. `IS DISTINCT FROM` treats the missing city as a value distinct from Leeds, so all 27 non-Leeds rows come back.

</details>

**5. How does `NOT EXISTS` decide a row is unmatched when the correlated column is unknown?**

<details>
<summary>Answer</summary>

It looks for a row where the inner condition is true. An unknown comparison is not true, so nothing matches, and `NOT EXISTS` keeps the outer row. That is why the unknown-city customers appear in the `EXISTS` count of 22.

</details>
