# Booleans, numerics and the value contract

## There is no boolean and no decimal

PostgreSQL has a `boolean` type and a `numeric` type with a declared scale. SQLite has neither: a `BOOLEAN` column holds 1 or 0, and a `NUMERIC` column holds whatever storage class the value turned out to be. The port therefore has two moving parts — the spelling the query uses, and the value the client receives — and the second one is what a contract has to name.

```sql
SELECT TRUE AS t, FALSE AS f, typeof(TRUE) AS t_stored;
```

| t | f | t_stored |
| --- | --- | --- |
| 1 | 0 | integer |

`TRUE` and `FALSE` parse, and they are the integers 1 and 0. Where PostgreSQL returns `t`/`f` (or `true`/`false` in a JSON result), SQLite returns 1/0, and an encoding rule reports that as a number. That is not a bug to paper over — a smallint is what the storage model actually has — but it means a client that branched on `=== true` now sees `1`, and a `STRICT` table will not let you declare the column `BOOLEAN` at all. `INTEGER` holding 1/0 is the honest shape.

## Money has no fixed scale

`products.price` and `order_items.unit_price` are `numeric(10,2)` in PostgreSQL: an exact decimal that always prints two places. They are `NUMERIC` in SQLite, which is an affinity, not a scale. The seed writes `59.00` and the column holds the integer `59`; it writes `42.50` and the column holds the real `42.5`. `typeof()` shows both, and `printf('%.2f', price)` is how the two-decimal form comes back at the edge.

Floating-point addition is where that becomes visible:

```sql
SELECT SUM(1.0 * oi.quantity * oi.unit_price)          AS raw_revenue,
       ROUND(SUM(1.0 * oi.quantity * oi.unit_price), 2) AS rounded_revenue
FROM orders o
JOIN order_items oi ON oi.order_id = o.id
WHERE o.status = 'completed'
  AND strftime('%Y-%m', o.ordered_at) = '2026-04';
```

| raw_revenue | rounded_revenue |
| --- | --- |
| 1803.6200000000001 | 1803.62 |

PostgreSQL's `numeric` would have returned the exact `1803.62`. SQLite's REAL arithmetic returned the nearest double, and the JSON number carrying it cannot be shortened back to the decimal. `ROUND(x, 2)` at the edge is the fix, and it is a *contract* fix rather than a display one: a result compared cell for cell must not carry an artifact of how the engine summed.

The `1.0` is deliberate — it forces REAL arithmetic on integer-valued operands (`quantity` is INTEGER). `SUM(quantity * unit_price)` sums whatever the operands turn out to be, which on this data is a mix; that is the dynamic typing showing through a sum.

## Identity: `serial` becomes the rowid

The other value-contract port is the primary key. PostgreSQL's `serial` and `GENERATED … AS IDENTITY` create a sequence object, with `nextval` and `currval` to manage. SQLite's `INTEGER PRIMARY KEY` makes the column an alias for the table's `rowid`, which the engine assigns on insert; there is no sequence to own, and the id is the physical key.

`AUTOINCREMENT` is the keyword that looks like the port and usually is not. A plain `INTEGER PRIMARY KEY` reuses the largest id after a delete — the rowid is the largest ever used *or* the largest in the table, whichever is cheaper. `AUTOINCREMENT` adds a `sqlite_sequence` table and promises ids that never repeat. It is a different guarantee with a different cost, so port `serial` to `INTEGER PRIMARY KEY`, and reach for `AUTOINCREMENT` only when the application needs the monotonic promise.

`RETURNING` (3.35+) does port: `INSERT … RETURNING id` works. `last_insert_rowid()` is the older, connection-scoped alternative, and it is confused by inserts that fire inside triggers.

## Text building and concatenation

`||` is the same operator in both dialects and has the same NULL rule: `'a' || NULL` is NULL. What differs is the surrounding vocabulary. PostgreSQL's `concat()` skips NULLs and `concat_ws()` joins with a separator; SQLite only learned `concat()` in 3.44, so the portable expression is `||` with an explicit `COALESCE`, or `printf`, which is SQLite's formatting primitive.

```sql
SELECT CAST(59 AS TEXT) || ' units' AS with_units,
       printf('%.2f', 42.5)        AS fixed_scale,
       (1 || 2)                    AS concat_nums;
```

| with_units | fixed_scale | concat_nums |
| --- | --- | --- |
| 59 units | 42.50 | 12 |

`1 || 2` is `'12'` — the operator coerces both sides to text — and `printf('%.2f', …)` is how a fixed scale comes back for a report. `CAST(x AS TEXT)` and `x || ''` are the same conversion.

## Check yourself

**1. What does a `BOOLEAN` column hold, and what does a client receive?**

<details>
<summary>Answer</summary>

1 or 0. Nothing coerces it back to true/false — the value is reported as an integer and `typeof(TRUE)` is `integer`. A STRICT table cannot declare `BOOLEAN` at all.

</details>

**2. Why did the April revenue come back as 1803.6200000000001?**

<details>
<summary>Answer</summary>

The sum ran in REAL arithmetic, which is binary floating point, so the exact decimal is not representable. PostgreSQL's `numeric` would have been exact. `ROUND(x, 2)` at the edge restores the contract.

</details>

**3. What is the port of `serial`, and when do you want `AUTOINCREMENT`?**

<details>
<summary>Answer</summary>

`INTEGER PRIMARY KEY` — the rowid alias, which auto-assigns and needs no sequence. `AUTOINCREMENT` earns its `sqlite_sequence` table only when ids must never be reused after a delete.

</details>
