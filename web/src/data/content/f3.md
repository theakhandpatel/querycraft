# ORDER BY, LIMIT and OFFSET

The product list shows three items at a time, most expensive first, and a "Next" link asks for page two. That request returns three rows, and nothing in it promises which three. Change one row, add one index, and page two can repeat a row from page one or skip a row that belongs to neither.

That is the point of this chapter. A query without `ORDER BY` returns rows in whatever order the engine found convenient, and "whatever the engine found convenient" is not a fact you can build a page on. `ORDER BY` fixes a sequence, `LIMIT` cuts the end off that sequence, and `OFFSET` skips the front. Used together they page a result.

## A result has no order until you ask for one

Rows live in a table in the order the server wrote them, and that order is not part of the table's meaning. When you run a query with no `ORDER BY`, PostgreSQL returns the rows in whatever order its chosen plan produced them. A sequential scan tends to return them in storage order. An index scan returns them in index order. A parallel plan splits the work across workers and stitches the results together as they finish.

None of that is a bug, because no order was promised. It is still a hazard, because the order can change for reasons that have nothing to do with your query.

Update a row and the server may move it to the end of the table. Add an index and the plan changes. Run the same query on a bigger machine and the workers finish in a different sequence. A report that relies on the incidental order will pass every test today and shift its rows next month. A paged list loses the row instead: it falls between two requests, and no screen prints an error.

`ORDER BY` turns the order into part of the answer. It runs after `WHERE` has dropped rows, so it sorts the survivors and no others. It runs before `LIMIT`, which is what makes a cut meaningful. Each key can be ascending (the default) or descending, and you set that per key.

`ORDER BY` can use a column name, an output alias from `SELECT`, or an expression. It also accepts a column position, as in `ORDER BY 2`, which counts the output columns. That form works and it breaks the moment someone edits the `SELECT` list, so name the column instead.

## Ties need a second key

Two rows tie when they have the same value on the first sort key. All 20 products have different prices, so `ORDER BY price DESC` happens to leave no product tied with another. That is luck, not a property of the table. Most real sorts tie constantly: `orders` has five status values across 80 rows, so eleven orders share `cancelled` and eleven more share `shipped`.

When rows tie, `ORDER BY` has nothing to say about their relative order, and the engine puts them in whatever sequence the sort produced. A second key settles that:

```sql
SELECT id, status, ordered_at
FROM orders
ORDER BY status, ordered_at
LIMIT 4;
```

| id | status | ordered_at |
| --- | --- | --- |
| 1012 | cancelled | 2026-01-20 03:00 |
| 1003 | cancelled | 2026-01-22 09:03 |
| 1019 | cancelled | 2026-02-01 02:00 |
| 1026 | cancelled | 2026-02-13 01:00 |

`status` puts all the cancelled orders together at the top of the list. `ordered_at` then sorts inside that group, oldest first, because it inherits the ascending default. Every one of the 80 orders has its own timestamp, so this pair settles every tie in this data. On a busier table two orders can share a minute, and then you add `id` as a third key.

The second key is not decoration. Suppose you page through `ORDER BY status LIMIT 3 OFFSET 0`, then `OFFSET 3`, then `OFFSET 6`. Every row on page one is `cancelled`, and the query never says which cancelled rows.

Nothing forces the two requests to break the tie group the same way, so a row can land on two pages or on none. End the `ORDER BY` with something unique, usually the primary key, and the pages stop overlapping.

Try this: remove `ordered_at` from the `ORDER BY` above and run it again. It still returns four cancelled orders, but which four, and in what order, is now up to the plan. Page two of that sort can hold rows page one already showed.

## Walking through one sorted query

The demo query pages the product list, three at a time, most expensive first.

```sql
SELECT name, price
FROM products
ORDER BY price DESC, name
LIMIT 3 OFFSET 3;
```

| name | price |
| --- | --- |
| Harbor Rain Shell | 118.00 |
| Summit Hiking Poles | 96.40 |
| Vertex Mechanical Keyboard | 89.50 |

Read it as five steps, in this order.

```text
FROM      -> 20 rows from products
SELECT    -> keep name and price for each row
ORDER BY  -> sort by price, then name
OFFSET 3  -> drop the first 3 rows
LIMIT 3   -> keep the next 3 rows
```

Here is the sorted list the middle steps see, with the page each rank belongs to.

| rank | name | price | page |
| --- | --- | --- | --- |
| 1 | Granite Cookware Set | 210.00 | 1 |
| 2 | Trail Runner Jacket | 139.00 | 1 |
| 3 | Nimbus Headphones | 129.00 | 1 |
| 4 | Harbor Rain Shell | 118.00 | 2 |
| 5 | Summit Hiking Poles | 96.40 | 2 |
| 6 | Vertex Mechanical Keyboard | 89.50 | 2 |

`OFFSET 3` discards ranks 1 to 3, `LIMIT 3` keeps ranks 4 to 6, and page three starts at rank 7. The `name` key never fires here, because no two products cost the same. It sits in the query so that the ranking stays total if two prices ever match, and so a page cannot shuffle when that happens.

## LIMIT and OFFSET cut a window

The two clauses have different jobs, and mixing them up is the most common paging bug.

`LIMIT n` says how many rows the result may contain. `OFFSET k` says how many rows to skip before the result starts. `LIMIT` is the page size. `OFFSET` is the count of rows behind the page.

Page one needs no `OFFSET`, since nothing is skipped. From page two onward the arithmetic is `OFFSET = (page - 1) * size`, so a page size of three gives an offset of 0, 3, 6, 9 and so on.

```mermaid
flowchart TD
    S["ORDER BY price DESC, name"] --> R0["ranks 1-3<br/>page 1: OFFSET 0"]
    S --> R1["ranks 4-6<br/>page 2: OFFSET 3"]
    S --> R2["ranks 7-9<br/>page 3: OFFSET 6"]
    R0 --> OUT["LIMIT 3 keeps<br/>the page you asked for"]
    R1 --> OUT
    R2 --> OUT
```

Both clauses run on the sorted list, so they only mean something when the sort is complete. `LIMIT 3` with no `ORDER BY` asks for three rows and gives no reason to prefer any three. The result looks fine in a small table, which is why the bug ships.

One more detail in your favour: when a query has both an `ORDER BY` and a `LIMIT`, PostgreSQL can stop early. With an index on `price`, it can walk the index from the expensive end and stop after three rows, instead of sorting all 20. That is a reason to name a real column in `ORDER BY`, and a reason not to wrap it in an expression when a plain column would do.

## Swapping the two numbers returns a different page

Here is the mistake. You know the page size is three and the page number is two. So you write a 3 and a 6, in whichever order came to mind.

```sql
SELECT name, price
FROM products
ORDER BY price DESC, name
LIMIT 6 OFFSET 3;
```

| name | price |
| --- | --- |
| Harbor Rain Shell | 118.00 |
| Summit Hiking Poles | 96.40 |
| Vertex Mechanical Keyboard | 89.50 |
| Linen Duvet Cover | 84.00 |
| Pulse Fitness Tracker | 74.25 |
| Bamboo Shelf | 72.30 |

Six rows. `OFFSET 3` still dropped the top three, so the page starts in the right place, and `LIMIT 6` then hands back two pages instead of one. The first three rows are exactly what page two should contain, which is why the mistake survives a glance at the top of the output.

The difference is what each number counts. `LIMIT` counts rows you receive. `OFFSET` counts rows you never see. Write the offset as a product first, then let the limit be the page size:

```text
OFFSET (2 - 1) * 3  ->  3
LIMIT  3            ->  3
```

## The cost of a deep offset

`OFFSET` has a price. The server still has to produce the rows it is about to throw away, so `OFFSET 6000` sorts and discards 6,000 rows before it returns anything. Page 500 costs 500 pages of work, and a crawler that walks every page pays for the whole list many times.

An experienced developer pages by key instead. Remember the last sort value on the previous page, then ask for the rows strictly past it. Page one ended at `Nimbus Headphones`, 129.00, so page two becomes a filter:

```sql
SELECT name, price
FROM products
WHERE price < 129
ORDER BY price DESC, name
LIMIT 3;
```

| name | price |
| --- | --- |
| Harbor Rain Shell | 118.00 |
| Summit Hiking Poles | 96.40 |
| Vertex Mechanical Keyboard | 89.50 |

The same three rows as `LIMIT 3 OFFSET 3`, from a query that skips nothing. This is called keyset pagination, and with an index on `price` it can seek straight to the boundary.

Two caveats. When the sort keys tie, you have to compare both keys together rather than the first one alone, which is why a real paging key is often a pair. And if a row is inserted while someone pages, both schemes drift; keyset drifts less, because it anchors to a value instead of a count.

`LIMIT` and `OFFSET` remain the shape you will read most in existing code. Learn them first, and recognise keyset paging when you meet it.

## What the exercise asks you to do

The exercise pages the same product list, three per page, price descending, ties broken by name, and asks for page three. Nothing in it is new: you have the sort keys and the page size, and the offset comes from the arithmetic above.

Work out the offset before you touch the keyboard. Write it as `(page - 1) * size`, then check the rows that come back against the sorted list. A paging answer that gets the rows right and the order wrong still passes a careless glance.

## What to remember

What I would do: end every paged `ORDER BY` with a unique key, usually the primary key, and derive the offset from the page number in one place in the code. Keep `LIMIT` and `OFFSET` for the lists you read, and move a list to keyset paging once its page numbers run high. A page boundary is a filter on the last row you saw, not a count of rows you never wanted.

- A table has no order. Without `ORDER BY`, the row order is an accident of the plan and can change between runs.
- `ORDER BY` sorts the rows that survive `WHERE`, and sorts them before `LIMIT` cuts the list.
- A second sort key decides ties. Without it, tied rows have no defined order, and paged results can repeat or skip a row.
- `LIMIT` is the page size. `OFFSET` is `(page - 1) * size`, and page one needs no offset.
- A deep `OFFSET` still produces every skipped row. Keyset paging filters on the last key seen instead.
- `LIMIT` without `ORDER BY` returns any n rows, not the first n.

## Check yourself

**1. What exactly does `LIMIT 3` promise when the query has no `ORDER BY`?**

<details>
<summary>Answer</summary>

It promises three rows at most. Nothing decides which three, so the set depends on the plan and the storage layout. A test that passes today can fail after an unrelated update.

</details>

**2. Why does a sort on `status` need a second key before you page it?**

<details>
<summary>Answer</summary>

Many orders share a status, so the first key leaves those rows tied. Two separate page requests can break the tie group differently, so a row can appear on both pages or on neither. A unique second key pins the order.

</details>

**3. A colleague writes `LIMIT 6 OFFSET 3` for page two of a six-per-page list. How many rows come back, and where does the page start?**

<details>
<summary>Answer</summary>

Six rows, starting at rank 4. With a page size of six, page two should skip the first six rows: `LIMIT 6 OFFSET 6`. `OFFSET 3` skips only half a page, so the result overlaps page one and returns rows 4 to 9. The overlap is the symptom to look for.

</details>

**4. Which is cheaper, `OFFSET 30` on a sorted list or `WHERE price < 129` with a limit, and why?**

<details>
<summary>Answer</summary>

The key filter, usually. The offset version must produce and sort the 30 rows it discards, so its cost grows with how far in you page. The key filter can use an index to seek to the boundary, and its cost stays close to the page size.

</details>

**5. Page two is derived from rank 4 of the sorted list. What makes ranks 4 to 6 a fixed set?**

<details>
<summary>Answer</summary>

A total order. The first key ranks the rows and the second key settles every tie, so each row has one rank. Without the second key, ranks 4 to 6 hold a different set of rows on each run.

</details>
