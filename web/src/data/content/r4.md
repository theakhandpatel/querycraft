# Constraints, foreign keys and `ON CONFLICT`

`order_items` holds 161 rows, and a report that joins it to `orders` counts 160. The extra line points at an order id nobody created, and no statement complained when it was written. The row lands, the statement returns, and the mistake stays invisible until the join drops the line without a word.

A foreign key is the rule that forbids that write: a declaration that a column holds a value which exists in another table's key. The commerce schema declares three of them. The declaration alone enforces nothing, because SQLite checks foreign keys only when the connection asks, and the default is to skip the check.

This chapter reads those declarations, turns the check on, and shows what a refused write looks like. It then covers the two write features you will reach for next: `ON CONFLICT` for an upsert and `RETURNING` for the row you just wrote.

## A row that points at nothing

Start with the write that should not be possible. On a connection with the check off, this statement succeeds:

```sql
INSERT INTO order_items (order_id, product_id, quantity, unit_price)
VALUES (999999, 1, 1, 5.00);
```

No error, no warning. Ask the table what it now holds:

```sql
SELECT (SELECT count(*) FROM order_items) AS lines,
       (SELECT count(*) FROM order_items oi JOIN orders o ON o.id = oi.order_id) AS joined;
```

| lines | joined |
| --- | --- |
| 161 | 160 |

Read the two numbers together. `lines` counts rows in the table: 161, one more than the 160 lines the seed shipped. `joined` asks for the same count through a join to `orders` and gets 160. The extra row exists and no order owns it.

That row is an orphan. It costs storage, it appears in no report that reaches `order_items` through `orders`, and it will never be deleted by anything that cleans up an order.

A total built by joining the two tables is now wrong by one line, and the table that holds the error looks fine.

Nothing was checked, because no rule ran. The schema does declare the rule, and the next two sections show where it lives and what turns it on. If you run that insert in this workspace first, it fails: the app opens the connection with the check on.

## What a declaration says

Open `backend/internal/dataset/schema.sqlite.sql` and read the `order_items` definition. It is the file's own text, so read it rather than run it: the table already exists in the workspace.

```sql
-- The shipped definition, shown for reading; the table already exists.
CREATE TABLE order_items (
    id         INTEGER PRIMARY KEY,
    order_id   INTEGER NOT NULL REFERENCES orders(id),
    product_id INTEGER NOT NULL REFERENCES products(id),
    quantity   INTEGER NOT NULL CHECK (quantity > 0),
    unit_price NUMERIC NOT NULL
);
```

Two of those columns carry `REFERENCES`, and that keyword is the whole declaration. It names a parent table, `orders` or `products`, and in parentheses the parent column, `id`. The table that holds the declaration is the child. So `order_items` is a child of `orders` through `order_id`, and a child of `products` through `product_id`.

The vocabulary pays off later, because the pragmas use it. A foreign key runs from one column in a child table to one column in a parent table. The child column carries the value. The parent column holds the key that value must match.

The declaration is text inside the `CREATE TABLE` statement, so it survives in the catalog. Reading `sql` from `sqlite_master` for `order_items` returns the statement as written, `REFERENCES` and all. That tells you two things. The rule travels with the file, and the file cannot enforce it, because a file has no connection.

The schema declares several kinds of constraint, and two of them do not behave alike. The same definition declares `CHECK (quantity > 0)` on `quantity`. A `CHECK` runs on every connection with no switch to find. A `REFERENCES` runs only when the connection has the check on.

The asymmetry is history: SQLite enforced `CHECK` from early on and added foreign keys in 3.6.19, so enforcement had to be opt-in. Otherwise every existing program that wrote a child row first would break on upgrade.

## The switch follows the connection

One pragma answers whether this connection is checking:

```sql
PRAGMA foreign_keys;
```

| foreign_keys |
| --- |
| 1 |

The number is 1 in this app, because the code that opens the workspace runs `PRAGMA foreign_keys = ON` before it applies the schema. A `sqlite3` shell opened on the same file reports 0, because the setting was never written to the file.

Keep that sentence: a foreign key is declared in the file and enforced by the connection. The pragma is not stored anywhere in the database. It is a flag inside the connection object, true for as long as that handle is open.

A program with ten connections must set it ten times. A pool that replaces handles must set it on each new one. The gateway sets it where it opens the file, which is why its write path cannot forget.

The flag can move only while no transaction is open. On a connection that starts with the check off, run `BEGIN; PRAGMA foreign_keys = ON; COMMIT;` and then read the pragma: it still reports 0. The engine ignores the setting inside a transaction, because turning the check on halfway through would judge writes the transaction had already made. Set the pragma first, then begin.

## What a refusal looks like

With the check on, the same insert from the first section stops:

```sql
INSERT INTO order_items (order_id, product_id, quantity, unit_price)
VALUES (999999, 1, 1, 5.00);
```

```
FOREIGN KEY constraint failed
```

Same file, same statement, different flag. The engine looked up `orders.id` for 999999, found nothing, and refused the row. The message names the kind of constraint and not the column, so read the statement to find the culprit.

A `CHECK` failure is more specific. Send a zero in the `quantity` column and the message names the expression.

```
CHECK constraint failed: quantity > 0
```

Deleting a parent fails in the other direction, and the default is to refuse it:

```sql
DELETE FROM customers WHERE id = 1;
```

```
FOREIGN KEY constraint failed
```

Customer 1 has five orders, so the delete would leave five orphans. The schema declares no `ON DELETE` action, and the engine's default is `NO ACTION`: refuse the delete while a child still points at the parent. `pragma_foreign_key_list` reports that default in its `on_delete` column. `ON DELETE CASCADE` would delete the five orders and their lines instead, which is what a schema says when a child row has no meaning without its parent.

An orphan that arrived while the check was off stays in the file. `PRAGMA foreign_key_check` walks the declared keys and reports every row that fails:

```sql
PRAGMA foreign_key_check;
```

| table | rowid | parent | fkid |
| --- | --- | --- | --- |
| order_items | 161 | orders | 1 |

Four columns: the child table, the rowid of the bad row, the parent table, and the position of the key. An empty result means no orphans. To clear the one above, delete or update that rowid, then run the check again.

In this workspace you can watch both sides. Run `PRAGMA foreign_keys = OFF`, run the insert, and the count query reports 161 lines and 160 joined. Turn the pragma back on and the same insert is refused. Reset the workspace when you are done, and the seed is back.

## The declared keys are rows

The declarations are not only text. A table-valued pragma returns them as rows you can filter, join and sort. That is how you audit a schema instead of reading DDL by eye.

```sql
SELECT "table", "from", "to"
FROM pragma_foreign_key_list('order_items')
ORDER BY id;
```

| table | from | to |
| --- | --- | --- |
| products | product_id | id |
| orders | order_id | id |

`table` is the parent, `from` is the child column, and `to` is the parent column. The three names are reserved words, so they need double quotes wherever they appear. Two rows come back, one per key on `order_items`.

`ORDER BY id` is there because the engine's own row order is not a promise. `id` numbers the keys in declaration order, which is stable, and it is what makes a result table safe to compare with the one in the exercise.

`pragma_index_list` and `pragma_index_info` do the same job for indexes, with the same table-valued shape. The exercise asks for a file-wide audit: every declared key as `child`, `parent`, `child_column` and `parent_column`. The demo above reads one table, so the exercise needs a second argument. `pragma_foreign_key_list(m.name)` takes the table name from the outer row, and a join calls it once per table. This file declares three keys across two tables, so the audit returns three rows. Reading them in one list is the quickest way to see a child table with a parent nobody expected.

## The upsert: `ON CONFLICT DO UPDATE`

`dataset_meta` holds one row per dataset, keyed by `dataset`. Try to write the same dataset twice:

```sql
INSERT INTO dataset_meta (dataset, version) VALUES ('commerce', 2);
```

```
UNIQUE constraint failed: dataset_meta.dataset
```

The primary key refuses it, because `commerce` is already there at version 1. A program that wants to record version 2 has to update the row instead. The obvious way to write that is a `SELECT` to see whether the row exists, then an `INSERT` or an `UPDATE` depending on the answer. That is two statements, with a window between them where another writer can insert the same key and make your `INSERT` fail.

`ON CONFLICT` decides inside one statement:

```sql
INSERT INTO dataset_meta (dataset, version)
VALUES ('commerce', 2)
ON CONFLICT (dataset) DO UPDATE SET version = excluded.version;
```

| dataset | version |
| --- | --- |
| commerce | 2 |

The insert found the row, so it took the `DO UPDATE` branch and set `version` from `excluded.version`. `excluded` is the pseudo-table holding the rows you tried to insert, so `excluded.version` is the 2 you passed in. The check and the change happen with the write lock held, so nothing slips between them. That is the argument for the single statement, and the shape has a name: an upsert.

`ON CONFLICT (dataset)` names the unique index that decides the conflict. Name it. A bare `ON CONFLICT` catches every uniqueness violation on the table, including one you did not consider, and turns a real bug into a silent update.

`DO NOTHING` is the other branch. It leaves the existing row alone and reports no error, which is what you want when the row's presence is all that matters. With `RETURNING` it also returns no rows, and an empty result is the signal that the row was already there.

Try this: swap `DO UPDATE SET version = excluded.version` for `DO NOTHING` and run the statement again. It reports no error, and the row keeps the version it already had. Add `RETURNING version` and the answer is empty, which is how the clause tells you the row was already there.

This statement writes, so run it in the workspace. A copy of the file opened read-only answers `attempt to write a readonly database`, which is the limit chapter 1 covered, not a problem with the clause.

## `RETURNING` and the last rowid

An insert often needs the row back, and the id is the part you did not supply. A scratch table gives you somewhere to practise without touching the seed:

```sql
CREATE TABLE customers_scratch (
    id          INTEGER PRIMARY KEY,
    name        TEXT    NOT NULL,
    signup_date DATE    NOT NULL
);
```

`RETURNING` turns the insert into a statement that answers:

```sql
INSERT INTO customers_scratch (name, signup_date)
VALUES ('Ada Junior', '2026-02-01'), ('Bruno Junior', '2026-02-02')
RETURNING id, name;
```

| id | name |
| --- | --- |
| 1 | Ada Junior |
| 2 | Bruno Junior |

Neither id was in the insert, and both came back. The primary key took the next rowid for each row, and `RETURNING` reported the row as stored. One statement, no follow-up `SELECT` that another writer could interleave with.

The older mechanism is `last_insert_rowid()`, a function that reports the rowid of the most recent successful insert on the connection:

```sql
SELECT last_insert_rowid() AS last_rowid;
```

| last_rowid |
| --- |
| 2 |

The statement wrote two rows, and the function reports one. Compare that with the `RETURNING` table above, which reported both. That is the first difference.

The second is scope. `last_insert_rowid()` answers for the connection, not for your statement. An insert that fires a trigger, which inserts into another table, leaves the function pointing at the trigger's row. `RETURNING` reports the rows your statement wrote and nothing else. On any version from 3.35 on, prefer it.

## What to remember

**What I would do:** set `PRAGMA foreign_keys = ON` where the connection opens, before any transaction begins, and set it again on every handle a pool creates. Name the conflict target in every upsert, so a unique index you did not consider cannot turn into a silent update. Take ids from `RETURNING`, not from `last_insert_rowid()`. When a total comes back short by a row, run `PRAGMA foreign_key_check` before you edit the report.

- A foreign key is declared in the file and enforced by the connection. The file cannot check anything.
- `PRAGMA foreign_keys` is off by default on a new connection. Set it where the connection opens, before any transaction begins.
- With the check on, a child row without a parent fails with `FOREIGN KEY constraint failed`, and so does deleting a parent under the default `NO ACTION`.
- A `CHECK` constraint runs on every connection. No pragma turns it off.
- `ON CONFLICT (key) DO UPDATE SET column = excluded.column` is an upsert in one statement, with no window between the check and the write.
- `RETURNING` reports every row the statement wrote. `last_insert_rowid()` reports one rowid for the whole connection, and a trigger can move it.

## Check yourself

**1. A table declares a foreign key and a `CHECK`. Which one rejects a bad row on a connection that never ran a pragma?**

<details>
<summary>Answer</summary>

The `CHECK`. It is enforced on every connection. The foreign key needs `PRAGMA foreign_keys = ON`, and the default is off, so the reference is declared and inert until something turns it on.

</details>

**2. A report counts 160 lines in `order_items`, but the table holds 161 rows. What explains the gap, and which pragma finds the extra row?**

<details>
<summary>Answer</summary>

The report joins `order_items` to `orders`, and one line points at an order id that does not exist. The join drops it, so the total is short by one row. `PRAGMA foreign_key_check` reports the child table, the rowid and the parent table for each such row.

</details>

**3. Why is `ON CONFLICT (dataset) DO UPDATE` better than two statements?**

<details>
<summary>Answer</summary>

It checks for the conflict and writes under one lock, so nothing can insert the same key between the two steps. The two-statement version has that window, and its `INSERT` can fail with `UNIQUE constraint failed` for a reason that has nothing to do with the data.

</details>

**4. An `INSERT` writes two rows and you need both ids. Which mechanism reports them?**

<details>
<summary>Answer</summary>

`RETURNING id` reports every row the statement wrote, so both ids come back in one result. `last_insert_rowid()` reports the connection's most recent insert, which is the second row only, and a trigger can move it further.

</details>

**5. On a connection that starts with the check off, `BEGIN; PRAGMA foreign_keys = ON; COMMIT;` runs without an error, and the next insert still writes an orphan. Why?**

<details>
<summary>Answer</summary>

The engine ignores `PRAGMA foreign_keys` inside a transaction, so the flag never changed. Set the pragma before `BEGIN`, then check it with `PRAGMA foreign_keys` to confirm the value is 1 on that connection.

</details>
