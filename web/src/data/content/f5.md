# IN, BETWEEN and LIKE

The search box came back empty. The customer typed `camp` in lowercase, and the two products with Camp in the name never appeared. In the same week, the catalogue team asked for every Home or Kitchen product priced from 20 to 90, cheapest first.

Both requests fit in a `WHERE` clause, and you could spell the list and the range with comparisons joined by `OR`. PostgreSQL offers three shorter forms. `IN` tests a value against a list, `BETWEEN` tests it against a range, and `LIKE` tests text against a pattern. Each form names the shape of the test, so the next reader spends less time rebuilding your sentence.

Each form also carries one trap: a `NULL` inside a list, a date at the end of a range, and a capital letter. Get the first wrong and the query returns no rows. Get the second wrong and a day of orders goes missing with no error. Get the third wrong and the search box shows nothing.

## `IN` is a list of equality tests

```sql
SELECT name, category
FROM products
WHERE category IN ('Home', 'Kitchen')
ORDER BY name;
```

| name | category |
| --- | --- |
| Bamboo Shelf | Home |
| Cedar Desk Lamp | Home |
| Ceramic Vase | Home |
| Copper Kettle | Kitchen |
| Espresso Tamper | Kitchen |
| Granite Cookware Set | Kitchen |
| Linen Duvet Cover | Home |
| Maple Cutting Board | Kitchen |
| Wool Throw Blanket | Home |

`category IN ('Home', 'Kitchen')` means `category = 'Home' OR category = 'Kitchen'`. Both forms keep the same nine rows, and the shorter one scales. Ten values make a single predicate line instead of ten comparisons wrapped in brackets, and the brackets are usually where a mixed `AND`/`OR` mistake starts.

A misplaced bracket costs rows, not an error message: the query runs and returns a table, and only the count shows that the list did not do its job.

Read the predicate one row at a time. For each product, `category = 'Home'` and `category = 'Kitchen'` are two tests joined by `OR`. Five Home products answer true to the first test. Four Kitchen products answer true to the second.

The other eleven products answer false to both and never reach the result. The count is the check: five plus four is nine, and the table has nine rows.

The nine rows are five Home and four Kitchen products. Electronics and Outdoor fail both equality tests, so the other 11 products are dropped. `NOT IN` negates the whole list in the same way `<>` negates one value.

`IN` is not a speed trick; the plan decides whether a list becomes comparisons or a lookup. Reach for it because it reads like the request, and because a list is easier to extend than a chain of `OR`s.

## A `NULL` in a `NOT IN` list erases the result

Chapter 4 gave you three-valued logic: a comparison with an unknown is unknown, and `WHERE` keeps only true rows. `IN` inherits that rule, and the negation is where it hurts. `city NOT IN ('Leeds', NULL)` expands to `city <> 'Leeds' AND city <> NULL`.

Take a customer in Milan. The first half is true, the second half is unknown, and an `AND` with one unknown side is unknown.

Take a customer with no city. Both halves are unknown, so the result is unknown again. No row can pass.

```sql
SELECT count(*) AS rows_returned
FROM customers
WHERE city NOT IN ('Leeds', NULL);
```

| rows_returned |
| --- |
| 0 |

Drop the null and the same filter counts 23 rows, which is the `<>` count from chapter 4.

```sql
SELECT count(*) AS rows_returned
FROM customers
WHERE city NOT IN ('Leeds');
```

| rows_returned |
| --- |
| 23 |

A literal null in a hand-written list is usually a typo. The dangerous version arrives from a subquery or a join later in the course, where the null is invisible in the query text. Know what the list contains before you negate it.

The positive form has the same gap, smaller. `city IN ('Leeds')` returns 3 rows, because the four unknown cities match nothing. Adding a null to the list changes neither the count nor the reason.

Try this: cut the list to a single null, `city NOT IN (NULL)`, and run it. The count is still 0, because every row now compares against an unknown. One null is enough, so the city values never get a say.

## `BETWEEN` is inclusive at both ends

```sql
SELECT name, price
FROM products
WHERE price BETWEEN 20 AND 90
ORDER BY price;
```

Twelve of the twenty products fall in that range. To see how each boundary behaved, line up the products just outside and just inside each end.

| product | price | `price BETWEEN 20 AND 90` |
| --- | --- | --- |
| Espresso Tamper | 19.99 | false |
| Maple Cutting Board | 24.00 | true |
| Vertex Mechanical Keyboard | 89.50 | true |
| Summit Hiking Poles | 96.40 | false |

`BETWEEN 20 AND 90` means `price >= 20 AND price <= 90`. Read it as "at least 20 and at most 90", which needs no memory of which end is open. Espresso Tamper misses the lower bound by one cent. Summit Hiking Poles misses the upper bound by more than six.

No product costs exactly 20 or 90, so this data cannot show you that both ends are included. A range with equal ends can:

```sql
SELECT count(*) AS rows_returned
FROM products
WHERE price BETWEEN 89.50 AND 89.50;
```

| rows_returned |
| --- |
| 1 |

Only Vertex Mechanical Keyboard costs 89.50, and it matches a range whose two ends are the same number. An exclusive range would return no rows.

Reverse the bounds and `BETWEEN` matches nothing rather than raising an error, because `price >= 90 AND price <= 20` can never be true: `price BETWEEN 90 AND 20` returns 0 rows. A null in the column would make the comparison unknown, so `BETWEEN` would drop that row, exactly as `<>` did in chapter 4. This column is `NOT NULL`, so the rule is general rather than a case you can see here.

## A date range needs a half-open test

Now the trap. The orders team wants every order placed from 1 January 2026 to 19 January 2026, both days included. The obvious query:

```sql
SELECT count(*) AS january_orders
FROM orders
WHERE ordered_at BETWEEN '2026-01-01' AND '2026-01-19';
```

| january_orders |
| --- |
| 7 |

The half-open version counts one more:

```sql
SELECT count(*) AS january_orders
FROM orders
WHERE ordered_at >= '2026-01-01'
  AND ordered_at < '2026-01-20';
```

| january_orders |
| --- |
| 8 |

The missing row is order 1002, placed at 16:40 on 19 January. `ordered_at` is a `timestamp`, and the literal `'2026-01-19'` is a date, which PostgreSQL converts to `2026-01-19 00:00:00`. The `BETWEEN` upper bound therefore covers the first instant of the 19th and nothing after it.

The fix is to stop treating the upper bound as a day. Write the start of the next day and exclude it with `<`. A row at midnight on the 20th then belongs to the next range, so no instant is lost or counted twice.

```sql
SELECT count(*) AS february_orders
FROM orders
WHERE ordered_at >= '2026-02-01'
  AND ordered_at < '2026-03-01';
```

| february_orders |
| --- |
| 19 |

That is the February count, and the same shape works for a week, a quarter or a year: include the start, exclude the next start.

The mistake survives review because the wrong query often counts correctly. Run `ordered_at BETWEEN '2026-01-01' AND '2026-01-31'` and you get 16 orders, the same as `ordered_at >= '2026-01-01' AND ordered_at < '2026-02-01'`, because no January order landed after midnight on the 31st.

A right number from a fragile predicate is the hardest kind of bug to catch. The rule follows from the type: a `date` column has no time part, so `BETWEEN` on a `date` is exact, and a `timestamp` needs the exclusive upper bound.

## `LIKE` matches a pattern and `ILIKE` ignores case

`LIKE` compares text against a pattern. Two characters carry meaning inside the pattern. `%` stands for any run of characters, including no characters at all. `_` stands for exactly one character. Everything else has to match, and the comparison is case-sensitive.

```sql
SELECT name, category
FROM products
WHERE name LIKE 'C%'
   OR name LIKE 'S%'
ORDER BY name;
```

| name | category |
| --- | --- |
| Cedar Desk Lamp | Home |
| Ceramic Vase | Home |
| Copper Kettle | Kitchen |
| Solar Camp Lantern | Outdoor |
| Summit Hiking Poles | Outdoor |

`'C%'` means a capital C followed by anything, which is a prefix search. Put `%` on both sides and you get a contains search. The `_` form is the one people misread, so here is each pattern with its match count in `products`.

| pattern | reads as | matches |
| --- | --- | --- |
| `'C%'` | starts with a capital C | 3 products |
| `'%Kettle%'` | contains Kettle | 1 product |
| `'%Camp%'` | contains Camp | 2 products |
| `'%_ase'` | any run, then one character, then ase | 1 product |

```sql
SELECT name
FROM products
WHERE name LIKE 'C_____ Kettle';
```

| name |
| --- |
| Copper Kettle |

The pattern is a capital C, five single characters, a space, then the word Kettle. Copper Kettle fits. Change the run to three placeholders and the same query returns 0 rows, which is how you learn that `_` counts one character and never stands for a run.

`LIKE` tests the whole value, so a pattern has to account for every character in it. `'%_ase'` reads as any run of characters, then one character, then `ase`, and it matches Ceramic Vase through its V. The pattern `'_ase'` would need a name of exactly four characters, so it returns 0 rows.

Now the search box from the opening. The customer typed `camp`, and the application wrapped the word as a contains pattern and passed it through unchanged:

```sql
SELECT count(*) AS rows_returned
FROM products
WHERE name LIKE '%camp%';
```

| rows_returned |
| --- |
| 0 |

No row matches, because the stored names capitalise Camp and `LIKE` compares characters exactly. One letter's case hides two products. `ILIKE` is the case-insensitive version:

```sql
SELECT name
FROM products
WHERE name ILIKE '%camp%'
ORDER BY name;
```

| name |
| --- |
| Discontinued Camp Stove |
| Solar Camp Lantern |

Two rows, which is the answer support wanted.

`ILIKE` is a PostgreSQL extension, so a query written for another database usually spells the same idea as `LOWER(name) LIKE LOWER('%camp%')`. Reach for `ILIKE` when the pattern comes from a person, and keep `LIKE` when case is part of the meaning, such as a product code or a two-letter country field.

## A leading wildcard costs a scan

A pattern's shape decides how much work the database does. `'C%'` fixes the first character, so PostgreSQL can jump to the start of the `C` range in an ordered index and stop at the end of it. A prefix pattern can use a btree index with `text_pattern_ops`, and a trigram index serves it too.

`'%Kettle%'` fixes nothing at the start. Any row could match, so the engine reads each row, runs the pattern against it, and keeps the matches. On 20 products you cannot measure it. On millions of rows it is the difference between a few index pages and the whole table.

A prefix or an exact pattern keeps the search cheap. A leading `%` buys flexibility and pays for it with a scan, and a contains search on a large table is a job for a trigram index or a full-text search column, both later in the course.

## What the exercise asks you to do

The exercise asks for the name and price of every Home or Kitchen product priced between 20 and 90 inclusive, cheapest first, with ties broken by name. It is the catalogue request from the opening. You have the list form for the categories, the range form for the price, and a sort that needs two keys because prices can repeat.

Two checks catch a wrong answer. Seven rows should come back. And Espresso Tamper, a Kitchen product at 19.99, must be absent: the category list keeps it and the price range drops it, which is how you know the range is doing its job.

## What to remember

**What I would do:** spell the list with `IN` and every timestamp range with `>= start AND < next_start`. Never negate a list that might hold a `NULL`, because one unknown turns the whole filter into zero rows. Send a person's search pattern through `ILIKE`, and read the plan before you rely on a leading `%` over millions of rows.

- `IN` tests a value against a list. `x IN (a, b)` means `x = a OR x = b`.
- A `NULL` in a `NOT IN` list returns no rows at all: `city NOT IN ('Leeds', NULL)` is unknown for every row. A `NULL` in a positive `IN` list changes nothing, because a true match still wins.
- `BETWEEN a AND b` is inclusive at both ends, and reversed bounds match nothing instead of raising an error.
- A timestamp range needs `>= start AND < next_start`. `BETWEEN` on a timestamp drops every row after midnight on the last day.
- `LIKE` matches `%` for any run and `_` for one character, and it is case-sensitive. `ILIKE` ignores case.
- A pattern with a leading `%` has no starting point, so it scans the table instead of seeking in an index.

## Check yourself

**1. You need every product priced from 20 up to but not including 90. Write the predicate two ways, and say which one you would keep.**

<details>
<summary>Answer</summary>

`price >= 20 AND price < 90`, or `price BETWEEN 20 AND 89.99`. Keep the explicit comparison, because it states both boundaries in the same units as the column and does not depend on remembering which end `BETWEEN` includes. Both return 12 rows on this data, since no product costs between 89.99 and 90.

</details>

**2. Why does `WHERE city NOT IN ('Leeds', NULL)` return no rows at all, rather than the 23 rows outside Leeds?**

<details>
<summary>Answer</summary>

`NOT IN` expands to `city <> 'Leeds' AND city <> NULL`. Every row has an unknown on at least one side, so the `AND` is unknown whether the city is known or null. `WHERE` keeps only true rows. Remove the null, or test with `IS DISTINCT FROM`.

</details>

**3. `ordered_at BETWEEN '2026-01-01' AND '2026-01-19'` counts 7 orders, and the half-open version counts 8. Which order is missing, and what would change if `ordered_at` were a `date`?**

<details>
<summary>Answer</summary>

Order 1002, placed at 16:40 on 19 January. The upper bound became midnight, so every later instant on that day fell outside. A `date` column has no time part, so the same `BETWEEN` would cover the whole day and the two counts would agree.

</details>

**4. A colleague writes `name LIKE 'c%'` and gets no rows, though the table contains Copper Kettle. What went wrong, and what are two fixes?**

<details>
<summary>Answer</summary>

`LIKE` is case-sensitive, so a lowercase c matches nothing. Use `name ILIKE 'c%'`, or lower both sides with `LOWER(name) LIKE 'c%'`.

</details>

**5. Why can `name LIKE 'C%'` use an index while `name LIKE '%Kettle%'` cannot use one for its search?**

<details>
<summary>Answer</summary>

A prefix fixes the first character. The index then has a known range to seek into and a known place to stop. The leading wildcard fixes nothing, so any row could match and the engine has to test each one.

</details>
