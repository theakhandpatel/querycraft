# Reading a query plan

## Three commands, three jobs

SQLite has three commands people confuse.

| Command | What it gives you |
| --- | --- |
| `EXPLAIN` | the virtual machine bytecode: opcodes, registers, jumps |
| `EXPLAIN QUERY PLAN` | the plan: scans, index searches, loop order |
| `ANALYZE` | statistics in `sqlite_stat1`, with no plan output |

Read `EXPLAIN QUERY PLAN`. The bytecode is the engine's lowest level and almost never the answer. `ANALYZE` does not answer a question about your query; it gives the planner better numbers for the next one.

SQLite has no `EXPLAIN ANALYZE`. It cannot report measured rows per node, so a plan is an intention, not a measurement. This app does not grade a plan for that reason.

## What the plan says

`EXPLAIN QUERY PLAN` returns rows. The `detail` column has one line per loop. `SCAN` visits every row; `SEARCH` seeks into an index. `USING COVERING INDEX` means the index alone answers the query; plain `USING INDEX` follows the index back to the table.

```sql
EXPLAIN QUERY PLAN
SELECT id FROM orders WHERE status = 'refunded';
```

| id | parent | notused | detail |
| --- | --- | --- | --- |
| 2 | 0 | 55 | SEARCH orders USING COVERING INDEX orders_status_idx (status=?) |

One line: an equality on `status` becomes an index search. The query asks only for `id`, which is the rowid, and every index entry carries the rowid, so the index alone is enough.

A join shows one line per loop:

```sql
EXPLAIN QUERY PLAN
SELECT o.id
FROM orders o
JOIN order_items oi ON oi.order_id = o.id
WHERE o.customer_id = 1;
```

| id | parent | notused | detail |
| --- | --- | --- | --- |
| 3 | 0 | 53 | SEARCH o USING COVERING INDEX orders_customer_id_idx (customer_id=?) |
| 7 | 0 | 54 | SEARCH oi USING COVERING INDEX order_items_order_id_idx (order_id=?) |

Read top to bottom as the loop order: find the customer's orders, then find each order's lines.

A `SCAN` where you expected a `SEARCH` usually means the predicate hides the column from the index. `WHERE date(ordered_at) = '2026-01-04'` computes a value per row, so the index on `ordered_at` cannot help. A range on the bare column can:

```sql
WHERE ordered_at >= '2026-01-04'
  AND ordered_at < '2026-01-05'
```

## Analyze is not a plan

`ANALYZE` surveys the tables and writes what it finds into `sqlite_stat1`. It produces no result rows. It changes the next plan by giving the planner better counts. Run it after a bulk load, then leave it alone.

What you lose compared with PostgreSQL is the feedback loop. There is no estimate next to a measured count, so you cannot say "the plan was wrong by two orders of magnitude." You can say "the plan scans, and I expected a search." That is enough to answer the question this chapter cares about: is my index being used, and if not, which predicate is hiding it?

## Check yourself

**1. What is the difference between `EXPLAIN` and `EXPLAIN QUERY PLAN`?**

<details>
<summary>Answer</summary>

`EXPLAIN` prints the bytecode program: opcodes and jump targets. `EXPLAIN QUERY PLAN` prints the readable plan: scans, index searches, and loop nesting.

</details>

**2. What does `SEARCH orders USING COVERING INDEX` mean, versus `USING INDEX`?**

<details>
<summary>Answer</summary>

Both are index seeks. Covering means the index holds every column the query needs, so SQLite never visits the table. Plain `USING INDEX` follows the index back to the table for other columns.

</details>

**3. Why can `WHERE date(ordered_at) = '2026-01-04'` cause a scan?**

<details>
<summary>Answer</summary>

The index is on `ordered_at`, but the predicate is on `date(ordered_at)`, which SQLite has to compute per row. It cannot use the index on the column for a value it has not computed.

</details>
