# Set operations: UNION, INTERSECT, EXCEPT

The retention team asked for one customer list and got 47 rows for 21 customers. The filter was the obvious one, `WHERE status IN ('completed', 'pending')`, and it answers a different question: one row per order, not one row per customer.

A join between the two lists does no better. It pairs each completed order with each pending order for the same customer and returns 15 pairs, one for every customer who has both. You already know how to get the two lists separately. Combining them without pairing or multiplying is the new problem.

This chapter covers the four operators that stack lists, the column shape they insist on, and the difference between asking whether a row appears and asking how often.

## Stacking rows is not joining tables

A join answers a matching question. It takes a row from each side, pairs them by a condition, and returns both rows' columns side by side. The result is wider than either input, and a one-to-many relationship multiplies the rows.

A set operation answers a membership question. It takes two result sets that already have the same shape, compares whole rows, and returns one result set holding rows from one input, the other, or both. The result is never wider. It can be shorter than either input, or longer than either one.

Ada Whitfield has five orders. Join her orders to her orders and the engine pairs each of the five with each of the five, so one customer with five orders becomes 25 rows.

```sql
SELECT o1.id AS left_id, o2.id AS right_id
FROM orders o1
JOIN orders o2 ON o2.customer_id = o1.customer_id
WHERE o1.customer_id = 1
ORDER BY left_id, right_id
LIMIT 4;
```

| left_id | right_id |
| --- | --- |
| 1001 | 1001 |
| 1001 | 1002 |
| 1001 | 1005 |
| 1001 | 1006 |

Twenty-five pairs in total, and not one of them is a new fact. The join is doing exactly what it should. The query asked the wrong question, which is how most join mistakes start.

That multiplication is the cost. A `count(*)` over those 25 rows reports 25 orders for a customer who placed five, and nothing in the result flags the difference.

What you want here is a list of customer ids, each appearing once, drawn from two separate lists of customer ids. Nothing gets paired, so nothing multiplies. That is the shape a set operation produces.

## Both sides must line up

The inputs are matched by position, not by name. The first column of the first `SELECT` is compared with the first column of the second, the second with the second, and so on. PostgreSQL resolves each position to a common type, so the two sides must have the same number of columns, in the same order, with types that can be compared.

```sql
SELECT customer_id FROM orders WHERE status = 'completed'
UNION
SELECT customer_id FROM orders WHERE status = 'pending';
```

Two one-column lists of integers, so the statement runs. Give the second side a second column and PostgreSQL refuses the statement with `each UNION query must have the same number of columns`. The error is worth recognising, because it names the rule rather than the typo.

Column names come from the first `SELECT`. The second `SELECT` can call its column anything, and the result will still carry the first one's name, which is why aliasing the second side is wasted effort.

A trailing `ORDER BY` belongs to the whole compound statement, not to either input. It runs once, on the stacked result, and it can only name the output columns of the first `SELECT`, or refer to their positions. Sorting the first input on its own would need brackets and a subquery, which is rarely what you want.

Precedence is the last shared rule. In PostgreSQL, `INTERSECT` binds tighter than `UNION` and `EXCEPT`, and `UNION` and `EXCEPT` associate left to right. When one statement mixes them, add parentheses. The brackets cost two characters and save the next reader a parse.

## UNION merges lists, UNION ALL keeps copies

`UNION` returns the rows of both inputs with duplicates removed. `UNION ALL` returns every row from both inputs, duplicates included, so its row count is always the sum of the two inputs.

The two customer lists show the gap. The completed list draws on 37 orders, and the pending list on 10.

```sql
SELECT count(*) AS union_rows
FROM (
    SELECT customer_id FROM orders WHERE status = 'completed'
    UNION
    SELECT customer_id FROM orders WHERE status = 'pending'
) AS either;
```

| union_rows |
| --- |
| 21 |

```sql
SELECT count(*) AS union_all_rows
FROM (
    SELECT customer_id FROM orders WHERE status = 'completed'
    UNION ALL
    SELECT customer_id FROM orders WHERE status = 'pending'
) AS either;
```

| union_all_rows |
| --- |
| 47 |

Twenty-one ids against 47 rows, from the same pair of inputs. Nineteen distinct customers have a completed order and ten have a pending one, and eight customers have both, which is why the merged list holds 21 names rather than 29.

The `UNION ALL` version keeps one row per order, so those eight customers appear twice and several others appear three or four times.

Both answers are correct, and they answer different questions. The report wants a set of customers, so the de-duplicated form is the one to send.

Removing duplicates costs work. PostgreSQL has to sort or hash the combined rows to spot the repeats, and that pass grows with the number of rows. `UNION ALL` skips it because it never asks the question.

When the inputs cannot overlap, such as two filters on mutually exclusive statuses of the same id column, `UNION ALL` says what you mean and costs less.

One detail about nulls: set operations treat `NULL`s as equal for the purpose of comparison. Two rows that match in every column, including columns that are null on both sides, count as duplicates under `UNION`. That is a deliberate exception to three-valued logic, and it is what makes stacking rows predictable.

## INTERSECT keeps the rows both lists share

`INTERSECT` returns only the rows that appear in both inputs. The two category lists make the point, because they are small enough to check by hand.

```sql
SELECT category FROM products WHERE active
INTERSECT
SELECT category FROM products WHERE NOT active;
```

| category |
| --- |
| Outdoor |

The first input holds 19 rows across four categories. The second holds one row, `Outdoor`, from the discontinued camp stove. Only that category appears on both sides, so it is the whole answer.

Read the query as "categories that hold both an active product and a discontinued one". Notice that the first input repeats `Outdoor` five times and still contributes one row. `INTERSECT` de-duplicates, so multiplicity in the inputs does not leak into the result.

## EXCEPT subtracts one list from another

`EXCEPT` returns the rows of the first input that do not appear in the second. It is a subtraction, and the order of the two inputs matters in a way that `UNION` and `INTERSECT` do not.

```sql
SELECT category FROM products WHERE active
EXCEPT
SELECT category FROM products WHERE NOT active
ORDER BY category;
```

| category |
| --- |
| Electronics |
| Home |
| Kitchen |

Three rows, and Outdoor is missing. Outdoor sits on both sides, so the subtraction removes it and leaves the three categories that hold only active products. Swap the inputs and you get an empty result: the inactive list holds only `Outdoor`, and that row is present in the active list too.

The mechanism is a comparison of whole rows. For each row of the first input, PostgreSQL checks whether an identical row appears in the second, and keeps the row when none does. Because the comparison covers every column, EXCEPT needs the shapes to match. That constraint is also a discipline: it forces you to say which values identify a row before you compare two lists.

## The ALL forms count copies

The plain operators answer "does this row appear". The `ALL` variants answer "how many copies are there", which is the arithmetic of bags. A bag, sometimes called a multiset, is a collection where order does not matter and repeats do count.

`INTERSECT ALL` emits a row `min(m, n)` times, where `m` and `n` are its counts in the two inputs. `EXCEPT ALL` emits it `max(m - n, 0)` times. Both keep multiplicity, so the result length depends on the counts and not only on membership.

Take the same pair of category lists. Active products hold Electronics 5, Home 5, Kitchen 4 and Outdoor 5. Inactive products hold Outdoor once. All six statements run against those two inputs:

| statement | rows | where they come from |
| --- | --- | --- |
| `UNION` | 4 | each category once |
| `UNION ALL` | 20 | 19 active rows plus 1 inactive row |
| `INTERSECT` | 1 | Outdoor |
| `INTERSECT ALL` | 1 | `min(5, 1)` copies of Outdoor |
| `EXCEPT` | 3 | Electronics, Home, Kitchen |
| `EXCEPT ALL` | 18 | 4 Outdoor copies, plus Electronics 5, Home 5 and Kitchen 4 |

Automatic de-duplication drops information that some questions need. A stock report sometimes asks how many more active products than discontinued ones a category holds. That question needs `EXCEPT ALL`, because the plain form throws the counts away and answers with a yes or a no.

Try this: run the category `INTERSECT` pair again with `INTERSECT ALL`. Both queries return one row, because the inactive side holds a single Outdoor and `min(5, 1)` is 1. The `ALL` forms only move the count when both sides hold more than one copy.

## The exercise subtracts the sold list

The exercise asks which customers have never placed an order. A smaller version of the same subtraction is easier to check first. Start with the Home products, and look for any that never sold.

```sql
SELECT name FROM products WHERE category = 'Home'
EXCEPT
SELECT p.name
FROM products p
JOIN order_items oi ON oi.product_id = p.id
ORDER BY name;
```

The result holds the column `name` and no rows. That is a correct answer, not a failure. Order lines exist for all five Home products: Linen Duvet Cover appears on 9 lines, and Cedar Desk Lamp, Bamboo Shelf, Ceramic Vase and Wool Throw Blanket on 8 each. Nothing is left after the subtraction, so an empty result is the report's real content: every Home product sells.

Drop the category filter and the subtractor becomes every product that has at least one order line. One row survives.

```sql
SELECT name FROM products
EXCEPT
SELECT p.name
FROM products p
JOIN order_items oi ON oi.product_id = p.id
ORDER BY name;
```

| name |
| --- |
| Discontinued Camp Stove |

The camp stove costs 0.00, holds no stock and is marked inactive, and no order line references it. It is the only product in that position, which makes it the one row the query returns.

An empty result is worth printing rather than treating as an error. Zero rows when you expected rows tells you something about the data. Zero rows when the data says zero is the answer.

The exercise moves from products to customers. It wants the name of every customer who has never placed an order, alphabetically, and chapter 3 produced the same seven names with `NOT EXISTS`.

The shape follows the Home example. The first input is every customer name. The second input is every customer name that reaches an order, which needs a join to `orders`. `EXCEPT` subtracts the second list from the first, and the names that never ordered are what remain.

Two details decide whether it passes. Both sides must return one text column in the same position, so the join side selects the name rather than the whole row. And names are compared as values, so a duplicated name on either side counts once after the subtraction.

The seven names are the same ones chapter 3 listed, because the question has one answer. They differ in what they say about `NULL`: `EXCEPT` compares whole rows, while `NOT EXISTS` tests each outer row and keeps it when nothing matches.

## What to remember

**What I would do:** write the question as one row per entity before you pick an operator, then check that both inputs return that row. Use `UNION ALL` when the two lists cannot overlap, and `EXCEPT` when the answer is a subtraction. When the result carries a count, reach for the `ALL` form, because the plain operators throw multiplicity away.

- A join pairs rows and widens the result. A set operation stacks rows and never adds columns.
- Inputs must have the same column count, in the same order, with comparable types. Names come from the first `SELECT`.
- A trailing `ORDER BY` sorts the whole compound result and names only the first `SELECT`'s output columns.
- `UNION` removes duplicates and `UNION ALL` keeps them. `UNION ALL` is cheaper and is the right default when the inputs cannot overlap.
- `INTERSECT` keeps rows present in both inputs. `EXCEPT` keeps rows of the first input that the second lacks, and the input order matters.
- The `ALL` variants keep multiplicity: `min(m, n)` for `INTERSECT ALL`, `max(m - n, 0)` for `EXCEPT ALL`.

## Check yourself

**1. Ada has five orders. Why does joining `orders` to `orders` on her customer id return 25 rows when only five orders exist?**

<details>
<summary>Answer</summary>

The join pairs every order with every other order. Five rows on each side give 5 × 5 = 25 pairs, and each pair repeats two ids you already had. A set operation combines lists of rows, so it adds lengths instead of multiplying them.

</details>

**2. The completed and pending customer lists contain 19 and 10 distinct customers, yet `UNION` returns 21 rows. Where did the other eight go?**

<details>
<summary>Answer</summary>

Eight customers have both a completed order and a pending one. `UNION` removes duplicate rows, so each of those customers appears once instead of twice. Nineteen plus ten is 29, minus the 8 repeats gives 21.

</details>

**3. Why does the category `EXCEPT` return three rows when the second input holds one row?**

<details>
<summary>Answer</summary>

`EXCEPT` removes rows from the first input that also appear in the second. The second input holds Outdoor, so only Outdoor is removed from the four active categories. The remaining three never appear on the inactive side.

</details>

**4. When is `EXCEPT ALL` the right choice over plain `EXCEPT`?**

<details>
<summary>Answer</summary>

When the counts carry meaning. Plain `EXCEPT` keeps a row once if it is absent from the second input, so it cannot say how many spare copies exist. `EXCEPT ALL` emits `max(m - n, 0)` copies, which is what a report about quantities needs.

</details>

**5. The Home `EXCEPT` returns no rows. How would you tell an empty correct answer from a broken query?**

<details>
<summary>Answer</summary>

Run each input on its own. The second returns five Home product names, so both sides hold data and the empty result follows from the comparison. An empty first input would produce the same visible output, and that is the case worth catching.

</details>
