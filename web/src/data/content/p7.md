# Making a predicate sargable

An index is only useful if the predicate gives it something to seek with. "Sargable" — from *Search ARGument able* — describes a predicate shaped so that an index can bound it. Most slow queries that look indexed and are not are one wrapped column away from using an index that already exists.

## The shape the index needs

A B-tree is ordered by a column. It can seek to a value, walk a range, and stop at the first match. It can do that only when one side of the comparison is the bare column and the other is a constant or a parameter:

```sql
WHERE customer_id = 7                          -- sargable
WHERE customer_id IN (7, 8, 9)                 -- sargable
WHERE ordered_at >= '2026-03-01'
  AND ordered_at <  '2026-04-01'               -- sargable
WHERE UPPER(status) = 'REFUNDED'               -- not: which key would the index seek?
WHERE customer_id::text = '7'                  -- not: the comparison is on a cast, not the column
```

The rule generalises: any expression sitting between the index and the column hides the column from the planner. The index is still there, the predicate is still correct, and the plan becomes a `Seq Scan` with a `Filter` that discards rows after reading them.

The cost is not only the scan. Module 4's default applies: a predicate the planner cannot match to a statistic is estimated at a flat 0.5% of the relation, whatever it actually matches. Wrapping a column is therefore two mistakes at once — the index goes unused, and the row estimate becomes a guess that can pick the wrong join algorithm downstream.

## Functions on the column

Functions are the most common wrapper, and usually the easiest to remove:

- `WHERE UPPER(status) = 'REFUNDED'` — normalise the constant instead of the column, or store the value already normalised: `WHERE status = 'refunded'`.
- `WHERE DATE(ordered_at) = DATE '2026-03-01'` — replace it with a half-open range on the bare column, `ordered_at >= '2026-03-01' AND ordered_at < '2026-03-02'`. The half-open form is also the only fully correct way to express "this day" against a timestamp, because the upper bound is exclusive.
- `WHERE EXTRACT(YEAR FROM ordered_at) = 2026` — the same rewrite with a year-long range.

When the expression really is the right domain model and the rewrite is not available, the escape hatch is an expression index: `CREATE INDEX ON orders (UPPER(status))` gives the planner a key that matches the predicate. That is a real fix, and it costs storage and write time on every insert.

## Casts

A cast around the column is a function in disguise. `customer_id::text = '7'` builds a text value per row and compares text; the index on `customer_id` stores integers and has nothing to seek to. `customer_id = 7` seeks.

What looks like the same cast is usually harmless: `customer_id = '7'` has a bare column on the left, and the untyped literal on the right is parsed into the column's type before the predicate exists. The asymmetry — cast the constant, never the column — is the whole rule.

Implicit casts between column types are the subtle version. Comparing a `text` column with a `varchar` column is free (the two are binary-compatible, so no conversion is needed for the comparison), but comparing an `integer` column with a `text` column has to convert one side. Keep the comparison on the type the column is stored as, and the index stays available.

## `OR` and `IN`

`IN (1, 2, 3)` is normalised to `x = 1 OR x = 2 OR x = 3`, and when every branch is indexable the planner can use a `BitmapOr`: one index scan per value, unioned into a single bitmap that drives one pass over the heap. So neither `IN` nor `OR` is automatically a problem. The problem is a branch that has no index.

```sql
WHERE customer_id = 7 OR status = 'refunded'   -- both indexed: BitmapOr
WHERE customer_id = 7 OR price > 200           -- price is not indexed: one sequential scan
```

When one branch is unindexable, the second form forces a sequential scan for the whole predicate, and the indexed branch buys nothing. If the two branches are genuinely different questions, `UNION ALL` of two index-using queries is a legitimate rewrite: each branch gets its own plan, and the results are stacked. It is more SQL, and it is usually faster.

## `LIKE` prefixes

A leading-anchored pattern is a range in disguise: `LIKE 'Aurora%'` matches every string that sorts at or after `Aurora` and before `Aurorap`. A B-tree can seek that range, but only when the index's collation makes sort order match pattern order. In practice that means an index with the `text_pattern_ops` operator class, or a database using the `C` collation:

```sql
CREATE INDEX products_name_pattern_idx ON products (name text_pattern_ops);
```

`LIKE '%Aurora%'` has no bound at all — the match can start anywhere — so no B-tree helps. That case needs a trigram index (`pg_trgm`) or full-text search, which are different tools rather than a different way to write the same predicate. `ILIKE` is in the same boat: case-insensitive matching cannot be answered by an index ordered by case-sensitive bytes.

## `IN` versus `EXISTS`

They often answer the same question and produce the same plan, but not always:

```sql
SELECT c.name
FROM customers c
WHERE c.id IN (SELECT o.customer_id FROM orders o WHERE o.status = 'refunded');

SELECT c.name
FROM customers c
WHERE EXISTS (SELECT 1 FROM orders o WHERE o.customer_id = c.id AND o.status = 'refunded');
```

The planner is free to turn either into a semi join, and usually does: `IN (subquery)` becomes a hashed semi join over the distinct subquery values, `EXISTS` becomes a nested-loop semi join that stops at the first matching row per customer. Which is cheaper depends on the sizes, and the plan tells you which one you got.

The reason to prefer `EXISTS` is correctness, not speed. `NOT IN (subquery)` returns no rows at all if the subquery produces a single `NULL`, because `x <> NULL` is never true; `NOT EXISTS` has no such trap. When the id set comes from a nullable column, the choice is between `NOT EXISTS` and filtering the `NULL`s out explicitly.

## Rewrites that actually help

| Instead of | Write | Why it helps |
| --- | --- | --- |
| `UPPER(status) = 'REFUNDED'` | `status = 'refunded'` | the index can bound the bare column, and the 0.5% default estimate disappears |
| `DATE(ordered_at) = DATE '2026-03-01'` | `ordered_at >= '2026-03-01' AND ordered_at < '2026-03-02'` | a half-open range is sargable and correct |
| `customer_id::text = '7'` | `customer_id = 7` | a cast on the column hides it; a typed literal does not |
| `name LIKE '%Aurora%'` | a trigram or full-text index | a leading wildcard has no seekable bound |
| `x = 1 OR y = 2` with one indexed branch | `UNION ALL` of two indexed queries | each branch gets its own access path |

The rewrites that do not help, however much they feel like they should: adding `LIMIT` to a query that aggregates (the aggregate still reads everything), removing `SELECT *` from a sequential scan (fewer columns does not mean fewer rows), or reordering the tables in `FROM` (join order belongs to the planner, module 5). None of them changes the predicate the index needs.

## What to remember

- An index needs a bare column on one side of the comparison; any function or cast around the column hides it.
- A wrapped column also loses its statistics, and falls back to a flat 0.5% estimate.
- `DATE(col) = ...` becomes a half-open range; a leading-anchored `LIKE` needs the right operator class; a leading wildcard needs a different index type altogether.
- `OR` and `IN` are fine while every branch is indexable, and expensive when one is not; `UNION ALL` separates the branches.
- `IN` and `EXISTS` mostly plan the same; `NOT IN` with a `NULL` is where they diverge, and `NOT EXISTS` is the safe one.
