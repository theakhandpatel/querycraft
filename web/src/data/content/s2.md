# Storage classes and type affinity

Open `products` and read the `price` column. The schema declares it `NUMERIC`, the seed writes every price with two decimals, and the first five rows come back as 59, 129, 84, 42.5, 139. One value keeps a fraction and the others look like they lost their cents. Nothing was rounded.

SQLite stores each value in a class that fits it, and the declared type only nudges that choice at the moment of writing. The gap between the two costs you a wrong answer, and no error marks it. A sum adds zero for a text value in a numeric column, and a filter keeps that row.

This chapter separates the two ideas, then shows the queries that reveal what a column actually holds.

## A class belongs to the value, an affinity belongs to the column

SQLite answers the type question twice, and keeps the two answers apart.

The storage class belongs to one value: `NULL`, `INTEGER`, `REAL`, `TEXT`, or `BLOB`. Two values in the same column can have different classes, and one of them can be an integer while the next is text.

The affinity belongs to the column. It comes from the declared type in `CREATE TABLE`, and it decides what happens to a value as it is written. It does not change a value after the write, and it does not reject anything.

`typeof(x)` reports the storage class of an expression as text: `'null'`, `'integer'`, `'real'`, `'text'`, or `'blob'`. It is the only honest way to ask what the engine stored, because a declared type is a claim about the column, not a report about the value.

Skip `typeof` and the declaration is the only answer left. That is how the `price` column gets reported as one type while it holds two.

## The five storage classes

| Class | Holds | In this dataset |
| --- | --- | --- |
| `NULL` | no value at all | the `city` of 4 customers, the `email` of 4 customers |
| `INTEGER` | a signed 64-bit whole number | `stock`, and `active` as 1 or 0 |
| `REAL` | an 8-byte floating point number | `price` for 10 of the 20 products |
| `TEXT` | a string of characters | `name`, and `signup_date` as `2025-11-02` |
| `BLOB` | bytes, stored as given | no column in this dataset uses one |

Two declared types in the schema have no class of their own. `customers.signup_date` is declared `DATE`, and `products.active` is declared `BOOLEAN`. Neither word names a storage class:

```sql
SELECT (SELECT typeof(signup_date) FROM customers LIMIT 1) AS signup_class,
       (SELECT typeof(active) FROM products LIMIT 1)      AS active_class;
```

| signup_class | active_class |
| --- | --- |
| text | integer |

A date is the text that spells it. A boolean is the integer 1 or 0. Neither declaration created a new class, so the values take the classes SQLite has.

## The declared type picks an affinity

SQLite reads the declared type as text, looks for keywords in it, and stops at the first match. The order is fixed:

| The declared type contains | Affinity |
| --- | --- |
| `INT` | INTEGER |
| `CHAR`, `CLOB`, or `TEXT` | TEXT |
| `BLOB`, or nothing at all | BLOB |
| `REAL`, `FLOA`, or `DOUB` | REAL |
| anything else | NUMERIC |

The order is the part people get wrong. `VARCHAR(20)` contains `CHAR`, so it gets TEXT affinity, not NUMERIC. `BIGINT` contains `INT`, so it gets INTEGER. A column declared with no type at all gets BLOB affinity, which converts nothing.

The last row catches more than it looks. `NUMERIC`, `DECIMAL(10,2)`, `BOOLEAN`, `DATE`, and `TIMESTAMP` contain none of the keywords above, so all five get NUMERIC affinity. In this dataset, `price`, `unit_price`, `signup_date`, `ordered_at`, and `active` share one affinity, and those five columns use four different declarations because `price` and `unit_price` are both `NUMERIC`.

## Affinity converts on write

Follow one price from the seed file to the column. The first product row, written as a single statement, looks like this:

```sql
INSERT INTO products (id, name, category, price, stock, active)
VALUES (1, 'Aurora Wireless Earbuds', 'Electronics', 59.00, 40, 1);
```

That statement is the seed's own insert. Running it in a workspace that already holds the seed fails with `UNIQUE constraint failed: products.id`. The queries below read the stored values instead.

`59.00` without quotes is a REAL literal, so the value reaches the column as the real 59.0. The column has NUMERIC affinity, and NUMERIC prefers the class that loses no information. A real with no fraction that fits in an integer is exactly that integer, so SQLite stores the INTEGER 59. The next seed row writes `42.50`, which has a fraction, so it stays the REAL 42.5.

Quoted numbers take the same route one step later. `'59.00'` arrives as TEXT, NUMERIC affinity sees text that looks numeric, and the same preference stores the integer 59. Text that does not look numeric skips the conversion and stays TEXT. That is the whole rule: try to convert, never refuse.

The result is a column with two classes and one declared type. This query counts each class.

```sql
SELECT typeof(price) AS stored, COUNT(*) AS products
FROM products
GROUP BY stored
ORDER BY stored;
```

| stored | products |
| --- | --- |
| integer | 10 |
| real | 10 |

Here are the first five rows, with the class beside the value.

```sql
SELECT id, name, price, typeof(price) AS stored
FROM products
ORDER BY id
LIMIT 5;
```

| id | name | price | stored |
| --- | --- | --- | --- |
| 1 | Aurora Wireless Earbuds | 59 | integer |
| 2 | Nimbus Headphones | 129 | integer |
| 3 | Linen Duvet Cover | 84 | integer |
| 4 | Cedar Desk Lamp | 42.5 | real |
| 5 | Trail Runner Jacket | 139 | integer |

The 10 and 10 split is a fact about this data, not a rule. Ten products happen to have a price with a zero fraction. A seed with one more price ending in `.25` would move the counts.

Affinity also applies when you compare. `WHERE price = '59'` matches the earbuds, because the column's affinity converts the text `'59'` before the comparison, the same way it would on a write.

## Affinity is not a constraint

A declared type does not restrict what the column accepts. It only decides the conversion attempt. You can prove that with a scratch table, which works in the in-browser workspace. The shared dataset file is read-only, so it refuses this write:

```sql
CREATE TEMP TABLE probe (
    numeric_col NUMERIC,
    text_col    TEXT,
    blob_col    BLOB
);

INSERT INTO probe VALUES ('59.00', 59, 59), ('abc', 'abc', 'abc');

SELECT numeric_col, typeof(numeric_col) AS numeric_class,
       text_col,    typeof(text_col)    AS text_class,
       blob_col,    typeof(blob_col)    AS blob_class
FROM probe;
```

| numeric_col | numeric_class | text_col | text_class | blob_col | blob_class |
| --- | --- | --- | --- | --- | --- |
| 59 | integer | 59 | text | 59 | integer |
| abc | text | abc | text | abc | text |

Read the three columns as three different rules. NUMERIC turned the text `'59.00'` into an integer and left `'abc'` alone. TEXT turned the integer 59 into the text `'59'`. BLOB affinity changed nothing, so the integer stayed an integer and the text stayed text.

Try this: rebuild the same scratch table with `text_col` declared `NUMERIC`, and insert the same two rows. Reset the workspace first if `probe` is still there. The `abc` row still stores text, because affinity converts only text that looks numeric, and the integer 59 stays an integer. The declared type is a preference on the way in, not a gate.

PostgreSQL rejects the same write into a `numeric(10,2)` column with `invalid input syntax for type numeric`. That refusal is a feature of the PostgreSQL type system. SQLite has no equivalent, and calling the difference a bug will not help you. Plan for it instead.

The cost of the freedom shows up in queries. A TEXT value stored in a numeric column sorts above every number, because SQLite orders classes before values: nulls first, then numbers, then text, then blobs.

So `WHERE price > 100` would keep a text row, and `sum(price)` would add zero for it instead of failing. Neither query reports a problem. You get an answer, and the answer is wrong.

## CAST is the only cast

PostgreSQL accepts `price::numeric`. SQLite has no `::`, and the parser stops at the colon:

```
unrecognized token: ':'
```

Use `CAST(x AS type)` instead. The type name picks the class or the affinity the value should move toward, and SQLite converts with the same preferences it uses on a write. That means a cast can succeed in the engine's sense while producing a value you did not want:

```sql
SELECT CAST('abc' AS INTEGER)   AS abc_to_int,
       typeof(CAST('abc' AS INTEGER)) AS abc_class,
       CAST('42abc' AS INTEGER) AS prefix_to_int,
       CAST('' AS INTEGER)      AS empty_to_int;
```

| abc_to_int | abc_class | prefix_to_int | empty_to_int |
| --- | --- | --- | --- |
| 0 | integer | 42 | 0 |

`'abc'` has no numeric prefix, so it becomes 0. `'42abc'` has one, so it becomes 42. An empty string becomes 0 as well. None of these raises an error, so `CAST` cannot validate input.

`CAST` to `INTEGER` also truncates toward zero, where PostgreSQL rounds. `CAST(3.9 AS INTEGER)` is 3 here and 4 in PostgreSQL, and `CAST(-3.9 AS INTEGER)` is -3 here and -4 there. A query ported with the cast intact can move a number by one.

Then there is the target that looks safe and is not. `CAST('2025-11-02' AS date)` returns 2025:

```sql
SELECT CAST('2025-11-02' AS date)          AS date_cast,
       typeof(CAST('2025-11-02' AS date))  AS date_class,
       CAST('2025-11-02' AS TEXT)          AS text_cast;
```

| date_cast | date_class | text_cast |
| --- | --- | --- |
| 2025 | integer | 2025-11-02 |

`date` matches no affinity keyword, so it means NUMERIC. The text starts with digits, so NUMERIC keeps the numeric prefix and drops the rest. Ask for `TEXT` when you want the characters back. Chapter 4 covers dates properly.

## A wrong turn: CAST does not format money

You want prices to print with two decimals. The stored values read 59 and 42.5, so you cast them to text:

```sql
SELECT id, CAST(price AS TEXT) AS price_text
FROM products
ORDER BY id
LIMIT 5;
```

| id | price_text |
| --- | --- |
| 1 | 59 |
| 2 | 129 |
| 3 | 84 |
| 4 | 42.5 |
| 5 | 139 |

The output is worse than before. Row 4 shows `42.5` and the whole-number prices show no decimals at all. `CAST` changes the storage class, not the number of digits. When SQLite turns a REAL into text, it writes the shortest string that reads back as the same number, so 42.5 becomes `42.5`.

Scale is a formatting decision, and `printf` is the function for it:

```sql
SELECT id, price, printf('%.2f', price) AS formatted
FROM products
WHERE id IN (1, 4, 15, 19)
ORDER BY id;
```

| id | price | formatted |
| --- | --- | --- |
| 1 | 59 | 59.00 |
| 4 | 42.5 | 42.50 |
| 15 | 19.99 | 19.99 |
| 19 | 15.5 | 15.50 |

The stored class does not change, and it does not need to. The number is right; only its display was wrong. The column label comes from the declared type; the value carries its own storage class. A formatted value arrives as text, an unformatted one as a number.

The exercise that follows asks for the id, name, and storage class of every product whose price is stored as a REAL, ordered by id. You now have the pieces: `typeof(price)` reports the class, and the class is what you filter on, not the declared type. The starter filters on the other class, which returns the other ten products, so read the class column in the output rather than the row count.

## What to remember

What I would do: run `typeof()` on any column whose declared type you rely on, then filter on the class you find. Keep display in `printf` and arithmetic on numbers, and never let a numeric column hold text. When a report looks wrong, check the class before you check the formula.

- A storage class belongs to a value: `NULL`, `INTEGER`, `REAL`, `TEXT`, or `BLOB`. There is no boolean class and no date class.
- An affinity belongs to a column and comes from its declared type, by substring rules read in a fixed order.
- NUMERIC affinity turns the real 59.0 into the integer 59 and keeps 42.5 as a real. Scale is lost, value is not.
- Affinity converts on write and never refuses. A numeric column will hold text.
- `typeof(x)` reports the class. Use it when a value's shape matters.
- `CAST` is the only cast, and it returns 0 for text with no numeric prefix. It does not validate and it does not format.
- Print money with `printf('%.2f', price)`, not with a cast to TEXT.

## Check yourself

**1. `products.price` is declared `NUMERIC`. Why does half the column report `integer`?**

<details>
<summary>Answer</summary>

Because the declared type sets the column's affinity, not the value's class. NUMERIC affinity stores the literal 59.00 as the integer 59, since the fraction is zero. The other ten prices have a non-zero fraction, so they stay real. One declared type, two classes.

</details>

**2. A column is declared `VARCHAR(20)`. What affinity does it get, and why not NUMERIC?**

<details>
<summary>Answer</summary>

TEXT affinity, because the rules are checked in order and `CHAR` matches before the catch-all. The catch-all would have chosen NUMERIC, but `CHAR` appears in the declared type, so TEXT wins first.

</details>

**3. Why does `CAST('3.9' AS INTEGER)` differ from PostgreSQL's `CAST(3.9 AS INTEGER)`?**

<details>
<summary>Answer</summary>

SQLite truncates toward zero, so 3.9 becomes 3. PostgreSQL rounds, so 3.9 becomes 4. A cast that is correct in one engine can change a number by one in the other.

</details>

**4. You store `'abc'` in a numeric column and later run `WHERE price > 100`. What happens, and why is it dangerous?**

<details>
<summary>Answer</summary>

The row is kept. SQLite orders storage classes before values, and text sorts above every number, so the text is "greater than" 100. `sum(price)` would add zero for that row instead of failing. No error is raised, so the report is wrong without announcing itself.

</details>

**5. Why does `CAST(price AS TEXT)` fail to produce two decimal places?**

<details>
<summary>Answer</summary>

A cast changes the storage class, not the formatting. Turning the real 42.5 into text gives `42.5`, the shortest string that reads back as the same number. Use `printf('%.2f', price)` when you need a fixed number of decimals.

</details>
