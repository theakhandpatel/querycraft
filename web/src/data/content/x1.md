# Casts are gone: `::` → `CAST`

A report that returns three rows in PostgreSQL returns nothing here. You paste it into SQLite, and the parser stops before it reads a row:

```sql
SELECT id, ordered_at::date AS ordered_on
FROM orders
LIMIT 3;
```

```
unrecognized token: ":"
```

The parser stopped at the colon, so no join, plan or value caused the failure. That error is the good case, because it names the character. The repair is one keyword, and it brings back no type check, no rounding and no date type. Three of those gaps change a number in a commerce report with no error at all, and the sections below take them one at a time.

## The colon is not a token here

PostgreSQL accepts two spellings of one operation: `unit_price::integer` and `CAST(unit_price AS INTEGER)`. The double colon is a shorthand. The SQL standard uses the `CAST` keyword, and SQLite parses only that form.

| PostgreSQL | SQLite | What you get |
| --- | --- | --- |
| `unit_price::integer` | `CAST(unit_price AS INTEGER)` | the value, moved to the integer class |
| `customer_id::text` | `CAST(customer_id AS TEXT)` | the digits as text |
| `ordered_at::date` | `date(ordered_at)` | a function, not a cast |
| `x::numeric(10,2)` | `ROUND(x, 2)` | a rounded number with no fixed scale |

The first two keep the value unchanged. The last two change it, and they are where ports break. A query that stops at the colon costs you a minute. A cast that runs and returns `2026` for every row costs you a report.

Try this: rewrite the first query as `SELECT id, CAST(ordered_at AS date) AS ordered_on FROM orders LIMIT 3;`. It runs, it returns three rows, and `ordered_on` holds `2026` on all three. The repair stopped the error and threw the day away.

## A cast chooses a storage class

Every SQLite value sits in one of five storage classes: NULL, INTEGER, REAL, TEXT, BLOB. A declared type is a preference, called an affinity, and a cast applies that preference to one value.

The type word is read for keywords inside it, not as a name.

| Type word | Class |
| --- | --- |
| contains `INT` | INTEGER |
| contains `CHAR`, `CLOB` or `TEXT` | TEXT |
| contains `REAL`, `FLOA` or `DOUB` | REAL |
| `BLOB` | BLOB |
| anything else, including `DATE` | NUMERIC |

The demo converts four values:

```sql
SELECT CAST('2026-05-01' AS TEXT) AS text_cast,
       CAST('7' AS INTEGER)       AS int_cast,
       CAST(7 AS TEXT)            AS text_from_int,
       CAST('abc' AS INTEGER)     AS bad_text;
```

| text_cast | int_cast | text_from_int | bad_text |
| --- | --- | --- | --- |
| 2026-05-01 | 7 | 7 | 0 |

With no `FROM` there is no table: one row with no columns, four expressions, one result row. Columns one to three move a value and keep it. Column four returns the zero that the rest of this chapter is about.

## A bad value becomes zero

PostgreSQL refuses `'abc'::integer` with `invalid input syntax for type integer: "abc"`, code `22P02`, and no rows. That refusal earns its keep: it names the value that broke the promise.

SQLite's rule is quieter. Keep the longest numeric prefix, and use zero when there is none:

```sql
SELECT CAST('12abc' AS INTEGER) AS prefix, CAST('abc' AS INTEGER) AS none,
       CAST('' AS INTEGER) AS empty,      CAST(NULL AS INTEGER)  AS null_in;
```

| prefix | none | empty | null_in |
| --- | --- | --- | --- |
| 12 | 0 | 0 | NULL |

`'12abc'` becomes 12 and loses `abc` in silence. The empty string becomes the same 0 a real zero gives. NULL stays NULL, because a cast cannot invent a value from nothing.

The commerce columns hold clean values, so no query here can show the damage. Picture a price column holding `n/a`, as a spreadsheet import might. `SUM(CAST(price AS NUMERIC))` adds zero for that row, and the total drops with no error.

`typeof(price)` shows the class of a stored value, and a `CHECK` stops junk at the door.

## Fractions truncate toward zero

PostgreSQL's cast to integer rounds. SQLite's truncates:

```sql
SELECT CAST(2.9 AS INTEGER) AS pos, CAST(-2.9 AS INTEGER) AS neg,
       CAST(2.5 AS INTEGER) AS half;
```

| pos | neg | half |
| --- | --- | --- |
| 2 | -2 | 2 |

PostgreSQL returns 3, -3 and 3 for the same values, because its numeric cast rounds away from zero. A ported cast therefore changes every value with a fraction, and it moves each one toward zero.

Money shows the cost. Completed lines total 10241.59, and casting each unit price first gives 10204:

```sql
SELECT ROUND(SUM(quantity * unit_price), 2)                    AS exact_revenue,
       ROUND(SUM(quantity * CAST(unit_price AS INTEGER)), 2)   AS truncated_revenue
FROM orders o JOIN order_items oi ON oi.order_id = o.id
WHERE status = 'completed';
```

| exact_revenue | truncated_revenue |
| --- | --- |
| 10241.59 | 10204 |

A gap of 37.59, with no error and no warning. Round at the edge with `ROUND(x, 2)`. Cast money to INTEGER only when you mean to drop the fraction.

## The date target throws the day away

`ordered_at::date` is the cast that hurts most, because the obvious port succeeds. Here is a monthly report grouped on it:

```sql
SELECT CAST(ordered_at AS DATE) AS month, COUNT(*) AS orders
FROM orders
GROUP BY month;
```

| month | orders |
| --- | --- |
| 2026 | 80 |

The cast read 2026 out of every timestamp, because `DATE` names no storage class and falls back to NUMERIC affinity. The month and the day are gone, and nothing marks the loss. The counts you wanted were 16, 19, 18, 18 and 9, and every row landed in the same group.

Ask for text instead:

```sql
SELECT strftime('%Y-%m', ordered_at) AS month, COUNT(*) AS orders
FROM orders
GROUP BY month
ORDER BY month;
```

| month | orders |
| --- | --- |
| 2026-01 | 16 |
| 2026-02 | 19 |
| 2026-03 | 18 |
| 2026-04 | 18 |
| 2026-05 | 9 |

`strftime` reads the stored ISO-8601 text and writes the fields you name. `%Y-%m` is a four-digit year, a hyphen, and a two-digit month.

## DATE_TRUNC becomes a format string

`DATE_TRUNC('month', o.ordered_at)::date` does two jobs: truncate to the first of the month, and return a date. SQLite has no date value, so both jobs move into a format string.

```sql
SELECT id, strftime('%Y-%m-01', ordered_at) AS month, date(ordered_at) AS day
FROM orders
ORDER BY id
LIMIT 3;
```

| id | month | day |
| --- | --- | --- |
| 1001 | 2026-01-01 | 2026-01-04 |
| 1002 | 2026-01-01 | 2026-01-19 |
| 1003 | 2026-01-01 | 2026-01-22 |

`%Y-%m-01` reads as year, hyphen, month, hyphen, and the two literal characters `01`. The truncation is part of what gets printed, not an operation applied afterwards.

Both results are text, and they still sort in date order because ISO-8601 puts the widest field first. `date(ordered_at, 'start of month')` returns the same string. `TO_CHAR(d, 'YYYY-MM')` becomes `strftime('%Y-%m', d)`.

## A port you can repeat

Work one cast at a time. A cast to INTEGER is safe only if every value was already whole. A cast to TEXT changes how the value compares and how it sorts. A cast to `DATE` is never right.

One cast still earns its place. Division between two integers drops the fraction: `59 / 3` returns 19, and `CAST(59 AS REAL) / 3` returns 19.666666666666668. Where the old query divided a numeric column, the REAL cast keeps the fraction alive.

The exercise starts from `ordered_at::date` and asks for the three earliest orders, with the date as `ordered_on` and the status, oldest first and ties settled by `id`. The date function from the last three sections supplies the first column, and the rest is a sort key you know.

## What to remember

**What I would do:** port one cast at a time and compare each result with the PostgreSQL answer. Search the report for `::` before you run it, keep money numeric, and round at the edge with `ROUND(x, 2)`. Treat a cast to `DATE` as a bug, and reach for `strftime` or `date()` instead.

- `::` is PostgreSQL shorthand. SQLite parses only `CAST(expr AS type)`, and anything else stops at `unrecognized token: ":"`.
- A cast moves a value between five storage classes, and the type word picks the class by keywords inside it.
- Text with no number becomes 0, and a fraction becomes its truncated integer. PostgreSQL raises `22P02` and rounds instead.
- There is no date type. `CAST(x AS DATE)` returns 2026 from a date string, so `date(x)` and `strftime('%Y-%m-01', x)` are the ports.

## Check yourself

**1. Why does `CAST('abc' AS INTEGER)` return 0 instead of failing?**

<details>
<summary>Answer</summary>

SQLite reads the longest numeric prefix of the text and uses 0 when there is none. It converts values, it does not validate them. `typeof(column)` shows the class of a stored value, so text in a numeric column shows up there.

</details>

**2. You group a monthly report on `CAST(ordered_at AS DATE)` and get one row with 80 orders. What happened?**

<details>
<summary>Answer</summary>

`DATE` contains no keyword that names a storage class, so the cast selects NUMERIC affinity and reads 2026 out of every timestamp. All 80 rows land in one group. Use `strftime('%Y-%m', ordered_at)` for a month key, or `strftime('%Y-%m-01', ordered_at)` for the first of the month.

</details>

**3. A revenue report changes from 10241.59 to 10204 after a port. Which line do you suspect first?**

<details>
<summary>Answer</summary>

A cast of `unit_price` to INTEGER. SQLite truncates toward zero, so each line loses its cents, and the 74 completed lines turn that into a visible gap. PostgreSQL rounds instead. Keep the column numeric and round at the edge.

</details>
