# NULL is unknown

The support team asks for every customer who is not in Leeds, and the report comes back four rows short. `city <> 'Leeds'` returns 23 rows, `customers` holds 30, and only 3 of those rows are in Leeds. The four that vanish have no city recorded, so PostgreSQL refuses to call them "not Leeds", and it prints no warning.

A customer row can be incomplete. Dara Novak has an id, a name and an email address, and no city. The database does not store a blank there and it does not store the text `'Unknown'`. It stores `NULL`, which means one thing: no value has been recorded.

This chapter explains that refusal, the three answers a predicate can give, and the tools that handle an unknown on purpose: `IS NULL`, `IS DISTINCT FROM` and `COALESCE`. It ends on sorting, because an ordered list has to put the unknown rows somewhere.

## A customer with no city

```sql
SELECT id, name, email, city
FROM customers
WHERE id = 4;
```

| id | name | email | city |
| --- | --- | --- | --- |
| 4 | Dara Novak | dara@example.com | NULL |

The row exists, and `city` is the one value it lacks. `NULL` is how the database records that gap, and three other customers are in the same position: Bo Ivanov, Luca Novak and Tess Larsen. Every filter that meets one of those four rows drops it, and the count that comes back still looks like a count.

`NULL` is not another spelling of a value you already know. A price of `0.00` says the product is free. An empty string says someone submitted a form and left the field blank. `NULL` says nobody has answered yet.

Treating the three as the same thing causes most null bugs, because the fixes differ. You cannot repair an unknown with arithmetic, and `''` is a fact while `NULL` is the lack of one.

The marker shows up in counts too:

```sql
SELECT count(*) AS customers,
       count(city) AS known_cities,
       count(email) AS known_emails
FROM customers;
```

| customers | known_cities | known_emails |
| --- | --- | --- |
| 30 | 26 | 26 |

`count(*)` counts rows. `count(city)` counts the rows where `city` has a value, which is 26. The missing values are not zero and they are not counted. Four customers have no city and four have no email, and the two groups are different people, so eight customers are missing at least one field.

## A predicate has three answers

A predicate is the condition inside `WHERE`. You may expect every predicate to come out true or false for a row. In SQL it has a third answer: unknown. A comparison with an unrecorded value is unknown, because the database cannot know whether an unrecorded city equals Leeds.

This is three-valued logic: true, false, unknown. `WHERE` keeps a row only when the answer is true. False and unknown both drop the row, and that shared outcome is why a null can disappear without an error message.

The trouble starts with an innocent-looking test:

```sql
SELECT count(*) AS rows_returned
FROM customers
WHERE city = NULL;
```

| rows_returned |
| --- |
| 0 |

Four rows have a null city and this query returns none of them. `city = NULL` is not the question "is the city missing". It asks whether one unknown value equals another, and nobody can answer that. The same holds for `<>`, `<`, `>` and every other comparison.

The test for a missing value is its own operator:

```sql
SELECT name, city
FROM customers
WHERE city IS NULL
ORDER BY name;
```

| name | city |
| --- | --- |
| Bo Ivanov | NULL |
| Dara Novak | NULL |
| Luca Novak | NULL |
| Tess Larsen | NULL |

`IS NULL` inspects the row and answers true or false, never unknown. `IS NOT NULL` is its mirror. Both exist for this job, and no comparison operator can replace them.

Unknown spreads through `AND`, `OR` and `NOT` in a way you can predict:

| `a` | `b` | `a AND b` | `a OR b` |
| --- | --- | --- | --- |
| true | unknown | unknown | true |
| false | unknown | false | unknown |
| unknown | unknown | unknown | unknown |

`AND` needs both sides true, so one unknown is enough to make the result unknown. `OR` needs one side true, so a true side wins even against an unknown. `NOT unknown` is unknown. Keep the table in mind, because it explains the count in the next section.

## The not-Leeds report drops four rows

Here is the report from the opening, with the predicate shown as a column so you can watch each row decide.

```sql
SELECT name, city, city <> 'Leeds' AS not_leeds
FROM customers
ORDER BY id
LIMIT 4;
```

| name | city | not_leeds |
| --- | --- | --- |
| Ada Whitfield | Leeds | false |
| Bruno Sala | Milan | true |
| Chidi Okafor | Lagos | true |
| Dara Novak | NULL | NULL |

The count version keeps only the true rows. It is the same predicate, with the false and unknown rows dropped.

```sql
SELECT count(*) AS not_leeds
FROM customers
WHERE city <> 'Leeds';
```

| not_leeds |
| --- |
| 23 |

Here is the arithmetic, which is the check to run whenever a filtered count looks low. Thirty rows enter the filter. Three are in Leeds and answer false. Four have a null city and answer unknown. The other 23 answer true and reach the result.

A complete answer to "who is not in Leeds" is 27 rows, so the plain comparison loses the four in the middle.

`NOT city = 'Leeds'` is no better. It also returns 23, because negating an unknown gives an unknown. If the report needs the missing rows, you have to ask a different kind of question.

## `IS DISTINCT FROM` treats unknown as a value

`IS DISTINCT FROM` compares two values and gives true or false for every row, nulls included. It treats two nulls as the same, and a null against a known value as different. For "is this city something other than Leeds", that is the answer you wanted:

```sql
SELECT COUNT(*) FILTER (WHERE city <> 'Leeds') AS not_leeds,
       COUNT(*) FILTER (WHERE city IS DISTINCT FROM 'Leeds') AS truly_not_leeds
FROM customers;
```

| not_leeds | truly_not_leeds |
| --- | --- |
| 23 | 27 |

`COUNT(*) FILTER (WHERE ...)` counts the rows that pass a condition. Read it as a conditional count; chapter 7 takes `GROUP BY` and the aggregates apart.

The second column counts every customer whose city is not Leeds, including the four unknown cities, because `IS DISTINCT FROM 'Leeds'` returns true for a null. The first column is the query from the previous section, folded into the same statement.

`IS NOT DISTINCT FROM` is the equality version. It returns true when both sides are null, which `=` never does, and it is the right test when you compare two columns that can each be missing.

There is a second route to the same 27, and it changes the value instead of the operator. `COALESCE` returns the first of its arguments that is not null, and the next section takes it apart.

```sql
SELECT count(*) AS not_leeds
FROM customers
WHERE COALESCE(city, 'Unknown') <> 'Leeds';
```

| not_leeds |
| --- |
| 27 |

Now every row has a value, `'Unknown'` is different from `'Leeds'`, and the comparison returns true. The trade is that you invented a value. If a real city is ever named Unknown, the report will count those customers as unknown too. `IS DISTINCT FROM` makes no such claim, so prefer it when the comparison itself is the point.

## `COALESCE` supplies a fallback

`COALESCE` takes any number of arguments and returns the first one that is not `NULL`. Two arguments cover most cases: the column, then what to show instead.

```sql
SELECT id, name, email, city, COALESCE(email, city) AS contact
FROM customers
ORDER BY id
LIMIT 5;
```

| id | name | email | city | contact |
| --- | --- | --- | --- | --- |
| 1 | Ada Whitfield | ada@example.com | Leeds | ada@example.com |
| 2 | Bruno Sala | bruno@example.com | Milan | bruno@example.com |
| 3 | Chidi Okafor | NULL | Lagos | Lagos |
| 4 | Dara Novak | dara@example.com | NULL | dara@example.com |
| 5 | Emi Tanaka | emi@example.com | Osaka | emi@example.com |

Row 3 falls through to the city, because the email is unknown. Row 4 stops at the email, so the city is never consulted. Row 4 is also a reminder that a fallback only helps the column you name: `city` is still null, and a report that selects `city` still shows the gap.

`COALESCE` cannot repair a value you already combined. Text joined with `||` goes unknown when any part is unknown:

```sql
SELECT name, 'Order for ' || name || ' in ' || city AS address_line
FROM customers
WHERE name = 'Ada Whitfield' OR name = 'Dara Novak'
ORDER BY name;
```

| name | address_line |
| --- | --- |
| Ada Whitfield | Order for Ada Whitfield in Leeds |
| Dara Novak | NULL |

The concatenation runs first and produces an unknown. Wrap the nullable part, not the whole expression: `COALESCE(city, 'an unknown city')`. Arithmetic behaves the same way, so a total that includes one null is null.

## Sorting puts `NULL` somewhere

An ordered list has to place the unknown rows too. PostgreSQL sorts `NULL` as larger than any value, so it comes last in ascending order and first in descending order. That rule is reliable, and a reader should not have to recall it:

```sql
SELECT name, city
FROM customers
WHERE city = 'Milan' OR city IS NULL
ORDER BY city NULLS LAST, name;
```

| name | city |
| --- | --- |
| Bruno Sala | Milan |
| Noor Berg | Milan |
| Zane Lindqvist | Milan |
| Bo Ivanov | NULL |
| Dara Novak | NULL |
| Luca Novak | NULL |
| Tess Larsen | NULL |

Seven rows: three in Milan and four with no city. `NULLS LAST` states the placement, and the `name` key sorts inside each group, so the three Milans and the four unknowns each arrive in alphabetical order. Switch to `NULLS FIRST` when the rows nobody has classified belong at the top, as in a data-quality list.

The default and the explicit clause agree in ascending order. They disagree the moment someone adds `DESC`, which puts the nulls first without saying so. Write the clause when the position carries meaning.

Try this: change `NULLS LAST` to `NULLS FIRST` in the `ORDER BY` and run it again. The four unknown cities move to the top, the three Milan rows follow, and the `name` key still sorts inside each group. The seven rows are the same, and only the claim about where an unknown belongs has changed.

## What the exercise asks you to do

The exercise asks for the name and city of every customer whose city is unknown, with the missing city shown as `'Unknown'`, ordered by name. You now have both halves: an `IS NULL` filter to choose the rows, and a `COALESCE` fallback to give the missing value a label.

Two checks catch a wrong answer. There should be four rows, because four customers have no city. And no city cell should print `NULL`, because the fallback replaced every one of them. A `NULL` in the output means the fallback is missing or applied to the wrong column.

## What to remember

What I would do: test the gap with `IS NULL`, compare with `IS DISTINCT FROM` when either side can be missing, and reserve `COALESCE` for the places you want a label in the output. Decide once whether a null in this column means unknown or means nothing, and write that answer down, because the two reports differ. Never compare a nullable column to `NULL` with `=`.

- `NULL` marks a missing value. It is not zero, not an empty string, and not a label you chose.
- A comparison with `NULL` is unknown. `WHERE` keeps only true rows, so unknown rows disappear without an error.
- Use `IS NULL` and `IS NOT NULL` to test for a missing value. `= NULL` matches nothing, even on rows that hold a null.
- `IS DISTINCT FROM` treats two nulls as equal and returns true or false for every row. It counts 27 not-Leeds customers where `<>` counts 23.
- `COALESCE` returns the first argument that is not `NULL`. Wrap the nullable part before you concatenate or compute.
- PostgreSQL sorts `NULL` last ascending and first descending. `NULLS FIRST` and `NULLS LAST` say it out loud.

## Check yourself

**1. Four rows have a null city, yet `WHERE city = NULL` returns none. What did that predicate actually ask?**

<details>
<summary>Answer</summary>

It asked whether one unknown value equals another unknown value. The answer is unknown for every row, and `WHERE` drops unknown rows. `IS NULL` asks whether no value is recorded, which is a question the database can answer.

</details>

**2. A colleague reports 23 customers outside Leeds. How do you find the four their report lost, without reading their query?**

<details>
<summary>Answer</summary>

Count the null cities: `SELECT count(*) FROM customers WHERE city IS NULL` returns 4. Thirty customers minus 3 in Leeds gives 27, and 27 minus 4 gives 23. The gap matches the unknown cities exactly, which points at a plain `<>` comparison.

</details>

**3. Why does `COALESCE(city, 'Unknown') <> 'Leeds'` count 27 while `city <> 'Leeds'` counts 23?**

<details>
<summary>Answer</summary>

`COALESCE` replaces the null with the text `'Unknown'`, so every row has a value to compare and no comparison is unknown. The count rises by the four rows the plain comparison could not judge. The cost is that `'Unknown'` becomes a value, so a real city with that name would be misread.

</details>

**4. What is the difference between `IS DISTINCT FROM` and `<>` for a column that allows nulls?**

<details>
<summary>Answer</summary>

`<>` returns unknown when either side is null, and `WHERE` drops the row. `IS DISTINCT FROM` always returns true or false, treating two nulls as the same value and a null against a known value as different. Use `<>` when nulls cannot occur, and `IS DISTINCT FROM` when they can.

</details>

**5. `ORDER BY city DESC` puts the null cities first. Which clause changes that, and when would you use it?**

<details>
<summary>Answer</summary>

`NULLS LAST`, as in `ORDER BY city DESC NULLS LAST`. Use it when the reader expects the known values first whatever the direction, such as a ranked list with a block of unclassified rows at the end.

</details>
