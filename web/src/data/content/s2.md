# Storage classes and type affinity

## The declared type is a hint

SQLite answers "what type is this column?" twice. The declared type is the word in `CREATE TABLE`. The storage class is what a value actually is: `NULL`, `INTEGER`, `REAL`, `TEXT`, or `BLOB`.

The declared type chooses an affinity. The affinity decides whether a value converts when it is written. Nothing checks it when the value is read.

PostgreSQL rejects `'abc'` in a numeric column. SQLite accepts it and stores TEXT. That is the type system, not a bug.

| The declared type contains | Affinity |
| --- | --- |
| `INT` | INTEGER |
| `CHAR`, `CLOB`, or `TEXT` | TEXT |
| `BLOB`, or no declared type | BLOB |
| `REAL`, `FLOA`, or `DOUB` | REAL |
| anything else | NUMERIC |

The order matters. `VARCHAR(20)` contains `CHAR`, so it is TEXT affinity, not NUMERIC. `BIGINT` contains `INT`. A column with no declared type has BLOB affinity, which never converts. That is different from NUMERIC affinity, and it is easy to miss.

## Affinity converts on write

NUMERIC is the affinity that surprises people. The dataset declares money as `NUMERIC` and seeds values like `'59.00'` and `'42.50'`. SQLite stores the first as the integer `59`, because the fraction is zero and the integer is lossless. It stores the second as the real `42.5`. The scale is gone from the value; the column name still says NUMERIC.

```sql
SELECT typeof(price) AS stored, COUNT(*) AS products
FROM products
GROUP BY stored
ORDER BY stored;
```

| stored | products |
| --- | --- |
| integer | 10 |
| real | 10 |

Twenty products, two storage classes, one declared type. PostgreSQL would report `numeric` for all twenty. SQLite reports what the value actually is. That is why a shared contract compares the stored value, not the column declaration.

## `CAST` is the only cast

PostgreSQL spells a cast `x::integer` and also accepts `CAST(x AS integer)`. SQLite has no `::`; the token is a syntax error. Use `CAST`.

There is no `date` target because there is no date type. `CAST(x AS date)` parses, selects NUMERIC affinity, and does nothing that `CAST(x AS TEXT)` would not do better.

Casting uses the same conversion rule as affinity, but with a twist:

```sql
SELECT CAST('abc' AS INTEGER) AS abc_to_int,
       typeof(CAST('abc' AS INTEGER)) AS abc_type,
       CAST(59.00 AS TEXT) AS price_as_text;
```

| abc_to_int | abc_type | price_as_text |
| --- | --- | --- |
| 0 | integer | 59 |

`'abc'` cannot convert to an integer, so `CAST` returns `0`. It does not raise an error and it does not return NULL. Validate values in the application if you need a rejection.

## Check yourself

**1. A column is declared `INT`. Can `'abc'` be stored in it?**

<details>
<summary>Answer</summary>

Yes. The declaration selects INTEGER affinity, not an integer constraint. TEXT is a legal storage class for any column, and a non-numeric string is stored as TEXT.

</details>

**2. `price NUMERIC` is seeded with `'59.00'`. What does `typeof(price)` return, and why?**

<details>
<summary>Answer</summary>

`integer`. NUMERIC affinity converts numeric-looking text on write, and `'59.00'` is losslessly an integer, so the stored class is INTEGER even though the declared type says NUMERIC.

</details>

**3. How do you cast in SQLite, and what does `CAST('abc' AS INTEGER)` return?**

<details>
<summary>Answer</summary>

Use `CAST(x AS type)`. There is no `::` operator. `CAST('abc' AS INTEGER)` returns `0`, because the text cannot be converted and SQLite gives the coercion's zero value instead of raising an error.

</details>
