# Constraints, foreign keys and `ON CONFLICT`

## Foreign keys exist and do not fire

The commerce schema declares real foreign keys: `orders.customer_id REFERENCES customers(id)` and two on `order_items`. They are in the schema, they are in `sqlite_master` as part of the `CREATE TABLE` text, and by default **they do nothing**. `PRAGMA foreign_keys` is off at the start of every connection, and until it is on, the engine will insert a child row whose parent does not exist.

This is the most expensive default in SQLite for anyone arriving from PostgreSQL, where the constraint is enforced by the server and there is no session switch to forget. The fix is one pragma, set per connection, which is why a tool that opens connections itself must set it in the connection factory:

```sql
PRAGMA foreign_keys;
```

| foreign_keys |
| --- |
| 1 |

The gateway turns it on, so this fixture is enforcing. A connection that forgot would report `0` and silently accept the same writes.

## Reading the declared keys

The declarations are queryable, which is how you audit a schema instead of reading DDL by eye. `pragma_foreign_key_list(table)` returns one row per key, naming the parent table and both sides of the join:

```sql
SELECT "table", "from", "to"
FROM pragma_foreign_key_list('order_items')
ORDER BY id;
```

| table | from | to |
| --- | --- | --- |
| products | product_id | id |
| orders | order_id | id |

Two rows: `order_items` points at `products` and at `orders`, and each key says which child column maps to which parent column. The `id` column orders the rows; the engine's own order is not something to rely on, so `ORDER BY id` is what makes the output stable. `pragma_index_list` and `pragma_index_info` do the same job for indexes, including the ones the planner is actually using.

## `ON CONFLICT` is the upsert

`INSERT` has grown the conflict clause PostgreSQL has had for years. `ON CONFLICT DO NOTHING` makes the statement a no-op when a uniqueness constraint rejects the row; `ON CONFLICT (key) DO UPDATE SET …` updates the existing row instead, with the incoming row available under the name `excluded`:

```sql
INSERT INTO dataset_meta (dataset, version)
VALUES ('commerce', 2)
ON CONFLICT (dataset) DO UPDATE SET version = excluded.version;
```

That is one statement where an application would otherwise write select-then-insert-or-update with a race between the two halves. The conflict target matters: `ON CONFLICT (dataset)` names the unique index that decides the conflict, and without a target the clause catches any uniqueness violation.

The shared lesson fixture is read-only, so the statement above is here to read, not to run: the same reason chapter 1's write failed. If you want to exercise it, create your own file and try it there.

## `RETURNING` and the last rowid

`RETURNING` (3.35+) closes the other gap with PostgreSQL: the `INSERT`, `UPDATE` and `DELETE` statements can hand back the rows they touched, so you do not need a follow-up `SELECT`.

```sql
INSERT INTO customers (name, signup_date)
VALUES ('New Learner', '2026-01-01')
RETURNING id, name;
```

The older mechanism is `last_insert_rowid()`, a function that returns the rowid of the most recent successful insert on the connection. It is exactly the rowid chapter from the essentials course showing up in a write path: reliable for a single insert, and ambiguous if the insert fired a trigger that itself inserted rows. `RETURNING` does not have that problem, which is why it is worth preferring on any version that has it.

## Check yourself

**1. A schema declares a foreign key. Is it enforced?**

<details>
<summary>Answer</summary>

Only if the connection has `PRAGMA foreign_keys = ON`. It is off by default on every new connection, so a declared key can exist and never fire.

</details>

**2. What does `ON CONFLICT (dataset) DO UPDATE SET version = excluded.version` do?**

<details>
<summary>Answer</summary>

When an insert would violate the unique index on `dataset`, it updates the existing row instead, taking the new value from the `excluded` pseudo-row. It is an upsert in one statement.

</details>

**3. Why prefer `RETURNING` over `last_insert_rowid()`?**

<details>
<summary>Answer</summary>

`last_insert_rowid()` reports the connection's most recent insert and can be confused by inserts that fired inside triggers. `RETURNING` reports the rows the statement itself wrote.

</details>
