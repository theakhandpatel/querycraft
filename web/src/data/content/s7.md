# When SQLite is the right choice, and what it cannot do

## Where a file wins

SQLite fits when the database and the process share an owner and a lifetime. That covers a browser tab, a phone app, a desktop tool, a build cache, a test fixture, and an analytics file you send to a colleague. In each case, "install a database server" is work with no buyer. "Open a file" is the operation you wanted.

The schema, the data, and the queries ship as one artifact. There is no separate deployment to drift from development, no connection pool to size, and no migration window where the server is half upgraded. `make build` here produces one binary with the dataset inside it. Same argument at application scale.

| Question | SQLite | PostgreSQL |
| --- | --- | --- |
| Who writes? | one process, or one at a time | many clients |
| Where does it run? | in the process | in a server |
| What is access control? | the file | roles and grants |
| What is the schema? | one namespace per file | schemas and `search_path` |
| What is strong typing? | opt-in with `STRICT` | the default |

## What is missing

These limits are real. Plan around them.

**Roles and privileges.** There is no `GRANT` or `REVOKE`. Access is the file's access. If a process can open the file writable, it can write. `PRAGMA query_only` is a connection switch the host sets, not a rule the database enforces against a determined client.

**Schemas.** One file is one namespace. `ATTACH` adds another file to the connection; that is a second database, not a schema inside this one.

**General `ALTER TABLE`.** SQLite supports `RENAME TO`, `RENAME COLUMN`, `ADD COLUMN`, and, since 3.35, `DROP COLUMN`, with restrictions. Changing a column's type or adding a constraint means rebuilding the table: create the new one, copy the rows, drop the old one, rename. The production course covers the rebuild and `PRAGMA user_version`.

**Many writers.** One writer commits at a time. Readers can run alongside the writer under WAL, but two writers serialise. A second writer waits for its busy timeout and then fails with `SQLITE_BUSY`. PostgreSQL runs many writers against the same pages.

**Strong typing.** Without `STRICT`, a declared type is an affinity. A column declared `INT` can hold text. PostgreSQL rejects that write. `STRICT` tables, added in 3.37, give you the guarantee per table with a short list of allowed types.

`EXPLAIN ANALYZE` is missing too. Plans can be read; measurements cannot.

## Stack the tables

`UNION ALL` appends one result to another. Every branch must return the same number of columns, in the same order. The first branch names them.

```sql
SELECT 'customers' AS relation, COUNT(*) AS table_rows FROM customers
UNION ALL
SELECT 'products', COUNT(*) FROM products
ORDER BY table_rows DESC;
```

The exercise asks for all four commerce tables. Add the other two the same way.

## The whole store in one row

The positive case in one query:

```sql
SELECT (SELECT COUNT(*) FROM customers)   AS customers,
       (SELECT COUNT(*) FROM products)    AS products,
       (SELECT COUNT(*) FROM orders)      AS orders,
       (SELECT COUNT(*) FROM order_items) AS order_items;
```

| customers | products | orders | order_items |
| --- | --- | --- | --- |
| 30 | 20 | 80 | 160 |

Move the file and you have moved the database. `VACUUM INTO` or the backup API gives you a consistent snapshot without a server dump. Ship a read-only copy when you want a sandbox that cannot be broken.
