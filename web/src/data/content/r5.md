# JSON, generated columns and expression indexes

The `products` table has six columns, and every product fits them. Real catalogs rarely stay that tidy. A jacket carries a size and a fabric, a lamp carries a wattage and a bulb fitting, and the next product carries fields nobody has needed yet. One column per attribute produces a table that is mostly `NULL`, and a schema change every time a new attribute appears.

The alternative is to store the varying part as a JSON document in one text column. JSON is a text format for nested values: objects in braces, arrays in brackets, `"name": value` pairs inside them. SQLite reads and writes it without an extension, because the JSON functions are part of the library.

This chapter covers that trade. It reads a document, builds one from rows, computes a column from the row that holds it, and indexes the JSON path you search. The last part is where the mistakes live, because an index on a JSON path only helps a query that asks for the path in the same spelling.

## JSON is text in a column

Start where the dataset already is. `products` has no JSON column, and `json_object()` builds a document from the columns it has:

```sql
SELECT json_object('id', id, 'name', name, 'price', price) AS product
FROM products
WHERE id IN (1, 12)
ORDER BY id;
```

| product |
| --- |
| {"id":1,"name":"Aurora Wireless Earbuds","price":59} |
| {"id":12,"name":"Granite Cookware Set","price":210} |

Read the second row against the table. `price` is stored as `210` and the document repeats it as `210`, with no decimals, because a JSON number has no scale to keep. The column named `price` in the document is a member, not a table column, and nothing outside the document checks what it holds.

The result is a string. `json_object()` returns TEXT, and a column that holds documents declares `TEXT`. There is no JSON type and no write-time validation unless you ask for it with `CHECK (json_valid(payload))`. A binary form, JSONB, has existed since 3.45, and you have to ask for it by name. The plain functions store and return text.

That single decision explains the rest. A document is data you can copy, concatenate and compare as a string. The cost is that every function parses the text it is given, which is cheap for the size a row holds.

## `json1` is in the build

`json1` is the name of the JSON extension, and on any modern build it is compiled in. There is no `CREATE EXTENSION` and no package to load. The functions you will use are `json_valid()`, `json_object()`, `json_extract()`, `json_group_array()`, and the two shorthand operators that arrive with 3.38.

| form | returns | `typeof` of the result |
| --- | --- | --- |
| `payload -> '$.kind'` | the value as JSON text | `text` |
| `payload ->> '$.kind'` | the value as a SQL value | `integer`, `real`, `text`, or `null` |

The path is a string that starts at `$`, the document root. `$.kind` names a member, `$.tags[0]` names the first element of an array member, and `$` alone means the whole document.

The names are worth slowing over, because they read alike and behave differently. `json_extract(document, path)` does the work, and both operators are shorthand for it. `->` keeps the JSON spelling of the value. `->>` unwraps it into a SQL value, which is what a `WHERE` clause usually compares.

## Reading a document

Here is one document and both spellings:

```sql
SELECT json_extract('{"sku": "QC-1", "qty": 3}', '$.qty') AS qty,
       '{"sku": "QC-1"}' ->> '$.sku' AS sku;
```

| qty | sku |
| --- | --- |
| 3 | QC-1 |

`json_extract` parses the text, walks to `qty`, and returns the JSON number `3` as a SQL integer. `->>` walks to `sku` and returns the string without its quotes. The mapping is fixed: a JSON number becomes an integer or a real, a JSON string becomes text, `true` becomes `1`, `false` becomes `0`, and `null` becomes SQL `NULL`.

Now do it to a column. A table with a payload column is the shape most applications use, so create one in the workspace:

```sql
CREATE TABLE events (
    id      INTEGER PRIMARY KEY,
    payload TEXT NOT NULL CHECK (json_valid(payload))
);

INSERT INTO events (payload) VALUES
  ('{"kind": "visit",  "product": 3}'),
  ('{"kind": "order",  "product": 3}'),
  ('{"kind": "visit",  "product": 7}'),
  ('{"kind": "refund", "product": 7}');
```

The `CHECK` is the only validation the schema offers. Send `{kind: visit}`, which is not valid JSON, and the write stops with `CHECK constraint failed: json_valid(payload)`. Send a well-formed document that is missing `kind` and nothing objects, because a `CHECK` on the document tests the text, not the shape.

Filtering reads the payload like a column:

```sql
SELECT id, payload ->> '$.kind' AS kind, json_extract(payload, '$.product') AS product
FROM events
WHERE payload ->> '$.kind' = 'visit'
ORDER BY id;
```

| id | kind | product |
| --- | --- | --- |
| 1 | visit | 3 |
| 3 | visit | 7 |

Two of the four rows survive. The `WHERE` clause parses each payload, unwraps `kind`, compares it to the text `visit`, and keeps the matches. The `SELECT` list does the same work again for the rows that survive, which is the price of the text representation.

## The mistake `->` invites

The two operators look like punctuation. Here is the filter with the single arrow, which reads just as reasonable:

```sql
SELECT count(*) AS matched
FROM events
WHERE payload -> '$.kind' = 'visit';
```

| matched |
| --- |
| 0 |

Zero rows, and no error. `->` returned `"visit"`, quotes included, and a JSON value is not the SQL text `visit`. The comparison fails on every row, so the query answers "there are none" when the table holds two.

The same trap catches numbers, where it is harder to see. `payload -> '$.product'` returns the text `3`, not the integer 3, and `= 3` compares a text value to a number, which is false in SQLite. Add `->>` instead of `->` and the count changes:

```sql
SELECT count(*) AS matched
FROM events
WHERE payload ->> '$.kind' = 'visit';
```

| matched |
| --- |
| 2 |

The habit is to decide what you want out of the path. If the value is going into a comparison, an aggregate or an application, `->>` gives you the SQL value. If the value is going into a larger document, `->` keeps the JSON form, which is what `json_group_array()` and `json_object()` expect.

## Building JSON from rows

The other direction: a result set becomes a document with `json_group_array()` inside a `GROUP BY`. The demo query groups the catalog by category and collects the names:

```sql
SELECT category,
       json_group_array(name) AS products
FROM (SELECT category, name FROM products ORDER BY category, name)
GROUP BY category
ORDER BY category;
```

| category | products |
| --- | --- |
| Electronics | ["Aurora Wireless Earbuds","Nimbus Headphones","Noise-Cancel Earmuffs","Pulse Fitness Tracker","Vertex Mechanical Keyboard"] |
| Home | ["Bamboo Shelf","Cedar Desk Lamp","Ceramic Vase","Linen Duvet Cover","Wool Throw Blanket"] |
| Kitchen | ["Copper Kettle","Espresso Tamper","Granite Cookware Set","Maple Cutting Board"] |
| Outdoor | ["Discontinued Camp Stove","Harbor Rain Shell","Rope Dog Leash","Solar Camp Lantern","Summit Hiking Poles","Trail Runner Jacket"] |

Four groups, four arrays, and the inner `ORDER BY` is doing work that is easy to delete. Drop it and the same query returns the same names in a different order.

```sql
SELECT json_group_array(name) AS products
FROM products
WHERE category = 'Outdoor';
```

| products |
| --- |
| ["Trail Runner Jacket","Harbor Rain Shell","Summit Hiking Poles","Solar Camp Lantern","Rope Dog Leash","Discontinued Camp Stove"] |

The array holds the same six products as the demo row above, in primary-key order instead of name order. The aggregate collects rows in whatever order the scan produced them, and a scan of `products` walks the table in primary-key order. Nothing in the statement promises that order, so the array is stable today and not by contract.

Order the subquery and the array becomes a function of the data:

```sql
SELECT json_group_array(name) AS products
FROM (SELECT name FROM products WHERE category = 'Outdoor' ORDER BY name);
```

| products |
| --- |
| ["Discontinued Camp Stove","Harbor Rain Shell","Rope Dog Leash","Solar Camp Lantern","Summit Hiking Poles","Trail Runner Jacket"] |

That is the whole trick: sort the rows first, then aggregate. The exercise grades the array as a string, so the order is part of the answer, and this is the difference between a correct result and a failed comparison.

## Generated columns compute from a row

A generated column is a column whose value comes from an expression over other columns in the same row. You never write it, and it cannot disagree with the data it reads. Chapter 3 left the money column to you: `REAL` keeps the fraction, or a text column fixes the scale yourself. A generated column gives you both from one stored value:

```sql
CREATE TABLE products_v2 (
    id        INTEGER PRIMARY KEY,
    name      TEXT NOT NULL,
    price     NUMERIC NOT NULL,
    price_txt TEXT GENERATED ALWAYS AS (printf('%.2f', price)) STORED
);

INSERT INTO products_v2 (id, name, price)
SELECT id, name, price FROM products WHERE id IN (1, 4, 6);
```

| id | name | price | price_txt |
| --- | --- | --- | --- |
| 1 | Aurora Wireless Earbuds | 59 | 59.00 |
| 4 | Cedar Desk Lamp | 42.5 | 42.50 |
| 6 | Pulse Fitness Tracker | 74.25 | 74.25 |

Look at `price` in row 1: `59`, not `59.00`. The stored value is the number. `price_txt` fixes two decimals at write time, so the report reads a string that is already the right shape. The insert lists three columns and the fourth fills itself, because a generated column cannot take a value from an `INSERT`.

The keyword after the expression decides when the work happens. `STORED` computes once, on write, and puts the result in the row. `VIRTUAL` computes on read, stores nothing in the row, and costs the expression every time the row is read. Both can carry an index in this build, and the index holds the computed value either way, so the row pays for the storage only when the column is `STORED`.

The expression can read JSON too. `kind TEXT GENERATED ALWAYS AS (json_extract(payload, '$.kind'))` turns a path into an ordinary column, which is one way to index a JSON member by name instead of by expression.

## Index the expression, or a slice

An index on a JSON path indexes an expression, and `CREATE INDEX` accepts one.

```sql
CREATE INDEX events_kind_idx ON events (json_extract(payload, '$.kind'));
```

Now ask the planner what it does with the matching query.

```sql
EXPLAIN QUERY PLAN
SELECT id FROM events WHERE json_extract(payload, '$.kind') = 'visit';
```

| id | parent | notused | detail |
| --- | --- | --- | --- |
| 3 | 0 | 53 | SEARCH events USING COVERING INDEX events_kind_idx (<expr>=?) |

One seek, and `COVERING` means the index answered the query without opening the table. The detail line shows `<expr>=?` where a plain column index would name the column, which is how the planner marks the search key as an expression rather than a column.

The same filter with the arrow spelling does not get that plan:

```sql
EXPLAIN QUERY PLAN
SELECT id FROM events WHERE payload ->> '$.kind' = 'visit';
```

| id | parent | notused | detail |
| --- | --- | --- | --- |
| 2 | 0 | 216 | SCAN events |

Same rows, same answer, and the engine visits all four payloads to find them. The index stores one expression, `json_extract(payload, '$.kind')`. A query uses it only when it asks for that expression, through the same function with the same path. `payload ->> '$.kind'` is a different expression, so the index has nothing to offer.

Try this: swap the two spellings in the query above and run `EXPLAIN QUERY PLAN` after each one. The detail line changes from `SEARCH events USING COVERING INDEX events_kind_idx` to `SCAN events`, and the result stays four rows. The spelling is the index key.

That is the rule to carry away, and it is not specific to JSON. `CREATE INDEX products_name_nocase ON products (name COLLATE NOCASE)` answers `WHERE name = 'copper kettle' COLLATE NOCASE` with a seek. Drop the `COLLATE NOCASE` from the query and the plan reads `SCAN products USING COVERING INDEX products_name_nocase`, a walk, because the comparison and the index disagree about case.

A partial index takes the other approach: it indexes only the rows a predicate keeps. `CREATE INDEX orders_pending ON orders (customer_id) WHERE status = 'pending'` holds the 10 pending orders instead of all 80. The planner uses it when the query's `WHERE` implies that slice, as `WHERE status = 'pending' AND customer_id = 3` does. Ask for `status = 'shipped'` and the index cannot answer, because it holds none of those rows.

Chapter 6 of the essentials course reads plans in full. The skill to bring here is the habit. After you add an index for a JSON query, read the plan again and check that the detail line says `SEARCH` and names the index.

## What to remember

What I would do: store the varying part as JSON only when the shape varies. Keep the fields you filter on as generated columns or indexed expressions, and write those expressions exactly as the query writes them. A JSON column is not a licence to stop modelling.

- A JSON document is TEXT. `json_object()` and `json_group_array()` return text, and a column that holds documents declares `TEXT`.
- `json1` is compiled into the library. There is no extension to create.
- `json_extract()` and `->` return JSON, and `->>` returns the SQL value. Compare with `->>`.
- `json_group_array()` collects rows in scan order, so sort the subquery when the array order matters.
- A generated column computes from its row. `STORED` writes the value, `VIRTUAL` computes on read, and both can be indexed.
- An expression index serves only the exact expression the query uses, so `->>` and `json_extract()` are different keys to the planner.

## Check yourself

**1. A column holds `{"qty": 3}`. Why does `WHERE payload -> '$.qty' = 3` return no rows?**

<details>
<summary>Answer</summary>

`->` returns the value in JSON form, which is the text `3`, and comparing text to the integer 3 is false. `->>` returns the SQL integer 3, so that comparison matches. The return type is the difference, not the path.

</details>

**2. Two `json_group_array` queries return the same six names in different orders. Which one is the answer, and why?**

<details>
<summary>Answer</summary>

The one whose subquery has an `ORDER BY`. The aggregate collects rows in scan order, which the statement does not define, so the unordered array follows the table's storage order. Sorting the rows first makes the array a function of the data, and the exercise compares the string exactly.

</details>

**3. `price` is stored as `59` and `price_txt` reads `59.00`. What produced the difference, and when?**

<details>
<summary>Answer</summary>

`price_txt` is a `STORED` generated column, so `printf('%.2f', price)` ran once, on the insert, and the result sits in the row. The stored number kept its own form, which is `59`. A `VIRTUAL` column would run the same expression on every read instead.

</details>

**4. You index `json_extract(payload, '$.kind')` and the query that filters on `payload ->> '$.kind'` still scans. Why?**

<details>
<summary>Answer</summary>

Because the index holds one expression, and the query asks for a different one. The planner matches an index expression only against the identical expression in the query, so the arrow spelling cannot use a `json_extract` index. Rewrite the query to match the index, or index the spelling the query uses.

</details>

**5. A `CHECK (json_valid(payload))` constraint accepts `{"kind": null}`. What does that tell you about the check?**

<details>
<summary>Answer</summary>

It tests whether the text parses as JSON, and that document parses. It does not require the `kind` member, require a value for it, or reject unknown members. Shape rules need a separate expression or an application check.

</details>
