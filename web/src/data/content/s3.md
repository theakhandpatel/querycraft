# rowid, INTEGER PRIMARY KEY and AUTOINCREMENT

An order holds two lines for the same product: same quantity, same price, added twice by mistake. You still have to delete one of the two, and no clause over the visible columns can name the row you mean.

SQLite answers that with an address it keeps for every row, whether or not you declared one. The address is called the `rowid`. This chapter shows where it lives, how an `INTEGER PRIMARY KEY` column becomes it, and what `AUTOINCREMENT` adds.

## Every row has an address

An ordinary SQLite table is not a loose pile of rows. It is a B-tree whose keys are 64-bit signed integers. The key is the storage address of the row, and it is called the `rowid`.

Two things follow. The rows sit on disk in key order, so walking them in address order costs nothing extra. You can also reach a row by its address without knowing anything else about it. The duplicate lines in the intro need that second property: with no address to name, a delete matches both rows or neither. `products` shows the address next to the column that already holds the same number:

```sql
SELECT rowid AS rid, id, name
FROM products
ORDER BY id
LIMIT 3;
```

| rid | id | name |
| --- | --- | --- |
| 1 | 1 | Aurora Wireless Earbuds |
| 2 | 2 | Nimbus Headphones |
| 3 | 3 | Linen Duvet Cover |

The address has three spellings: `rowid`, `_rowid_` and `oid`. SQLite answers to all three, so a table with its own column named `rowid` still has two other names for the built-in address.

Write `AS rid` when you select both columns. Two result columns holding the same number need two names, and the exercise that follows asks for the same.

## A table you did not key still gets one

The `dataset_meta` table declares `dataset TEXT PRIMARY KEY`. No integer, no rowid in the schema, and yet the address exists:

```sql
SELECT rowid, dataset, version
FROM dataset_meta;
```

| rowid | dataset | version |
| --- | --- | --- |
| 1 | commerce | 1 |

The table holds one row and that row sits at address 1. Nothing in the `CREATE TABLE` statement mentions it, because the address is a property of the table itself. `SELECT *` never shows it: the address appears in a result only when you name it.

This table also closes a loose end from chapter 1. The catalog listed an index named `sqlite_autoindex_dataset_meta_1`, and now you can say what it is for. The table's own B-tree is keyed by the rowid, and the text key `commerce` needs a B-tree of its own, so SQLite builds one and names it for you. One table, two trees, two orders over the same row.

A plain read walks the rowid tree, so rows arrive in address order. That is a habit of the scan, not a promise, so write `ORDER BY` when the order matters.

## The alias rule is narrower than it looks

Here is the rule that makes `id` and `rowid` agree. When a column's declared type is exactly `INTEGER`, and it is the table's single declared `PRIMARY KEY`, that column is the rowid.

The rule is not a copy. No second index is built and no duplicate number is stored. Reading `id` reads the B-tree key, and inserting into `id` sets the key. That is why the two columns in the first query agreed: one value, two names.

The word `INTEGER` has to be exact. `INT` gives a column integer affinity, which chapter 2 covered, but affinity is not identity. This schema is wrong:

```sql
CREATE TABLE t_int (id INT PRIMARY KEY, name TEXT);
INSERT INTO t_int (name) VALUES ('a'), ('b');
SELECT rowid, id, name FROM t_int;
```

| rowid | id | name |
| --- | --- | --- |
| 1 | NULL | a |
| 2 | NULL | b |

The insert left `id` out, and SQLite had nothing to fill it with, because `INT PRIMARY KEY` is not the address. The address was still assigned, so `rowid` counts 1 and 2 while `id` holds nothing. A `PRIMARY KEY` that accepts a null protects nothing: both rows are unidentified, and SQLite allows as many null ids as you insert.

The fix is one word: declare the type as `INTEGER` and the column becomes the address. Two other declarations break the alias in the same silence. `INTEGER PRIMARY KEY DESC` is not an alias, because the descending marker makes it a different declaration. A composite `PRIMARY KEY (a, b)` is not an alias either, since the rule needs a single column. Neither mistake raises an error. Both leave you with a table whose declared key is not the address.

Try this: run the `t_int` script again with the type written as `INTEGER`, under a second table name. The addresses stay 1 and 2, and `id` now fills from them, so the two columns hold the same number.

## The address is a value you inserted

The order ids in this dataset start at 1001, not at 1.

```sql
SELECT MIN(rowid) AS min_rid, MAX(rowid) AS max_rid, COUNT(*) AS rows
FROM orders;
```

| min_rid | max_rid | rows |
| --- | --- | --- |
| 1001 | 1080 | 80 |

The seed wrote those ids into the column, and the address took the same values. Nothing in SQLite insists that keys start at 1, or that they run without gaps. An address is a stored value.

`products` runs 1 to 20 and `order_items` runs 1 to 160, because those seeds count from one. That gap-free run is a property of the seed, not of the engine.

It also gives the exercise its starting point. The three highest-id `order_items` sit at addresses 160, 159 and 158, so sorting by `id` descending begins at 160. Select `rowid` beside `id` and you will see the same number twice.

## The number SQLite picks for you

When you leave the id out of an insert, SQLite does not keep a counter. It reads the largest key currently in the table, adds one, and uses that.

The rule is simple and the consequences surprise people. Delete the row with the largest key and the next insert takes that key back. Run these demos one statement at a time; a workspace reset brings the seed back.

```sql
CREATE TABLE t_plain (id INTEGER PRIMARY KEY, name TEXT);
INSERT INTO t_plain (name) VALUES ('a'), ('b'), ('c');
DELETE FROM t_plain WHERE id = 3;
INSERT INTO t_plain (name) VALUES ('d');
SELECT id, name FROM t_plain ORDER BY id;
```

| id | name |
| --- | --- |
| 1 | a |
| 2 | b |
| 3 | d |

Key 3 was recycled because nothing in the file records that it was used. Delete a row from the middle instead, and the gap stays for good, because the largest key did not change.

```sql
CREATE TABLE t_gap (id INTEGER PRIMARY KEY, name TEXT);
INSERT INTO t_gap (name) VALUES ('a'), ('b'), ('c');
DELETE FROM t_gap WHERE id = 2;
INSERT INTO t_gap (name) VALUES ('d');
SELECT id, name FROM t_gap ORDER BY id;
```

| id | name |
| --- | --- |
| 1 | a |
| 3 | c |
| 4 | d |

Now the mistake that costs real time. It is easy to read an id as a row number, so a report assumes the highest id counts the rows.

```sql
SELECT COUNT(*) AS rows, MAX(id) AS max_id,
       MAX(id) - MIN(id) + 1 AS span
FROM t_gap;
```

| rows | max_id | span |
| --- | --- | --- |
| 3 | 4 | 4 |

Three rows, but the key span is four. An invoice number copied from `MAX(id)` breaks here. So does a check that reads a gap as a missing row, or a claim that order 4 is the fourth order.

The key answers "which row", never "how many rows". If you need a position, compute it when you read the data, with `ROW_NUMBER()` or a count in the report.

## AUTOINCREMENT removes reuse and nothing else

`AUTOINCREMENT` adds one promise: SQLite will never hand out a key that this table has used before, even if that row is gone. Delete every row, insert again, and the number keeps rising.

```sql
CREATE TABLE t_auto (id INTEGER PRIMARY KEY AUTOINCREMENT, name TEXT);
INSERT INTO t_auto (name) VALUES ('a'), ('b');
DELETE FROM t_auto;
INSERT INTO t_auto (name) VALUES ('c');
SELECT id, name FROM t_auto;
```

| id | name |
| --- | --- |
| 3 | c |

The same script on a plain `INTEGER PRIMARY KEY` table gives key 1, because an empty table has no largest key to build on.

The promise has a mechanism, and the mechanism has a cost. SQLite keeps the largest key ever issued in a table named `sqlite_sequence`, one row per AUTOINCREMENT table, and writes it on each insert. That is one more table in the file and one extra page written per insert. After the insert above, the bookkeeping row reads:

```sql
SELECT name, seq FROM sqlite_sequence;
```

| name | seq |
| --- | --- |
| t_auto | 3 |

Two limits come with it. The key space is the 64-bit signed integer range, and when an AUTOINCREMENT table reaches 9223372036854775807 the next insert stops with `database or disk is full` rather than reuse a number. Deleting the table's row from `sqlite_sequence` resets the count, and that puts reuse back.

The commerce dataset declares `AUTOINCREMENT` nowhere. The catalog keeps each `CREATE TABLE` statement, so you can check that claim rather than trust it:

```sql
SELECT name, sql LIKE '%AUTOINCREMENT%' AS uses_autoinc
FROM sqlite_master
WHERE type = 'table'
  AND name IN ('customers', 'products', 'orders', 'order_items')
ORDER BY name;
```

| name | uses_autoinc |
| --- | --- |
| customers | 0 |
| order_items | 0 |
| orders | 0 |
| products | 0 |

Four zeros. Nothing in this file pays the cost above, and a lesson database that resets on each load has nothing to protect anyway.

| Declaration | Assigns keys | Reuses after delete | Extra storage |
| --- | --- | --- | --- |
| `INTEGER PRIMARY KEY` | yes | yes | none |
| `INTEGER PRIMARY KEY AUTOINCREMENT` | yes | no | `sqlite_sequence` row |

The rule to carry away: `AUTOINCREMENT` promises no reuse. It does not promise consecutive keys, because a gap you leave in the middle stays a gap.

## Choosing a declaration

The default is `INTEGER PRIMARY KEY`. It is free, it is the address, and the commerce schema uses it on all four tables.

Reach for `AUTOINCREMENT` when a repeated key would be a real error, such as a receipt number that must never point at two payments. Reach for neither when you supply the ids yourself, which is the usual case for reference data with fixed codes.

A third option solves the opposite problem. `WITHOUT ROWID` makes the declared `PRIMARY KEY` the storage key and drops the hidden integer.

```sql
CREATE TABLE kv (k TEXT PRIMARY KEY, v TEXT) WITHOUT ROWID;
```

Ask such a table for `rowid` and SQLite reports `no such column: rowid`. Use it for small, narrow tables that are always read by key, where a second B-tree is one tree too many. The cost is that a secondary index there stores the full primary key instead of an integer address, so a wide key is paid for again in each index.

PostgreSQL has none of this. There is no rowid and no hidden address, so there is nothing to alias. A surrogate key there is a column whose default draws from a sequence object: `GENERATED ALWAYS AS IDENTITY` in current schemas, `serial` in older ones. The sequence keeps its state outside the table, and like `AUTOINCREMENT` it never reuses a value, which is why a failed insert in PostgreSQL still leaves a gap.

## What to remember

What I would do: declare every surrogate key as exactly `INTEGER PRIMARY KEY`, and reach for `AUTOINCREMENT` only when a reused key would be a real error, not to get consecutive numbers. Check `MAX(id)` against `COUNT(*)` before either number goes into a report.

- Every ordinary table has a rowid, and you reach it through `rowid`, `_rowid_` or `oid`.
- A declared type of exactly `INTEGER` on a single-column `PRIMARY KEY` makes that column the rowid. `INT`, `INTEGER PRIMARY KEY DESC` and composite keys do not.
- The rowid is the key value you stored, not a row number. `MAX(id)` is not a count.
- When you omit the key, SQLite uses one more than the largest key present, so the top key can come back and middle gaps stay.
- `AUTOINCREMENT` forbids reuse with a `sqlite_sequence` row, and still allows gaps.
- `WITHOUT ROWID` makes the declared primary key the storage key and removes the address.

## Check yourself

**1. A table declares `id INT PRIMARY KEY` and inserts rows without an id. What goes into `id`, and why is that not the alias rule failing halfway?**

<details>
<summary>Answer</summary>

`id` stays NULL, because the column is not the rowid. The alias needs the declared type to be exactly `INTEGER`, and `INT` only selects integer affinity. The row still gets an address, which is why `rowid` shows 1 and 2 while `id` shows nothing.

</details>

**2. Why does the next insert reuse the highest deleted id, and what does `AUTOINCREMENT` change?**

<details>
<summary>Answer</summary>

The next key is one more than the largest key present. That largest key is now the row below the one you deleted. `AUTOINCREMENT` records the highest key ever issued in `sqlite_sequence`, so the new row gets a fresh number.

</details>

**3. A report gives the total number of orders as `MAX(id)` from `orders`. What would you check, and what would you quote instead?**

<details>
<summary>Answer</summary>

Check `COUNT(*)`, because the key is a value, not a count. Deleted rows and explicit ids both push the maximum away from the number of rows. Quote the count. If the ids look surprising, read `MIN(id)` beside it: this dataset spans 1001 to 1080 with 80 rows.

</details>

**4. Why does `SELECT rowid, dataset FROM dataset_meta` work while the same query on a `WITHOUT ROWID` table fails?**

<details>
<summary>Answer</summary>

There is no address to name in a `WITHOUT ROWID` table. Its rows sit in a B-tree keyed by the declared primary key. `dataset_meta` is an ordinary rowid table whose primary key is text, so it keeps the address and adds an automatic index for the text key.

</details>
