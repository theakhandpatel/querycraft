# Revenue reports with conditional aggregation

The finance team wants one number per month: how much the shop sold. The obvious query adds up every line in `order_items` and returns 24,335.55, and nobody at the shop would call that revenue. The total mixes five order statuses, and the number gives no sign of which one it counted.

| order status | line amount |
| --- | --- |
| completed | 10241.59 |
| refunded | 4100.33 |
| shipped | 3979.11 |
| pending | 3591.03 |
| cancelled | 2423.49 |

A revenue number is a sum with a rule attached. The rule decides which lines count, and it changes from one metric to the next. Revenue counts completed orders. A cancellations report counts cancelled orders. A returns report counts refunded orders.

This chapter puts the rule inside the aggregate, so the query states it on the page and a reviewer can check it.

## Every line is not revenue

An aggregate is a function that turns many rows into one value: `COUNT`, `SUM`, `AVG`, `MIN`, `MAX`. Conditional aggregation is the same function with a condition attached, so it sees only the rows that pass.

The table above is why the condition matters. Every line in the dataset has an amount, and the same line belongs in different reports depending on the rule. Revenue reads the completed rows. A returns report reads the refunded rows.

Add everything together and you get a number that describes no question anyone asked. A wrong total that looks like a total is the expensive kind: it reaches the report unchallenged.

The usual alternative is to export the lines and apply the rule in a spreadsheet. That works until the rule changes or the person who wrote the formula leaves. The query is a better home for the rule, because the rule sits next to the number it produces.

## Two levers: WHERE removes rows, FILTER ignores them for one total

A `WHERE` clause holds a predicate: a test each row must pass. It runs before grouping, so a row that fails disappears for the whole query.

`FILTER (WHERE ...)` is different. It attaches a condition to one aggregate. The row stays in the group, and only that aggregate skips it.

```text
FROM  ->  WHERE  ->  GROUP BY  ->  aggregates, each with its own FILTER  ->  SELECT  ->  ORDER BY
```

Read the pipeline left to right. `WHERE` decides which rows reach the grouping at all. A filter inside an aggregate decides which of the rows that arrived are visible to that one total. Two rows in the same group can feed different aggregates, or none of them.

That difference buys you a report. Without `FILTER`, a query can carry only one status rule, because `WHERE` applies to every column in the result.

The older way to build the same report is one query per status, stitched together afterwards in a spreadsheet or a join. That works, and it costs repeated scans and a hand-assembled result. One statement with several filtered aggregates reads the rows once and cannot drift out of step with itself.

## Attach the condition to one aggregate

```sql
SELECT DATE_TRUNC('month', o.ordered_at)::date AS month,
       COUNT(*) FILTER (WHERE o.status = 'completed') AS completed,
       COUNT(*) FILTER (WHERE o.status = 'cancelled') AS cancelled
FROM orders o
GROUP BY 1
ORDER BY 1;
```

| month | completed | cancelled |
| --- | --- | --- |
| 2026-01-01 | 8 | 2 |
| 2026-02-01 | 8 | 3 |
| 2026-03-01 | 9 | 2 |
| 2026-04-01 | 7 | 3 |
| 2026-05-01 | 5 | 1 |

Take the query in pieces, in the order the engine works through it.

`FROM orders o` reads the 80 checkout rows. `DATE_TRUNC('month', o.ordered_at)` rounds each timestamp down to the first instant of its month, and the `::date` cast drops the time so the output reads `2026-01-01` instead of a full timestamp. `GROUP BY 1` groups by the first item in the `SELECT` list, which is `month`. The engine now holds one group per month.

Each `COUNT(*) FILTER (...) AS ...` runs inside its group. The `WHERE` word inside the parentheses belongs to the filter, not to the statement. January's group holds 16 orders, and the first count sees the 8 completed ones while the second sees the 2 cancelled ones. Nothing was removed from the group, so both counts can read it.

Add the columns down and you get 37 completed orders and 11 cancelled ones. Those are counts of order rows, because `COUNT(*)` counts whatever the aggregate was handed. A later section shows what happens when a join hands it lines instead.

## The same rule written with CASE

`FILTER` is the shortest spelling, and it is not the only one. A `CASE` expression inside `SUM` states the same rule.

```sql
SELECT DATE_TRUNC('month', o.ordered_at)::date AS month,
       SUM(CASE WHEN o.status = 'completed'
                THEN oi.quantity * oi.unit_price
                ELSE 0 END) AS revenue
FROM orders o
JOIN order_items oi ON oi.order_id = o.id
GROUP BY 1
ORDER BY 1;
```

`CASE` produces one value per row: the line amount when the order is completed, and 0 otherwise. `SUM` adds those values, so the non-completed lines contribute nothing. Run both spellings on this dataset and the two columns agree to the cent in every month.

Two details keep the `CASE` version correct. `SUM` ignores `NULL`, so you can drop the `ELSE 0` and return `NULL` instead, and the total is unchanged. `COUNT` needs more care, because it counts non-null values: the CASE version of a conditional count needs a `1` in the `THEN` branch and nothing in `ELSE`.

Try this: delete `ELSE 0` from the `CASE` and run the query again. The revenue column does not move, because `SUM` skips the `NULL` that the missing branch returns.

Choose `FILTER` when several metrics sit side by side, because the condition stays attached to its own total. Choose `CASE` when you need a portable query, or when the rule is a scale with several branches rather than a yes or no.

## A conditional count is not a WHERE clause

The tempting mistake is to add both levers to the same report. Add `WHERE o.status = 'completed'` to the section three query for safety, and it still runs.

```sql
SELECT DATE_TRUNC('month', o.ordered_at)::date AS month,
       COUNT(*) FILTER (WHERE o.status = 'completed') AS completed,
       COUNT(*) FILTER (WHERE o.status = 'cancelled') AS cancelled
FROM orders o
WHERE o.status = 'completed'
GROUP BY 1
ORDER BY 1;
```

| month | completed | cancelled |
| --- | --- | --- |
| 2026-01-01 | 8 | 0 |
| 2026-02-01 | 8 | 0 |
| 2026-03-01 | 9 | 0 |
| 2026-04-01 | 7 | 0 |
| 2026-05-01 | 5 | 0 |

The `completed` column is right and the `cancelled` column is zero in every month. `WHERE` ran first and removed all 11 cancelled orders. Each month's group was built from completed rows only, so the second filter found nothing to count.

It reported 0, not an error, which is the dangerous part: the report looks like a month with no cancellations. A column of zeros across every group is worth checking against the clause above it before you check the data.

The correction is to pick one lever per metric. If several metrics need different rules, put each rule in its own aggregate and leave status out of `WHERE`. If the whole report shares one rule, put it in `WHERE` and drop the filters. Writing the same condition twice is what produces the silent zero.

## A filtered count reads the rows it was given

Here is the same completed count with the lines joined in.

```sql
SELECT DATE_TRUNC('month', o.ordered_at)::date AS month,
       COUNT(*) FILTER (WHERE o.status = 'completed') AS completed
FROM orders o
JOIN order_items oi ON oi.order_id = o.id
GROUP BY 1
ORDER BY 1;
```

| month | completed |
| --- | --- |
| 2026-01-01 | 18 |
| 2026-02-01 | 14 |
| 2026-03-01 | 18 |
| 2026-04-01 | 14 |
| 2026-05-01 | 10 |

January holds 8 completed orders, and this query reports 18. The filter did its job; the count measured the wrong thing. The join fanned each order out into its lines, so `COUNT(*)` counted lines. The 37 completed orders carry 74 lines, and 74 is the total this query adds up to.

The repair is the one from Chapter 2, applied to a filtered count. Count distinct order ids, as in `COUNT(DISTINCT o.id) FILTER (WHERE o.status = 'completed')`, or count orders before joining and join the small result. A filtered count is still a count, and it can only report on the rows it was given.

## What the exercise asks

The exercise asks for net revenue per month, completed orders only, oldest month first. One metric, one rule: the report has no column that needs a different condition. That makes `WHERE` the right lever, because removing 86 non-completed line rows before grouping is exactly the intent, and the aggregate then adds up the 74 that remain.

`net_revenue` is `SUM(oi.quantity * oi.unit_price)`. The `quantity` and `unit_price` live on `order_items`, and the status lives on `orders`, so the query needs the join from Chapter 2 before it can group by month.

When your query is right it returns five rows with two columns, `month` and `net_revenue`:

| month | net_revenue |
| --- | --- |
| 2026-01-01 | 2132.55 |
| 2026-02-01 | 2311.07 |
| 2026-03-01 | 2456.40 |
| 2026-04-01 | 1803.62 |
| 2026-05-01 | 1537.95 |

The `FILTER` spelling returns the same five numbers. Reading either one is the skill this chapter is after: find the rule, check which lever carries it, then check the grain the aggregate sees. If a month comes back as a full timestamp instead of a date, the `::date` cast is missing.

## What to remember

**What I would do:** write the rule in the query, and treat every zero column and every inflated count as a question about the lever. A filtered count over a join reports lines. A `WHERE` beside a filter on the same condition reports zero. Both mistakes return a number, and neither raises an error.

- Revenue is a sum with a rule attached. Put the rule in the query, not in a spreadsheet.
- `WHERE` removes rows before grouping, so it affects every aggregate in the query.
- `FILTER (WHERE ...)` restricts one aggregate and leaves the others reading the full group.
- `SUM(CASE WHEN ... THEN ... ELSE 0 END)` is the same rule in portable SQL.
- Adding `WHERE` and a filter on the same condition silently zeroes the filtered metric.
- A filtered count counts the rows that reached it, so a join to `order_items` turns an order count into a line count.

## Check yourself

**1. A report needs completed orders and cancelled orders in one row per month. Which lever carries the status rule, and why not the other one?**

<details>
<summary>Answer</summary>

`FILTER`, one per count. A `WHERE` on status would remove one of the two kinds of row before grouping, so one of the columns could only ever report zero.

</details>

**2. The two-metric query with `WHERE o.status = 'completed'` returns 0 in the cancelled column. Why 0 rather than an error?**

<details>
<summary>Answer</summary>

`WHERE` ran before `GROUP BY` and dropped every cancelled order, so no group contained one. A count over an empty set is 0, and 0 is a valid number, so the query reports it without complaint.

</details>

**3. Why does the same completed count report 18 in January once you join `order_items`?**

<details>
<summary>Answer</summary>

The join produced one row per line, so `COUNT(*)` counted lines that belong to completed orders. The month holds 8 completed orders and 18 such lines. Join the line table only when the metric is about lines.

</details>

**4. A filtered `SUM` runs over an empty set. What does it return, and what does a filtered `COUNT` return?**

<details>
<summary>Answer</summary>

`SUM` returns `NULL`, because it has no values to add. `COUNT` returns 0, because it counts a set with nothing in it. Wrap the sum in `COALESCE(..., 0)` when a report needs a zero.

</details>
