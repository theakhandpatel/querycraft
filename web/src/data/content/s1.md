# A database in a file

Copy one file onto a laptop that has never seen this project and the whole store travels with it: 30 customers, 20 products, 80 orders, 160 order lines. That convenience carries a cost. The file is the database, so a copy taken while a write runs is not a backup. A write can be refused even when your SQL is sound.

SQLite stores a database in an ordinary file, and the engine that reads the file is a library inside whatever program opened it. There is no server to install and no port to open. You connect by opening a path, and the table definitions live inside the file. That one decision explains most of what follows, so start with the file itself, then read the catalog it carries.

## One file, one database

A SQLite database is a file with a known internal layout. The first 16 bytes read `SQLite format 3`, and after that the file is a sequence of equal-size pages holding table rows, index entries, free space, and the catalog.

Because the format is the database, a file that is not in that format is not a database. Point SQLite at a CSV and it refuses:

```
file is not a database
```

That error names the real rule. There is no import step, no separate data directory, and no metadata store somewhere else.

Copy the file while nothing is writing to it and you have a backup of every row. Take the copy while a write is in flight and you can catch a half-finished change. The cost lands at restore time, when the half-finished file is all you have left. Wait for a quiet moment, or use SQLite's backup interface, which copies a live database safely.

PostgreSQL works the other way round. A server owns a data directory, listens on a port, and hands out connections to clients.

| | SQLite | PostgreSQL |
| --- | --- | --- |
| Database | one file | a server and its data directory |
| Engine | a library in your process | a separate server process |
| Connect | open a path | host, port, user, password |

The comparison is worth keeping, because the rest of this course keeps returning to it. No server means no accounts, no grants, and no network protocol. The file is the boundary.

## The engine runs inside your program

When a program opens a SQLite database, it loads the SQLite library and the library opens the file. Your query is a function call in that process, not a message to another machine. The connection is a handle on the file, and the rows come back through the same call.

Two consequences follow immediately.

The SQL does not name a database. `SELECT COUNT(*) FROM customers;` names a table, and the connection already knows which file that table lives in. The host opened the file, so the file is the context.

Nothing authenticates you. SQLite has no users, no roles, and no `GRANT`. If a process can open the file for writing, that process can change every row in it. Two programs can still share one file, because SQLite uses file locks to let one writer in at a time, but that is coordination, not permission. Chapter 7 takes up what this means for a real deployment.

## The catalog is a table

SQLite keeps the schema in a table, and that table is queryable. `sqlite_master` holds one row per table, index, view, and trigger. `sqlite_schema` is the newer spelling of the same name, and both work.

Each row has a `type`, a `name`, the `tbl_name` it belongs to, a `rootpage`, and a `sql` column holding the `CREATE` statement as it was written. The catalog does not list itself.

Because the catalog is a table, everything you know about `SELECT` applies to it. You filter it with `WHERE`, sort it with `ORDER BY`, and match names with `LIKE`, exactly as you would filter `products`.

## Reading the catalog

This query asks for the tables and the indexes in one list:

```sql
SELECT type, name
FROM sqlite_master
WHERE type IN ('table', 'index')
ORDER BY type DESC, name;
```

| type | name |
| --- | --- |
| table | customers |
| table | dataset_meta |
| table | order_items |
| table | orders |
| table | products |
| index | order_items_order_id_idx |
| index | order_items_product_id_idx |
| index | orders_customer_id_idx |
| index | orders_status_idx |
| index | sqlite_autoindex_dataset_meta_1 |

Read the result in the order the clauses produced it. `FROM` reads ten catalog rows. `WHERE` keeps the rows whose type is `table` or `index`, which in this file is all ten. `ORDER BY type DESC, name` sorts by type, and the text `table` sorts after `index`, so the five tables come first. Within each type the sort is alphabetical.

Try this: delete the `WHERE` line and run the query again. The same ten rows come back in the same order, because the filter keeps every row in this file. It matters once a view or a trigger joins the catalog.

One index is not in the seed file. `sqlite_autoindex_dataset_meta_1` came from the primary key on `dataset_meta`, and SQLite named it. Its `sql` value is null, because no one wrote a `CREATE` statement for it. The other four indexes are rows someone wrote:

```sql
SELECT name, sql
FROM sqlite_master
WHERE name = 'orders_customer_id_idx';
```

| name | sql |
| --- | --- |
| orders_customer_id_idx | CREATE INDEX orders_customer_id_idx ON orders (customer_id) |

The catalog also answers questions about columns. `PRAGMA table_info('products')` returns one row per column, in declaration order:

```sql
PRAGMA table_info('products');
```

| cid | name | type | notnull | dflt_value | pk |
| --- | --- | --- | --- | --- | --- |
| 0 | id | INTEGER | 0 | NULL | 1 |
| 1 | name | TEXT | 1 | NULL | 0 |
| 2 | category | TEXT | 1 | NULL | 0 |
| 3 | price | NUMERIC | 1 | NULL | 0 |
| 4 | stock | INTEGER | 1 | 0 | 0 |
| 5 | active | BOOLEAN | 1 | 1 | 0 |

`notnull` and `pk` are numbers, so `1` means yes. The `id` row reports `0` in `notnull` even though it is the key, because the column has no declared `NOT NULL`; the `pk` column is what marks the key. Chapter 3 comes back to that. The `type` column shows the declared type, word for word, and Chapter 2 shows why that word is weaker than it looks.

## A wrong turn: ten objects, five tables

Here is a mistake that is easy to make on the first day. You want to know how many tables the database has, so you count the rows of the catalog:

```sql
SELECT COUNT(*) AS objects
FROM sqlite_master;
```

| objects |
| --- |
| 10 |

Ten. You write down "this database has ten tables" and move on. The number is correct and the sentence is wrong, because `sqlite_master` holds five tables and five indexes. The count answered "how many schema objects exist", not "how many tables exist".

The fix is to keep the type column in the answer:

```sql
SELECT type, COUNT(*) AS objects
FROM sqlite_master
GROUP BY type
ORDER BY type;
```

| type | objects |
| --- | --- |
| index | 5 |
| table | 5 |

Five and five. The difference is the `GROUP BY type`, which forms one group per object kind instead of collapsing everything into one number.

The habit worth keeping: when a count surprises you, ask what one row means. Here a row is a table, an index, a view, or a trigger. Counting rows counts all four kinds together.

## A file you can open read-only

A host can open a database for reading only, and SQLite enforces that at the engine level. The gateway serves the shared dataset that way: it opens the file with SQLite's own `mode=ro` plus the `query_only` pragma. Reads work there, and a write is refused:

```sql
INSERT INTO dataset_meta (dataset, version) VALUES ('oops', 1);
```

```
attempt to write a readonly database
```

That message is the file refusing the write, not a permission check. There is no account to fix and no grant to add. The host opened a handle that cannot write, and your statement reached a door that does not open.

This browser workspace is the other case. It holds the schema in memory, so it accepts that insert, and the reset control rebuilds the seeded database. Run the statement here and it succeeds; the read-only reply above belongs to the gateway's shared copy. Both behaviours come from the same engine, and the difference is the handle the host opened.

## One database, one namespace

A SQLite file holds one database and one namespace. Table names in that file resolve in one place, so `customers` and `main.customers` are the same table. There is no `search_path` and no schema qualifier to search through.

`ATTACH` adds a second file to the open connection:

```sql
ATTACH ':memory:' AS archive;
```

After that, a table in the second database is named `archive.orders`, and the same table in the first is `main.orders`. The two catalogs stay separate, and an unqualified name still resolves in `main`. The attached database here starts empty, so `SELECT COUNT(*) FROM archive.sqlite_master` returns 0 until something is created in it.

The tables you query in this course carry no schema prefix for the same reason. There is no `dataset` schema to hold them, so `products` is the whole name.

## What to remember

What I would do: read `sqlite_master` before you trust any count or column name, and filter by `type` whenever you mean tables. Copy the file only when nothing is writing to it, and open it read-only when a task does not need writes.

- A SQLite database is one file in a published format. Copying the file copies the database, when no write is in flight.
- The engine is a library inside your program. There is no server, no account, and no grant.
- The schema is a table. `sqlite_master` and `sqlite_schema` are the same catalog, one row per table, index, view, or trigger.
- Catalog rows carry the `CREATE` statement in the `sql` column, and SQLite's own objects have a null there.
- Counting catalog rows counts every object kind. Filter or group by `type` when you mean tables.
- A read-only connection refuses writes with `attempt to write a readonly database`. That is the file, not a missing permission.

## Check yourself

**1. Why does `SELECT COUNT(*) FROM customers` work without naming a database?**

<details>
<summary>Answer</summary>

Because the connection is already attached to one file. The host opens the file and hands you the connection, so an unqualified table name has one place to resolve. There is no server to name and no schema to prefix.

</details>

**2. A classmate reports that the file has ten tables. What did they measure, and what should they measure instead?**

<details>
<summary>Answer</summary>

They counted rows in `sqlite_master`, which returns 10. That counts tables and indexes together. Grouping by `type` gives five tables and five indexes, or a `WHERE type = 'table'` filter gives the five table names.

</details>

**3. The `sqlite_autoindex_dataset_meta_1` row has a name and a null `sql`. Why?**

<details>
<summary>Answer</summary>

SQLite created that index itself to enforce the `PRIMARY KEY` on `dataset_meta`. No one wrote a `CREATE INDEX` statement, so there is no stored text to keep. The four other indexes in this file came from the schema file, so their `sql` values hold the statements.

</details>

**4. Your `INSERT` fails with `attempt to write a readonly database`. What should you check first?**

<details>
<summary>Answer</summary>

Whether the connection was opened read-only. The shared dataset is served with `mode=ro` and `query_only`, so every write is refused there. If you need to write, use a writable workspace, such as the in-browser one, or a file of your own.

</details>
